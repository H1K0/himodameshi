# Соглашения по структуре репозитория и коммитам

Этот документ описывает правила организации репозитория и оформления коммитов для проекта **Himo**.  
Цель — чтобы история проекта была читаемой, а каждый участник понимал, где что лежит и как оформить изменение.

---

## Структура репозитория

```
himodameshi/
├── app/          # Flutter-приложение (Himo)
├── firmware/     # Прошивка ESP32-S3
├── hardware/     # Схемы, BOM, даташиты компонентов
├── docs/         # Документация
│   ├── spec/     # Спецификации, ФТТ
│   ├── adr/      # Архитектурные решения
│   └── assets/   # Диаграммы и прочее
├── scripts/      # Вспомогательные скрипты
├── .gitignore
├── CHANGELOG.md
├── GIT_CONVENTIONS.md
└── README.md
```

Каждая папка верхнего уровня — это отдельный технологический стек. Внутренняя структура каждой папки остаётся на усмотрение ответственного за неё.

Единственное жёсткое правило — не смешивать стеки между папками:

| Папка       | Что туда идёт                                                                               |
| ----------- | ------------------------------------------------------------------------------------------- |
| `app/`      | Мобильное приложение                                                                        |
| `firmware/` | Прошивка ESP32                                                                              |
| `hardware/` | Схемы KiCad, BOM, даташиты                                                                  |
| `docs/`     | Документация: спецификации (`spec/`), архитектурные решения (`adr/`), диаграммы (`assets/`) |
| `scripts/`  | Вспомогательная автоматизация                                                               |

## Соглашение по коммитам

Используется формат **Conventional Commits** с описанием на русском языке.

### Формат

```
<тип>(<scope>): <описание>
```

- **Тип** — категория изменения (см. таблицу ниже).
- **Scope** — папка верхнего уровня, которую затрагивает коммит.
- **Описание** — краткое, на русском, с маленькой буквы, без точки в конце.

### Типы коммитов

| Тип        | Когда использовать                  | Пример                                                |
| ---------- | ----------------------------------- | ----------------------------------------------------- |
| `feat`     | Новая функциональность              | добавлен экран подключения по BLE                     |
| `fix`      | Исправление бага                    | исправлен расчёт порога CMRR                          |
| `refactor` | Рефакторинг без изменения поведения | InsightGenerator вынесен в интерфейс                  |
| `test`     | Добавление или правка тестов        | юнит-тесты расчёта Health Score                       |
| `docs`     | Документация и ADR                  | ФТТ обновлены до версии 0.3 (`spec`), ADR-003 (`adr`) |
| `chore`    | Зависимости, конфиги, даташиты      | добавлен даташит ADS1115                              |
| `wip`      | Незавершённое, промежуточный коммит | начат модуль теста экранирования                      |
| `merge`    | Слияние любой ветки                 | экран тестирования завершён [Himo-12]                 |

> `wip` используется только для промежуточных сохранений в процессе работы.  
> В историю `dev` такие коммиты попадают как есть — внутри merge-пузыря задачной ветки.

### Допустимые значения scope

Scope строго соответствует папке верхнего уровня — за исключением `docs`, где scope уточняет подпапку, чтобы было понятно, что именно изменилось:

| Scope          | Папка          | Когда использовать            |
| -------------- | -------------- | ----------------------------- |
| `app`          | `app/`         | любые изменения в приложении  |
| `firmware`     | `firmware/`    | любые изменения в прошивке    |
| `hardware`     | `hardware/`    | схемы, BOM, даташиты          |
| `docs(spec)`   | `docs/spec/`   | ФТТ, архитектурные описания   |
| `docs(adr)`    | `docs/adr/`    | Architecture Decision Records |
| `docs(assets)` | `docs/assets/` | картинки, диаграммы           |
| `scripts`      | `scripts/`     | вспомогательные скрипты       |

Если изменение затрагивает сразу несколько папок — укажи их через `/`:

```
chore(app/firmware): обновлены интерфейсы BLE-пакетов
```

### Плохие коммиты ❌ и как их исправить

| Плохой коммит                                                      | Проблема                                       | Исправленный вариант                                    |
| ------------------------------------------------------------------ | ---------------------------------------------- | ------------------------------------------------------- |
| `fix`                                                              | Нет scope и описания — непонятно вообще ничего | `fix(firmware): исправлен расчёт сопротивления на pin2` |
| `изменения`                                                        | Нет типа, нет scope, описание бессмысленно     | `refactor(app): упрощён парсинг BLE-пакетов`            |
| `feat(app): Added BLE screen`                                      | Описание на английском при русском соглашении  | `feat(app): добавлен экран подключения по BLE`          |
| `feat(app): Добавил экран BLE, поправил баги, обновил зависимости` | Один коммит на три несвязанных изменения       | Три отдельных коммита: `feat`, `fix`, `chore`           |
| `feat: всё`                                                        | Нет scope, описание бессмысленно               | Разбить на конкретные коммиты по папкам                 |
| `WIP`                                                              | Нет scope и описания                           | `wip(app): начата реализация экрана паспорта`           |

## Architecture Decision Records (ADR)

Папка `docs/adr/` предназначена для фиксации **архитектурных решений** — не что было сделано, а почему именно так.

Формат файла: `NNN-короткое-название.md`, где `NNN` — порядковый номер.

Каждый ADR содержит четыре раздела:

```markdown
# ADR-NNN: Заголовок решения

## Контекст

Что за ситуация, почему вообще нужно было принимать решение.

## Решение

Что именно решили сделать.

## Варианты, которые рассматривались

Что ещё рассматривалось и почему отказались.

## Последствия

Что это решение даёт и какие ограничения накладывает.
```

### Пример ADR

**Файл:** `docs/adr/003-ina128p-selection.md`

```markdown
# ADR-003: Выбор INA128P вместо INA217

## Контекст

Для теста CMRR нужен инструментальный усилитель с высоким коэффициентом
подавления синфазной помехи. Изначально в документации был указан INA217,
но он оказался недоступен на российском рынке (Chipdip, OZON).

## Решение

Использовать INA128P: CMRR ≥ 100 дБ, корпус DIP-8, свободно доступен
в Chipdip, характеристики полностью подходят для MVP.

## Варианты, которые рассматривались

- **INA217** — оригинальный выбор, недоступен в РФ.
- **INA163** — есть в наличии, но избыточен и дороже.

## Последствия

Привязка к INA128P зафиксирована в BOM и схеме. Если в будущем потребуется
замена, нужно проверить распиновку и пересмотреть схему усилителя.
```

> ADR не нужно писать на каждое решение — только на те, которые не очевидны
> и которые будет сложно объяснить через полгода без контекста.

## Ветки

Схема из двух постоянных веток:

| Ветка          | Назначение                                                   |
| -------------- | ------------------------------------------------------------ |
| `master`       | Стабильный код. Напрямую не коммитим — только мёрж из `dev`. |
| `dev`          | Основная рабочая ветка. Сюда мёржатся задачи после приёмки.  |
| `task/Himo-XX` | Ветка под конкретную задачу из Vikunja. Стартует от `dev`.   |

Каждая задача из Vikunja выполняется в отдельной ветке, стартующей от `dev`:

```
task/<тикер>
```

Примеры: `task/Himo-12`, `task/Himo-47`.

Ветка создаётся в момент начала работы над задачей (перевод задачи в статус "In progress") и мёржится обратно в `dev` после того, как руководитель проекта принял задачу в Vikunja (пометил завершенной).

### Жизненный цикл задачной ветки

#### Начало задачи

Перед созданием ветки убедиться, что `dev` актуален:

```bash
git checkout dev
git pull origin dev
```

Создать ветку от `dev`:

```bash
git checkout -b task/Himo-12
```

Перевести задачу в Vikunja в статус **In progress**.

#### В процессе работы

Коммитить по мере готовности отдельных частей. Использовать `wip` для промежуточных сохранений:

```bash
git add app/lib/screens/cable_detail.dart
git commit -m "feat(app): добавлен экран паспорта кабеля"
```

```bash
git add app/lib/screens/cable_detail.dart
git commit -m "wip(app): начата секция истории тестов"
```

#### Сдача задачи на приёмку

1. Убедиться, что `dev` не ушёл вперёд. Если ушёл — подтянуть изменения в ветку задачи:

```bash
git checkout task/Himo-12
git merge dev
```

2. Опубликовать ветку:

```bash
git push origin task/Himo-12
```

3. В Gitea создать **запрос на слияние** (Pull Request): `task/Himo-12` → `dev`. В заголовке указать тикер и суть задачи. PM принимает задачу в Vikunja и вливает ветку в `dev` через Gitea.

#### После того как PM слил ветку

Синхронизировать локальный `dev`:

```bash
git checkout dev
git pull origin dev
```

Ветка `task/Himo-12` остаётся в репозитории — по ней видно, кто и когда работал над задачей.

### Стратегия мёржа

Во всех направлениях используется **merge commit (`--no-ff`)**. История сохраняет полную структуру веток: видно, из какой ветки пришли изменения, когда именно и что входило в задачу.

**`task/Himo-XX` → `dev`: merge commit**

```bash
git checkout dev
git merge --no-ff task/Himo-12
```

Git откроет редактор — вписать название merge-коммита. Формат: `merge(<scope>): <описание задачи> [Himo-XX]`

```
merge(app): добавлен экран подключения по BLE [Himo-12]
merge(firmware): модуль теста целостности проводников [Himo-23]
merge(app): исправлен порог CMRR при сравнении с нормой [Himo-31]
merge(app/docs): экран паспорта кабеля и схема БД [Himo-41]
```

Scope отражает папки, которых касается задача — так же, как в обычных коммитах.

**`dev` → `master`: merge commit**

```bash
git checkout master
git merge --no-ff dev
```

Название отражает суть вошедших изменений или номер релиза:

```
merge(dev): экран тестирования, тест целостности, исправление CMRR
merge(dev): релиз v0.2 — BLE-соединение и база кабелей
```

### Разрешение конфликтов

Конфликты возникают, если одни и те же файлы менялись и в `dev`, и в ветке задачи. Git сообщит об этом сразу после `git merge`:

```
CONFLICT (content): Merge conflict in app/lib/main.dart
Automatic merge failed; fix conflicts and then commit the result.
```

**1. Посмотреть список конфликтных файлов**

```bash
git status
```

**2. Открыть файл и разрешить конфликт**

Git помечает конфликтные зоны маркерами:

```
<<<<<<< HEAD
// версия из dev
=======
// версия из task/Himo-12
>>>>>>> task/Himo-12
```

Оставить нужный вариант (или объединить оба), убрать все маркеры `<<<<<<<`, `=======`, `>>>>>>>`.

В VSCode конфликты выделяются визуально — доступны кнопки:

- **Accept Current Change** — взять версию `dev`
- **Accept Incoming Change** — взять версию ветки
- **Accept Both Changes** — вставить оба варианта подряд

**3. Отметить файл как разрешённый и завершить мерж**

```bash
git add app/lib/main.dart
git merge --continue        # откроет редактор для merge-коммита
```

**Отменить мерж** (если нужно разобраться в ветке перед слиянием):

```bash
git merge --abort           # возвращает всё к состоянию до git merge
```

**Профилактика: актуализировать ветку перед мержем**

Если `dev` ушёл вперёд пока шла работа над задачей — перед мержем обновить ветку:

```bash
git checkout task/Himo-12
git rebase dev              # переносит коммиты ветки поверх текущего dev
git checkout dev
git merge --no-ff task/Himo-12
```

Конфликты всё равно придётся разрешать, но по одному коммиту — проще понять, что с чем столкнулось.

| Откуда         | Куда     | Когда мёржим               | Стратегия    | Пример merge-коммита                                      |

## Вопросы по задачам

Если в процессе работы над задачей возникает существенный вопрос — создаётся issue в GitHub с упоминанием тикера Vikunja:

- **Заголовок** включает тикер: `[Himo-12] Вопрос по согласованию MTU в BLE-пакетах`
- **Метка** `Вопрос` обязательна
- Все последующие вопросы и обсуждения по этой теме ведутся внутри того же issue в виде комментариев — новые issue на тот же вопрос не создаются

Пример:

```
Заголовок: [Himo-23] Как обрабатывать short-circuit на pin1–pin2 XLR?
Метка: Вопрос
```
