# Стайлгайд

Версия 1.0 · Ноябрь 2026

Этот документ описывает, как оформляется код и документация проекта **Himo**: язык, именование, комментарии, форматирование и обработка ошибок — для каждого стека репозитория.
Как работать с ветками, коммитами и PR — в [CONTRIBUTING.md](CONTRIBUTING.md).

Правила записаны по уже существующему коду: в основном они фиксируют то, как код написан сейчас. Там, где код расходится между файлами, выбран один вариант. Разделы с правилами описывают только то, как должно быть; места, где код им пока не соответствует, собраны в одном списке — в разделе [Существующий код](#существующий-код).

## Общие правила

### Язык

| Что                                                       | Язык       | Пример                                            |
| --------------------------------------------------------- | ---------- | ------------------------------------------------- |
| Идентификаторы: переменные, функции, типы, файлы, таблицы | английский | `cableNameMaxLen`, `health_score_calculator.dart` |
| Комментарии в коде, doc-комментарии                       | русский    | `// ListCables отдаёт каталог кабелей команды.`   |
| Тексты для пользователя: интерфейс, `detail` в ошибках    | русский    | `"Запрос не прошёл проверку"`                     |
| Сообщения в логах и тексты внутренних ошибок              | английский | `log.Info("server started")`, `"parse hash: %w"`  |
| Машиночитаемые коды и значения перечислений               | английский | `cable_archived`, `jack_trs`                      |
| Документация, ADR, описания в `openapi.yaml`              | русский    | —                                                 |
| Сообщения коммитов и заголовки PR                         | русский    | по [CONTRIBUTING.md](CONTRIBUTING.md#коммиты)     |

Логи остаются на английском, потому что их читают инструменты и поиск по логам, а не пользователь. Английские комментарии в старых служебных файлах (`.gitattributes`, `CODEOWNERS`, `.pre-commit-config.yaml`) и в файлах, созданных шаблоном генератора (`sv create`: `vite.config.ts`, `app.d.ts`), переписывать не нужно; новые комментарии пишутся по-русски.

### Файлы

- Кодировка UTF-8, переводы строк LF — это закреплено в [.gitattributes](.gitattributes). На Windows: `git config --global core.autocrlf false`.
- В конце файла — один перевод строки, в концах строк — без пробелов.
- Отступы — пробелами. Исключение — Go: табуляция, её ставит форматтер.
- Имена файлов — латиницей, без пробелов. Исключение — даташиты и схемы в замороженном `hardware/`.
- Длина строки и переносы — такие, как их расставляет форматтер стека. В Dart это 80 символов (`dart format`), в TypeScript и Svelte — 100 (Prettier). В Go жёсткого предела нет: длинный вызов или сигнатура переносится по аргументам, по одному на строку. В SQL — по одному условию на строку (см. [Оформление](#оформление)).

### Комментарии

Комментарий объясняет **почему** код написан так, а не что он делает: что делает код, видно из самого кода.

```go
// ✅ В образе distroless нет curl, поэтому healthcheck контейнера — подкоманда сервера (ADR-015).
// ❌ Проверяем, что первый аргумент — healthcheck.
```

- Если решение следует из ADR или требования — дайте ссылку на него в комментарии: `(ADR-022)`, `(HUB-3)`, `(data-model.md, раздел 6)`. Так читатель находит обоснование без поиска по истории.
- Комментарий — полное предложение с заглавной буквы. Точка в конце — по стилю соседних комментариев файла; короткие пометки в конце строки пишутся без точки: `-- NULL у удалённых`.
- Закомментированный код, отладочный вывод (`print`, `fmt.Println`, `console.log`) и `TODO` без кода задачи в PR не попадают. Отложенная работа — задача в YouGile; если ей нужна пометка в коде — `// TODO(YG-N): …`.

### Константы и «магические» значения

Пороги, лимиты, таймауты и прочие числа с предметным смыслом выносятся в именованные константы рядом с местом использования, с единицами измерения в имени или комментарии:

```dart
static const double cmrrFailThreshold = 40.0; // дБ
```

```go
const shutdownTimeout = 10 * time.Second
```

Значение, заданное в спецификации или контракте, объявляется **один раз в каждом компоненте**. Компоненты написаны на разных языках, поэтому общей константы у них быть не может; их согласует спецификация, и комментарий у константы ссылается на её раздел. Где объявляется значение:

- **Приложение** — в классе слоя `domain`, к которому относится значение. Пороги расчёта и цветовых зон Health Score живут в `HealthScoreCalculator`. Экраны и слой `data` берут их оттуда и не повторяют числа.
- **Hub** — в блоке `const` в начале файла пакета, который их использует: `cableNameMaxLen` в `server/cables.go`. Если значение нужно нескольким пакетам, оно объявляется экспортируемой константой в одном из них, остальные её импортируют. Лимиты полей совпадают с `maxLength` и `maximum` из контракта.
- **Веб** — в модуле `src/lib/`. Например, пороги Health Score — в `src/lib/health-score.ts`.

### Условия и ветвления

- **Ранний выход вместо вложенности.** Ошибки и особые случаи обрабатываются в начале функции и сразу возвращают результат; основной сценарий идёт без лишнего отступа. Так написаны обработчики Hub:

  ```go
  if !allowed {
  	return nil, errNotFound
  }
  ```

- **Сложное условие получает имя.** Условие из нескольких частей выносится в переменную, имя которой говорит, что оно означает:

  ```dart
  final bool anyRun = continuityRun || cmrrRun || freqRun;
  if (!anyRun) { … }
  ```

- **Без лишних отрицаний и сравнений с литералами:** `if (isConnected)`, а не `if (isConnected == true)`. Булева переменная называется утвердительно: `isArchived`, а не `isNotArchived`.
- **`switch` вместо цепочки `if`** по одному значению: перечисления, коды HTTP, типы кабелей. Для перечислений Dart сам проверяет, что разобраны все варианты.
- Смешанные `&&` и `||` в одном выражении — со скобками, даже если приоритет операторов и так даёт нужный порядок.
- В SQL необязательный фильтр — условие с проверкой параметра на `NULL`, а не склейка строки запроса (см. [Запросы sqlc](#запросы-sqlc)).

### DRY и KISS

**DRY — одно знание объявляется в одном месте.**

- Константы, коды ошибок и пороги из спецификаций — один раз (см. [Константы](#константы-и-магические-значения)).
- Контракт API — источник типов для всех клиентов: код сервера на Go, клиент на Dart и типы на TypeScript генерируются из `contracts/openapi.yaml`, а не пишутся вручную на каждом языке.
- Правило, описанное в одном документе, в другом не пересказывается, а даётся ссылкой — иначе документы со временем разойдутся.
- Общий код выносится, когда одинаковый фрагмент встречается в третий раз. Два похожих места — ещё не повод для абстракции: их может развести следующее же требование.

Допустимое дублирование:

- одинаковые фильтры в парных запросах sqlc (`ListCables` и `CountCables`): sqlc не умеет переиспользовать часть запроса, поэтому их связывает комментарий «Те же фильтры, что в ListCables»;
- подготовка данных в тестах: тест должен читаться сам по себе, без поиска общих помощников.

**KISS — выбирается простейшее решение, которое закрывает требование.** Проект — MVP: сложность добавляется, когда её требует задача, а не на будущее. Примеры из принятых решений: `limit` и `offset` вместо курсорной пагинации в списках и `PUT` вместо `PATCH` ([ADR-023](docs/adr/023-hub-api-conventions.md)), sqlc вместо ORM ([ADR-015](docs/adr/015-hub-stack.md)), синглтоны с подменой в тестах вместо DI-контейнера (см. [D](#d--инверсия-зависимостей)). Если решение сложнее очевидного, причина записывается в комментарии или в ADR.

### Секреты и конфигурация

Секреты не попадают в код и в git: значения — в переменных окружения или в неотслеживаемых файлах (`.env`, `app/config/dev.json`), образец — в отслеживаемом файле `*.example` с описанием каждой переменной. Проверку выполняет pre-commit (см. [CONTRIBUTING.md](CONTRIBUTING.md#проверки-перед-коммитом-pre-commit)).

## Принципы SOLID

SOLID в проекте — не самоцель. Разделение ответственности (S) и узкие интерфейсы (I) обязательны во всём коде. Расширение без правки кода (O), взаимозаменяемость реализаций (L) и зависимость от абстракций (D) применяются там, где у кода уже есть вторая реализация или её нужно подменять в тестах. Абстракции «на будущее», без второй реализации, не вводятся: для MVP они усложняют код и ничего не дают.

| Принцип | Hub                                                                                | Приложение                                                                       |
| ------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| S       | Пакет решает одну задачу; ответы с ошибками формирует только `handleErrors`        | `domain/` — только логика; экран не обращается к БД и сети напрямую              |
| O       | Новый код ошибки или раздел API — без правки общего кода                           | `InsightGenerator`, `BleDataSource`, веса Health Score                           |
| L       | Пул соединений и транзакция взаимозаменяемы через `store.DBTX`                     | Реализации `BleDataSource`, иерархия `InsightException`                          |
| I       | Маленькие интерфейсы у потребителя; исключение — сгенерированный интерфейс сервера | Интерфейс содержит только то, что нужно потребителю                              |
| D       | Зависимости — через конструктор, без интерфейсов-репозиториев                      | Интерфейсы — в `domain`, реализации — в `data`; зависимости подменяются в тестах |

**Веб.** Обязательны S и I. Страница показывает данные и обрабатывает действия, а запросы к API, данные-заглушки и общее состояние живут в `src/lib/`. Компонент получает через `$props` только то, что показывает. O, L и D пока не применяются: у каждого источника данных одна реализация, а переход с заглушек на API — замена модуля, а не вторая реализация интерфейса.

К прошивке SOLID не применяется: она заморожена, а код на Arduino framework процедурный.

### S — единственная ответственность

- **Hub.** Каждый пакет отвечает за одно: `config` — загрузка конфигурации, `auth` — пароли, токены и подпись Telegram без HTTP, `store` — только SQL, `server` — только HTTP. Ответы с ошибками формируются в одном месте — `handleErrors` в `problem.go`. Один обработчик — один маршрут, один файл — один раздел API.
- **Приложение.** `domain/` содержит только логику — `HealthScoreCalculator`, `FreqResponseStats`, `InsightGenerator` — без интерфейса и хранения. Экран показывает данные и обрабатывает действия пользователя; к БД, прибору и сети он обращается только через классы слоя `data`.
- Класс источника данных отвечает за один источник: обмен с прибором, локальную БД или API — не за несколько сразу.

### O — открытость для расширения

Применяется там, где вариантов уже несколько или замена запланирована:

- `InsightGenerator` — замена Z.ai на прокси Hub без изменений в интерфейсе ([ADR-018](docs/adr/018-insights-proxy.md));
- `BleDataSource` — mock-данные и настоящий прибор;
- веса Health Score заданы таблицей `baseWeights`: новый тип кабеля — новая строка таблицы, а не новая ветка `if`;
- в Hub новый код ошибки — новое значение в `problem.go`, новый раздел API — новый файл обработчиков; общий код при этом не меняется.

Точки расширения, иерархии классов и «плагины» без второй реализации не вводятся. Пока вариант один, код остаётся конкретным; абстракция выделяется, когда появляется второй.

### L — подстановка Лисков

Важна там, где у интерфейса несколько реализаций:

- `BleMockDataSource` и `BleRealDataSource` неотличимы для вызывающего кода: mock отдаёт пакеты строго по [BLE-протоколу](docs/spec/device/ble-protocol.md);
- подклассы `InsightException` обрабатываются кодом, который ловит базовый класс;
- в Hub пул соединений и транзакция взаимозаменяемы через `store.DBTX` — на этом основан `q.WithTx(tx)`.

Реализация не бросает «не поддерживается» на методы интерфейса и не сужает его контракт. Если реализации нужна только часть интерфейса — интерфейс разделяется (см. [I](#i--разделение-интерфейсов)).

### I — разделение интерфейсов

Интерфейс объявляет потребитель, и в нём только те методы, которые потребителю нужны.

- **Hub.** Интерфейс объявляется в пакете, который его использует, а не рядом с реализацией. Пример — `server`: `Pinger` содержит только `Ping` для `/health`, `DB` — только то, что серверу нужно от пула: `Pinger`, `store.DBTX` и `Begin`. Исключение — `StrictServerInterface` от oapi-codegen: один интерфейс на все операции API. Это сгенерированный код, он принимается как есть.
- **Приложение.** Интерфейс источника данных описывает один источник (см. [S](#s--единственная-ответственность)): потоку пакетов прибора и запросам к каталогу кабелей нужны разные интерфейсы.

### D — инверсия зависимостей

- **Hub.** Зависимости передаются через параметры конструктора — `server.New(db, cfg, log)`, глобальных переменных нет, текущее время подменяется полем `now`. Сервер при этом зависит от конкретного `*store.Queries`, без интерфейсов-репозиториев, и это осознанное решение: тесты API идут на настоящем PostgreSQL, и подменять хранилище в них не нужно. Интерфейс-репозиторий вводится, только когда нужна вторая реализация или подмена в тестах.
- **Приложение.** Зависимость направлена к `domain`: интерфейс и модели, с которыми работает бизнес-логика, объявлены в `domain`, реализация — в `data`, как у `InsightGenerator` и `ZaiInsightGenerator`. Синглтоны допустимы, если реализацию можно подменить в тестах — как в `InsightGeneratorProvider.overrideWith`. Способ внедрения зависимостей (синглтоны с подменой, Riverpod) выбирает разработчик приложения.

## Внешние API и сервисы

Внешние сервисы проекта: API Hub для приложения, LLM Z.ai для ИИ-комментариев ([ADR-020](docs/adr/020-zai-selection.md)), Telegram Login Widget для входа в Hub ([ADR-016](docs/adr/016-telegram-login-widget.md)).

- **Клиент — за интерфейсом, в одном месте.** Обращение к сервису живёт в слое `data` приложения, в отдельном пакете Hub или в `src/lib/api/` веба, остальной код работает с интерфейсом — как `InsightGenerator` и `ZaiInsightGenerator`. Формат запросов и ответов сервиса за пределы клиента не выходит.
- **Таймаут у каждого запроса.** Запрос без таймаута при пропавшей сети подвешивает экран. В `ZaiInsightGenerator` таймаут — 20 секунд; в Go он задаётся через `context.WithTimeout` или `http.Client{Timeout: …}`.
- **Ошибки сервиса переводятся в свои.** Сетевая ошибка, отказ в доступе, лимит запросов и сбой сервиса — разные классы, и по классу понятно, поможет ли повтор: `InsightNetworkException`, `InsightAuthException`, `InsightRateLimitException`, `InsightServerException`. HTTP-коды и тексты ошибок сервиса дальше клиента не расходятся.
- **Повтор — только для идемпотентных запросов** (`GET`, `PUT`, `DELETE`) и только при ошибках, которые повтор может исправить: сеть, `429`, `5xx`. При `429` учитывается заголовок `Retry-After`.
- **Ключи сервисов не попадают в сборку приложения.** Всё, что вшито в приложение, можно из него извлечь. Поэтому запросы к LLM идут через прокси Hub, а ключ хранится только на сервере ([ADR-018](docs/adr/018-insights-proxy.md)). В Hub ключи и токены — в переменных окружения (см. [Секреты и конфигурация](#секреты-и-конфигурация)).
- **Данные от внешнего сервиса проверяются.** Данные Login Widget сервер принимает только после проверки подписи и свежести `auth_date` (`auth.VerifyTelegram`). Ответ LLM — текст для показа пользователю, а не данные, от которых зависит логика.
- **API Hub для приложения:** клиент генерируется из контракта ([ADR-025](docs/adr/025-openapi-dart-generator.md)), ошибки различаются по `code` ([ADR-023](docs/adr/023-hub-api-conventions.md)), с каждым запросом передаётся заголовок `X-App-Version`.
- **API Hub для веба:** типы генерируются из контракта, сеанс — в cookie `HttpOnly` (см. [Запросы к API Hub](#запросы-к-api-hub)).

## Зависимости и версии библиотек

- **Файлы блокировки коммитятся:** `hub/go.sum`, `app/pubspec.lock`, `web/package-lock.json`. Так у всех участников и в CI собираются одни и те же версии. В CI и в Dockerfile зависимости веба ставятся через `npm ci`, а не `npm install`: `npm ci` берёт версии строго из файла блокировки.
- В вебе все пакеты — в `devDependencies`: они нужны только для сборки, в образ попадает собранная статика.
- **Версии инструментов закреплены точно**, без «последней»: генератор — `oapi-codegen@v2.4.1` в `go:generate`, хуки — `rev` в `.pre-commit-config.yaml`, базовые образы — по тегу в Dockerfile, действия CI — по версии: `actions/checkout@v4`.
- **Новая зависимость — с обоснованием.** В описании PR — зачем она и почему не хватает стандартной библиотеки или уже подключённых пакетов. Ради пары строк кода библиотека не подключается. Предпочтение — пакетам, которые поддерживаются и широко используются.
- **Обновление зависимостей — отдельным коммитом** `chore` с версией в описании: `chore(app): обновлён flutter_blue_plus до 1.31`. Обновление вместе с изменением кода мешает понять, что именно сломало сборку.
- **Неиспользуемая зависимость удаляется:** из `go.mod` — командой `go mod tidy`, из `pubspec.yaml` — вручную, из `package.json` — командой `npm uninstall`.
- Версия языка указана в `go.mod` и в `pubspec.yaml` (`environment: sdk`); её повышение — тоже отдельный коммит `chore`.

## Совместимость и сопровождение

Как выпускаются версии и делаются хотфиксы — в [CONTRIBUTING.md](CONTRIBUTING.md#релизы-теги-компонентов) и [ADR-024](docs/adr/024-hotfix-branches.md). Здесь — правила для кода, которые позволяют обновлять компоненты по отдельности: у пользователя может стоять старая версия приложения, а Hub уже обновлён.

- **API Hub меняется только совместимо.** Добавить поле в ответ или необязательный параметр можно; удалить или переименовать поле, изменить его тип или смысл — нельзя. Несовместимое изменение — новая версия API (`/api/v2`), старая работает, пока ею пользуются. Клиенты не падают на незнакомых полях ответа.
- **Веб выпускается вместе с сервером** — в одном образе и с одной версией ([ADR-015](docs/adr/015-hub-stack.md)). Поэтому совместимость со старыми версиями API для веба не нужна: изменение контракта и веба делается в одном PR.
- **Устаревшее приложение отсекается сервером**, а не ломается молча. Если версия из `X-App-Version` ниже `MIN_APP_VERSION`, сервер отвечает `426` с `code: app_outdated`, и приложение просит обновиться ([ADR-023](docs/adr/023-hub-api-conventions.md)). `MIN_APP_VERSION` повышается, только когда старые версии действительно не могут работать с сервером.
- **Схема БД меняется только вперёд:** применённая миграция не правится (см. [Миграции](#миграции)), локальная БД приложения меняется повышением версии (см. [Локальная БД](#локальная-бд)).
- **BLE-протокол версионируется полем `pv`:** изменение любого поля — через ADR и новую версию `pv` ([ble-protocol.md](docs/spec/device/ble-protocol.md)).
- **Изменение поведения документируется:** изменение требований — новая версия спецификации в `docs/spec/`, архитектурное решение — ADR.

## Go — Himo Hub (`hub/`)

За основу взяты [Effective Go](https://go.dev/doc/effective_go) и [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments). Ниже — то, что они не определяют или что в проекте принято по-своему.

### Форматирование и линтер

- Форматтер — **gofumpt** (строже, чем `gofmt`), линтер — **golangci-lint** с `go vet` ([ADR-015](docs/adr/015-hub-stack.md)). Перед PR запустите их локально:

  ```bash
  cd hub
  gofumpt -l -w .
  golangci-lint run
  ```

- Импорты — тремя группами через пустую строку: стандартная библиотека, внешние модули, пакеты самого Hub.

  ```go
  import (
  	"context"
  	"errors"

  	"github.com/gin-gonic/gin"

  	"git.hakoniwa.ru/tech/himodameshi/hub/internal/api"
  )
  ```

### Структура

- Точка входа — `cmd/hub`, весь остальной код — в `internal/`. Пакет называется по тому, что он предоставляет: `config`, `auth`, `store`, `server`.
- `main` только разбирает аргументы и вызывает `run`, который возвращает ошибку. `os.Exit` — только в `main`.
- Обработчики API — в `internal/server`, по файлу на раздел контракта: `cables.go`, `teams.go`, `tests.go`. Тесты — рядом, в `*_test.go`.

### Именование

- Обычные правила Go: `camelCase` для неэкспортируемых имён, `PascalCase` для экспортируемых, аббревиатуры целиком в одном регистре: `userID`, `DatabaseURL`, `toAPICable`.
- Ошибки-значения — `errXxx` (`errNotFound`, `errCableArchived`), конструкторы ошибок — по смыслу: `validationError(...)`, `versionConflict(...)`.
- Получатель метода — одна-две буквы по типу: `(s *Server)`, `(p *problem)`.

### Doc-комментарии

Каждое экспортируемое имя и каждый пакет имеют doc-комментарий на русском, который начинается с имени:

```go
// Package config загружает конфигурацию сервера из переменных окружения.

// UpdateCable заменяет изменяемые атрибуты кабеля с оптимистичной блокировкой.
// Правка без изменений версию не меняет и в журнал не попадает.
```

Для неэкспортируемых функций комментарий пишется, когда из имени и сигнатуры не понятно, что функция делает или почему она устроена именно так.

### Ошибки

- Ошибка возвращается вызывающему, а не логируется на месте. Логирует тот, кто её окончательно обрабатывает, — для запросов это `handleErrors`.
- Если без контекста непонятно, где ошибка возникла, она оборачивается через `%w`, контекст — на английском, с маленькой буквы, без двоеточия и точки в конце: `fmt.Errorf("decode password hash salt: %w", err)`. Ошибку, смысл которой и так ясен, возвращают как есть.
- Проверка — через `errors.Is` и `errors.As`, не сравнением строк.
- **Ошибки API** — значения типа `*problem` из `problem.go` ([ADR-023](docs/adr/023-hub-api-conventions.md)). Обработчик возвращает их как обычную ошибку, ответ `application/problem+json` формирует `handleErrors`. Новый код ошибки добавляется одновременно в `problem.go` и в таблицу ошибок `contracts/openapi.yaml`. Внутренние подробности (текст ошибки БД, стек) в ответ клиенту не попадают — только в лог.

### Логи

- `log/slog` в JSON; логгер передаётся явно, не через глобальную переменную.
- Сообщение — короткая фраза на английском с маленькой буквы, без точки; данные — парами ключ–значение, а не в тексте сообщения. Ключи — `snake_case`, ошибка — под ключом `error`:

  ```go
  s.log.ErrorContext(c, "request failed", "method", c.Request.Method, "path", c.FullPath(), "error", err)
  ```

- В запросах — варианты `…Context`, чтобы в запись попал `request_id`.
- В лог не пишутся пароли, токены, хеши и содержимое тела запроса.

### Контекст и горутины

- `context.Context` — первый параметр функции, которая ходит в БД или в сеть или может долго выполняться. В структурах контекст не хранится.
- Контекст запроса передаётся дальше по цепочке вызовов, а не заменяется на `context.Background()`: так запрос к БД отменяется, когда клиент отключился. `context.Background()` — только в `main` и в фоновых задачах, у которых нет запроса.
- У каждой горутины есть способ завершиться и сообщить о результате — как сервер в `main`: ошибка уходит в канал `errc`, остановка — через `srv.Shutdown` с таймаутом.
- Общие данные горутин защищаются `sync.Mutex` или передаются через каналы. Тесты, где это важно, запускаются с `go test -race`.

### База данных

- Запросы — только через sqlc ([ADR-015](docs/adr/015-hub-stack.md)): SQL в `internal/store/queries/*.sql`, вызов — через сгенерированные методы `store.Queries`. SQL в строках Go допустим только в тестах для подготовки данных.
- Несколько изменений, которые должны выполниться вместе, — в одной транзакции через `pgx.BeginFunc` и `q.WithTx(tx)`.

### Сгенерированный код

`internal/api/api.gen.go` и `internal/store/*.sql.go` не правятся вручную. Изменение — в источнике (`contracts/openapi.yaml`, `queries/*.sql`, миграции) и перегенерация:

```bash
cd hub
go generate ./...
sqlc generate
```

Сгенерированные файлы коммитятся вместе с изменением источника, в том же коммите.

### Тесты

- Имена — `TestЧтоПроверяется` в `PascalCase`, по сценарию: `TestRegisterNicknameTaken`, `TestClientIPFromTrustedProxyOnly`.
- Несколько похожих случаев — табличный тест с `t.Run(tt.name, …)`; имена случаев — по-русски или по-английски, но одинаково в пределах файла.
- Вспомогательные функции вызывают `t.Helper()` первой строкой.
- Тесты API ходят через HTTP-обработчик и настоящий PostgreSQL, БД не подменяется моками.

## SQL — миграции и запросы Hub

Схема — [data-model.md](docs/spec/hub/data-model.md), миграции — `hub/internal/migrations`, запросы — `hub/internal/store/queries`.

### Оформление

- Ключевые слова — `ПРОПИСНЫМИ`: `SELECT`, `CREATE TABLE`, `NOT NULL`. Типы, функции и идентификаторы — строчными: `uuid`, `timestamptz`, `now()`, `count(*)`.
- Отступ — 4 пробела. Каждое условие `WHERE` — с новой строки, начиная с `AND`.
- В `CREATE TABLE` имена, типы и ограничения выровнены по колонкам; пояснение к столбцу — комментарием `--` в конце строки.

### Именование

| Объект            | Правило                           | Пример                                    |
| ----------------- | --------------------------------- | ----------------------------------------- |
| Таблица           | `snake_case`, множественное число | `cables`, `team_members`, `auth_sessions` |
| Столбец           | `snake_case`, единственное число  | `cable_type`, `health_score`              |
| Внешний ключ      | `<объект>_id`                     | `team_id`, `assignee_id`                  |
| Время события     | `<событие>_at`, тип `timestamptz` | `created_at`, `archived_at`, `revoked_at` |
| Флаг              | `is_<свойство>`, тип `boolean`    | `is_personal`                             |
| Индекс            | `<таблица>_<столбцы>_idx`         | `team_members_user_idx`                   |
| Уникальный индекс | `<таблица>_<столбцы>_uq`          | `users_nickname_uq`                       |

Значения перечислений хранятся как `text` с `CHECK (… IN (…))` и записываются в `snake_case` — так же, как в API и в BLE-протоколе.

### Миграции

- Файл — `NNNNN_что_меняется.sql` для goose, номер — следующий по порядку: `00002_cable_tags.sql`.
- В начале файла — комментарий о том, что и зачем меняется, со ссылкой на требование или ADR.
- Миграция, которая уже применена на dev или prod, не меняется: исправление — новой миграцией.

### Запросы sqlc

- Перед запросом — аннотация `-- name: ИмяЗапроса :one|:many|:exec`, имя — глагол в `PascalCase`: `ListCables`, `GetMemberRole`, `AdvanceChangeSeq`. Под аннотацией — комментарий, если у запроса есть неочевидные правила.
- Параметры — именованные: `@team_id`; необязательные фильтры — `sqlc.narg('name')` с проверкой на `NULL`. Позиционные `$1` — только в SQL внутри тестов.

## Dart — мобильное приложение (`app/`)

За основу взят [Effective Dart](https://dart.dev/effective-dart) и набор линтов `flutter_lints` из `analysis_options.yaml`.

### Форматирование и анализатор

- Форматтер — `dart format` со стандартными настройками, анализатор — `flutter analyze` без предупреждений. Перед PR:

  ```bash
  cd app
  dart format lib test
  flutter analyze
  ```

- Строки — в одинарных кавычках. После последнего аргумента в многострочном вызове — запятая: так форматтер раскладывает аргументы по строкам.

### Структура

Код разделён на слои Clean Architecture:

| Папка               | Что содержит                                                    | Может импортировать |
| ------------------- | --------------------------------------------------------------- | ------------------- |
| `lib/domain/`       | Бизнес-логика без Flutter: Health Score, статистика, интерфейсы | только `domain`     |
| `lib/data/`         | Источники данных: BLE, SQLite, API Hub, ИИ-комментарии; модели  | `domain`, `data`    |
| `lib/presentation/` | Экраны и виджеты                                                | все слои            |

`domain` не импортирует `package:flutter` и `presentation`: так бизнес-логику можно проверять обычными юнит-тестами. Модели, с которыми работает `domain`, объявляются в `domain`.

### Именование

- Файлы — `snake_case.dart`; экран — `<что>_screen.dart` с классом `<Что>Screen`: `cable_passport_screen.dart` → `CablePassportScreen`.
- Типы — `PascalCase`, всё остальное, включая константы, — `lowerCamelCase`: `continuityOkThreshold`, а не `CONTINUITY_OK_THRESHOLD`.
- Интерфейс и реализации: `BleDataSource` → `BleRealDataSource`, `BleMockDataSource`. Mock-реализация лежит рядом с настоящей и называется `…Mock…`.
- Приватные члены — с `_`; всё, что не нужно другим файлам, делается приватным.

### Импорты

Файлы самого приложения импортируются через `package:app/…` — не относительными путями и не путями от корня (`'/data/…'`).

```dart
import 'dart:async';

import 'package:flutter/material.dart';

import 'package:app/data/test_models.dart';
```

Порядок групп — `dart:`, внешние пакеты, файлы приложения, через пустую строку.

### Документация и типы

- Doc-комментарии `///` на русском — у публичных классов и у методов, смысл которых не ясен из имени. Первая строка — короткое описание одним предложением.
- Данные между слоями передаются типизированными моделями, а не `Map<String, dynamic>`. Разбор JSON (BLE-пакеты, ответы API) — в одном месте, в модели или в источнике данных; дальше по коду идут поля модели.
- Модели неизменяемые: поля `final`, конструктор `const`, где это возможно.

### Ошибки

- Ошибки каждой области — иерархия от общего базового класса, по образцу `InsightException` → `InsightNetworkException`, `InsightAuthException`. Doc-комментарий подкласса говорит, когда она возникает и поможет ли повтор.
- Пользователь видит понятный текст на русском, а не `toString()` исключения. Ошибки API Hub различаются по полю `code`, а не по тексту ([ADR-023](docs/adr/023-hub-api-conventions.md)).
- Пустой `catch (_) {}` не допускается: ошибка либо обрабатывается, либо пробрасывается дальше.

### Асинхронность

- **Подписка отменяется.** Результат `stream.listen(…)` сохраняется в поле `StreamSubscription` и отменяется в `dispose()` экрана или класса, который подписался. Иначе после ухода с экрана обработчик продолжает вызываться и обращается к уничтоженному `State`.
- **После `await` в `State` проверяется `mounted`** — прежде чем вызывать `setState` или использовать `context`: за время ожидания пользователь мог уйти с экрана.

  ```dart
  final cables = await _dataManager.getAllCables();
  if (!mounted) return;
  setState(() => _cables = cables);
  ```

- **`Future` не теряется.** Асинхронный вызов либо ожидается через `await`, либо явно запускается без ожидания через `unawaited(…)` из `dart:async` — тогда видно, что это сделано намеренно. Иначе ошибка в таком `Future` пропадает незаметно.
- Ошибки асинхронного кода ловятся через `try`/`catch` вокруг `await`, а не через `.catchError` в цепочке; ошибки потока — обработчиком `onError` в `listen`.
- Долгий расчёт не выполняется в обработчике события интерфейса: его выносят в `Isolate.run`, чтобы экран не замирал.

### Логи

- Отладочный вывод — через `log()` из `dart:developer` с именем источника, а не через `print`: `log('connection result: $result', name: 'ble')`. Такие записи видны в DevTools и не засоряют вывод релизной сборки.
- Сообщения — на английском, как в Hub. В лог не пишутся ключи, токены и данные пользователя.
- Ошибка, о которой сообщили пользователю, тоже записывается в лог — с исключением и стеком: `log('insight failed', name: 'insight', error: e, stackTrace: st)`.

### Локальная БД

- Параметры запроса передаются только через `whereArgs` или `?` в `rawQuery`, не интерполяцией строки: `db.query('cables', where: 'id = ?', whereArgs: [id])`.
- Запросы к SQLite — только в слое `data`: экраны получают модели, а не строки таблиц (см. [S](#s--единственная-ответственность)).
- Схема меняется повышением `version` в `openDatabase` и шагом в `onUpgrade`. Изменения в `onCreate` до уже установленных приложений не доходят.
- Несколько связанных записей — в одной транзакции `db.transaction(…)`: например, сеанс теста и результаты каждого теста.

### Тексты интерфейса

Тексты — на русском, с той же типографикой, что в документации (см. [Типографика](#типографика)). Термины — как в [глоссарии](docs/spec/glossary.md): «Health Score», «паспорт кабеля», «CMRR», «АЧХ».

## TypeScript и Svelte — веб-интерфейс (`web/`)

Веб — SvelteKit в режиме SPA, собранная статика отдаётся сервером Hub ([ADR-015](docs/adr/015-hub-stack.md)). За основу взята [документация Svelte](https://svelte.dev/docs) и настройки проекта, созданного `sv create`: Svelte 5 в режиме рун, TypeScript в режиме `strict`.

### Форматирование и проверка типов

- Форматтер — Prettier с плагином `prettier-plugin-svelte`, настройки — в `web/.prettierrc`: отступ 2 пробела, одинарные кавычки, точка с запятой, длина строки 100. Prettier форматирует и `<style>`: по одному свойству CSS на строку.
- Проверка — `npm run check` (svelte-check) без ошибок и предупреждений. Предупреждения о доступности (a11y) не подавляются, а исправляются.

  ```bash
  cd web
  npm run format
  npm run check
  ```

### Структура

| Путь                  | Что содержит                                                                     |
| --------------------- | -------------------------------------------------------------------------------- |
| `src/routes/`         | Страницы и общий каркас (`+layout.svelte`): разметка, состояние экрана, действия |
| `src/lib/components/` | Компоненты, которые используются больше чем на одной странице                    |
| `src/lib/api/`        | Клиент API Hub и типы, сгенерированные из контракта                              |
| `src/lib/mocks/`      | Данные-заглушки, пока нет нужного эндпоинта                                      |
| `src/lib/*.svelte.ts` | Общее состояние на рунах                                                         |
| `src/lib/*.ts`        | Функции без разметки: форматирование дат, цвет по Health Score                   |
| `src/app.css`         | Глобальные стили и переменные CSS                                                |

- Страница не обращается к `fetch` и не содержит данных-заглушек и общих функций: они живут в `src/lib/`. Так замена заглушек на API меняет один модуль, а не каждую страницу.
- Компонент, который разросся больше чем на 200–250 строк или содержит повторяющуюся разметку, делится на компоненты.
- Идентификатор ресурса — в пути (`/teams/[teamId]/cables/[cableId]`), параметры запроса — только для фильтров, сортировки и номера страницы. Один и тот же идентификатор называется одинаково во всех маршрутах.
- Режим SPA задаётся `adapter-static` с `fallback: 'index.html'` и `export const ssr = false` в `src/routes/+layout.ts` ([ADR-015](docs/adr/015-hub-stack.md)).
- Игнорируемые файлы веба — в разделе «Frontend» корневого `.gitignore`, отдельный `.gitignore` в `web/` не заводится.

### Именование

- Компоненты — `PascalCase.svelte`: `CableCard.svelte`. Маршруты — по соглашениям SvelteKit: `+page.svelte`, `[cableId]`. Остальные модули — `kebab-case.ts`; модуль с рунами — с суффиксом `.svelte.ts`, его требует Svelte.
- Переменные, функции и константы — `camelCase`, как в Dart: `healthScoreOkMin`, а не `HEALTH_SCORE_OK_MIN`. Типы — `PascalCase`. Параметры маршрута — `camelCase`: `[measureId]`.
- Булевы — с `is`/`has`: `isEditing`, `isTelegramLinked`.
- Классы CSS — `kebab-case`: `cable-card`, `nav-item`.
- Ключи `localStorage` — с префиксом `himo_`: `himo_profile`.

### Импорты

Модули из `src/lib` импортируются через алиас `#lib/…` из `package.json`, а не относительными путями (`../../lib/…`):

```ts
import { page } from '$app/state';

import type { Cable } from '#lib/api/types';
import CableCard from '#lib/components/CableCard.svelte';
```

Порядок групп — модули SvelteKit (`$app/…`) и внешние пакеты, затем `#lib/…`, затем стили, через пустую строку. Типы импортируются через `import type`.

### Типы

- `any` не используется. Если тип заранее неизвестен — `unknown` с проверкой. Состояние на рунах типизируется явно: `$state<Team[]>([])`.
- Типы данных API не пишутся вручную: их генерирует `openapi-typescript` из `contracts/openapi.yaml` ([ADR-015](docs/adr/015-hub-stack.md)). Сгенерированный файл не правится, он пересоздаётся скриптом после изменения контракта. Вручную описываются только типы состояния интерфейса.
- Данные из `JSON.parse` и `localStorage` получают тип в месте чтения, разбор — в `try`/`catch`: испорченное значение не должно ломать запуск страницы.
- Даты хранятся как `Date` или строки RFC 3339, как в API ([ADR-023](docs/adr/023-hub-api-conventions.md)). В текст для пользователя они превращаются только при выводе — через `toLocaleDateString('ru-RU')` или общую функцию из `src/lib/`.

### Компоненты

- Только руны: `$state`, `$derived`, `$props`, `$effect`. Режим рун включён для всего проекта в `vite.config.ts`. `export let`, `$:` и хранилища `writable` не используются.
- Порядок блоков в файле — `<script lang="ts">`, разметка, `<style>`.
- Вычисляемое значение — `$derived`, а не `$effect`, который записывает в `$state`. `$effect` — только для побочных действий: запись в `localStorage`, подписки.
- Фильтрация и сортировка списка — в `$derived` в `<script>`, а не цепочкой `.filter().sort()` внутри `{#each}`: разметка остаётся читаемой, а логику видно в одном месте.
- У `{#each}` по изменяемому списку — ключ: `{#each cables as cable (cable.id)}`.
- Обработчики — атрибутами `onclick={…}`, как требует Svelte 5, а не директивой `on:click`.
- Компонент получает через `$props` только то, что показывает: карточка кабеля — кабель, а не всю команду (см. [I](#i--разделение-интерфейсов)).
- Ссылка `<a>` — для перехода, `<button>` — для действия. У кнопки с одной иконкой — `aria-label`, у картинки — `alt`.

### Стили

- Стили компонента — в его `<style>`, они действуют только внутри компонента. Глобальные стили — только в `src/app.css`.
- Цвета и повторяющиеся размеры — переменные CSS в `:root` файла `app.css` (`--color-accent: #ff7a00;`), в компонентах — `var(--color-accent)`, а не повтор значения.
- Пороги цветовых зон Health Score — те же, что в приложении, они объявляются в `src/lib/health-score.ts` (см. [Константы](#константы-и-магические-значения)).

### Запросы к API Hub

- Запросы — через один модуль клиента в `src/lib/api/`, адреса относительные: `/api/v1/…`. Веб и API на одном домене, в разработке запросы проксирует Vite ([ADR-015](docs/adr/015-hub-stack.md)).
- Токен сеанса — в cookie `HttpOnly`, его ставит сервер. Веб не хранит токен в `localStorage` и не передаёт его в заголовке ([ADR-022](docs/adr/022-hub-authentication.md)).
- Ошибки API различаются по полю `code` ответа RFC 9457 ([ADR-023](docs/adr/023-hub-api-conventions.md)). Пользователь видит понятный текст на русском, а не `detail` или статус HTTP как есть. Ответ `401` ведёт на страницу входа.
- Данные-заглушки повторяют форму типов из контракта: при переходе на API меняется источник данных, а не страницы.

### Состояние

- Общее состояние — в модулях `src/lib/*.svelte.ts` на `$state`, как `store.svelte.ts`. Локальное состояние страницы — в самой странице.
- В `localStorage` хранятся только настройки интерфейса — например, выбранная сортировка, — а не данные с сервера и не токены. Данные команд и кабелей приходят из API.

### Ошибки и логи

- `console.log` в PR не попадает (см. [Комментарии](#комментарии)). Неожиданная ошибка пишется через `console.error` с объектом ошибки, сообщение — на английском, как в остальных компонентах.
- Пустой `catch {}` не допускается: ошибка либо показывается пользователю, либо пробрасывается дальше.
- Ошибка загрузки страницы показывается страницей `+error.svelte`, а не пустым экраном.

### Тексты интерфейса

Правила те же, что в приложении (см. [Тексты интерфейса](#тексты-интерфейса)): русский язык, типографика документации — кавычки «ёлочки», термины из [глоссария](docs/spec/glossary.md). Язык страницы — `<html lang="ru">` в `src/app.html`.

## C++ — прошивка (`firmware/`, заморожено)

Реализация прибора отложена ([ADR-013](docs/adr/013-device-postponed.md)), правила — на случай возобновления:

- отступ — 4 пробела, фигурная скобка — на той же строке;
- константы — `static constexpr` в `UPPER_SNAKE_CASE`: `LED_PIN`; функции и переменные — `camelCase`, типы — `PascalCase`;
- `#include` — сначала системные и библиотечные в `<>`, затем свои в `""`;
- формат пакетов и имена полей — только по [BLE-протоколу](docs/spec/device/ble-protocol.md).

## Конфигурация, CI и скрипты

### YAML

- Отступ — 2 пробела, без табуляции; синтаксис проверяет pre-commit (`check-yaml`).
- Расширение — `.yaml`.
- В начале файла — комментарий о назначении файла и ссылка на ADR, если он есть. В workflow Gitea Actions имена шагов (`name:`) — на русском: они видны в интерфейсе.

### Shell-скрипты

- Первая строка — `#!/usr/bin/env bash`, сразу после шапки — `set -euo pipefail`.
- Под первой строкой — комментарий: что делает скрипт и как его вызвать (`# Использование: deploy/deploy.sh <dev|prod> <тег образа>`).
- Переменные в кавычках: `"$HIMO_ENV"`. Сообщения об ошибках — в `stderr` (`>&2`) с ненулевым кодом выхода.

### Dockerfile

- Многоэтапная сборка, финальный образ — не от root ([ADR-015](docs/adr/015-hub-stack.md)).
- Слой зависимостей (`go.mod`, `go.sum`) копируется отдельно от исходников, чтобы не пересобираться при каждом изменении кода.
- Каждый неочевидный шаг сопровождается комментарием.

### Структура документа

- Заголовок первого уровня — один, в начале файла. Под ним — строка версии для спецификаций и правил: `Версия 0.4 · Октябрь 2026`.

### Оформление

- Таблицы выравниваются по колонкам — это делает форматтер Markdown (например, Prettier в VS Code), вручную выравнивать не нужно.
- Код, имена файлов, команды, поля и значения — в `обратных кавычках`. Блоки кода — с указанием языка: ` ```bash `, ` ```go `.
- Ссылки на другие документы репозитория — относительные: `[ADR-015](../adr/015-hub-stack.md)`. Требования упоминаются кодом: `HUB-7`, `APP-3`, `DVC-2`.
- Списки: пункт, продолжающий фразу перед списком, — со строчной буквы с `;` в конце, последний — с точкой; самостоятельные предложения — с заглавной и с точкой.

## Существующий код

Стайлгайд записан после того, как значительная часть кода уже написана, поэтому код не везде ему соответствует. Порядок такой:

- **Новый код** пишется по стайлгайду.
- **Изменяемый код.** Если задача и так переписывает функцию или файл, их можно привести к стайлгайду в той же ветке — отдельным коммитом `refactor`, по правилу исключения из [попутных исправлений](CONTRIBUTING.md#попутные-исправления).
