# Правила работы с репозиторием

Версия 1.1 · Октябрь 2026

Этот документ описывает, как устроен репозиторий проекта **Himo** и как вносить в него изменения: ветки, коммиты, Pull Request, ревью, проверки и тесты.
Цель — чтобы история проекта была читаемой, а каждый участник понимал, где что лежит и как оформить изменение.

---

## Структура репозитория

```
himodameshi/
├── .gitea/                    # Шаблон PR, CODEOWNERS
├── app/                       # Мобильное приложение (Flutter)
├── contracts/                 # Контракт API Himo Hub (OpenAPI)
├── firmware/                  # Прошивка ESP32-S3 — заморожено
├── hardware/                  # Схемы, BOM, даташиты — заморожено
├── docs/                      # Документация
│   ├── spec/                  # Спецификации, ФТТ
│   ├── adr/                   # Архитектурные решения
│   └── assets/                # Диаграммы и прочее
├── .gitignore
├── .pre-commit-config.yaml    # Проверки перед коммитом
├── CONTRIBUTING.md
└── README.md
```

Каждая папка верхнего уровня — это отдельный технологический стек. Внутренняя структура каждой папки остаётся на усмотрение ответственного за неё. Единственное жёсткое правило — не смешивать стеки между папками.

`firmware/` и `hardware/` заморожены: реализация прибора отложена, файлы остаются в репозитории как проработанный замысел.

## Начало работы

### Подпись коммитов

Перед первым коммитом настройте имя и почту — **те же, что в вашей учётной записи Gitea**:

```bash
git config --global user.name "Ваш ник"
git config --global user.email "почта@из.gitea"
```

Gitea связывает коммит с учётной записью по почте. Если почта не совпадает, коммит отображается как чужой или безымянный, и ваш вклад не виден ни в истории, ни в статистике репозитория — а по ней оценивается вклад каждого участника (в том числе в оценке 360°). Проверить текущие значения: `git config user.name` и `git config user.email`.

### Проверки перед коммитом (pre-commit)

[pre-commit](https://pre-commit.com) — менеджер git-хуков. Перед каждым `git commit` он запускает проверки из `.pre-commit-config.yaml` и останавливает коммит, если проверка не прошла.

| Проверка                                         | Что делает                                                                                                                                                                                                          |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [gitleaks](https://github.com/gitleaks/gitleaks) | Ищет в изменениях секреты: ключи API, токены, пароли. Секрет, попавший в историю, остаётся в ней навсегда — даже если удалить его следующим коммитом, он доступен в старых коммитах и у всех, кто сделал `git pull` |
| `check-yaml`                                     | Проверяет синтаксис YAML-файлов. Ошибка в отступах иначе обнаружится только после пуша                                                                                                                              |

**Установка** — один раз на машину (нужен Python 3):

```bash
pip install pre-commit
```

И один раз в каждом клоне репозитория, из его корня:

```bash
pre-commit install
```

Если команда `pre-commit` не находится (на Windows каталог `Scripts` после `pip install --user` не всегда попадает в PATH), запускайте через Python: `python -m pre_commit install`.

**Первый коммит** после установки займёт несколько минут: pre-commit скачает Go в свой кэш и соберёт gitleaks. Устанавливать Go или gitleaks вручную не нужно. Дальше проверки занимают доли секунды.

**Если коммит заблокирован.** gitleaks показывает файл, строку и тип найденного секрета (само значение скрыто):

- настоящий секрет — уберите его из файла и перенесите в файл, который не попадает в git (`.env`, `app/config/dev.json`), затем снова добавьте файл в индекс;
- ложное срабатывание — допишите в эту строку комментарий `gitleaks:allow`.

Не обходите проверку через `git commit --no-verify`.

## Ветки

Репозиторий — [git.hakoniwa.ru/tech/himodameshi](https://git.hakoniwa.ru/tech/himodameshi): здесь ведётся разработка, Pull Request и ревью.

| Ветка       | Назначение                                                                                                                                                                        |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `master`    | Слитый и проверенный код; компоненты выпускаются тегами на его коммитах (см. [Релизы](#релизы-теги-компонентов)). Появится с первым релизом. Изменения — только слиянием из `dev` |
| `dev`       | Ветка по умолчанию и интеграционная. Сюда сливаются задачи после ревью                                                                                                            |
| `task/YG-N` | Ветка под конкретную задачу. Стартует от `dev`                                                                                                                                    |

`dev` защищена:

- прямой push запрещён — изменения попадают только через Pull Request;
- для слияния нужно одобрение (approval) хотя бы одного ревьюера;
- новые коммиты в ветке задачи сбрасывают ранее полученные одобрения;
- слить можно только ветку, в которой есть все коммиты текущего `dev`.

### Коды задач

| Код    | Откуда                                                                                                                      |
| ------ | --------------------------------------------------------------------------------------------------------------------------- |
| `YG-N` | Задача в YouGile — текущий трекер. Используется в именах веток и заголовках PR                                              |
| `VK-N` | Архив Vikunja, прежнего трекера. Встречается только в старых коммитах (там же бывший формат `Himo-N` переименован в `VK-N`) |

YouGile подключён к репозиторию как внешний трекер задач: код `YG-N` в сообщениях коммитов, заголовках и описаниях PR и комментариях Gitea показывает ссылкой на задачу. Код распознаётся, если перед ним пробел, начало строки или скобка, — поэтому в заголовке PR он пишется как `[YG-N]`. Встроенные issues Gitea при этом отключены: задачи и баги заводятся в YouGile.

Ссылки вида `(tech/himodameshi-legacy#N)` в старых сообщениях коммитов ведут на Pull Request архивного репозитория.

## Жизненный цикл задачи

### Начало задачи

Обновить `dev` и создать от него ветку задачи:

```bash
git switch dev
git pull origin dev
git switch -c task/YG-12
```

Перевести задачу в YouGile в работу.

### В процессе работы

Коммитить по мере готовности отдельных частей — каждый коммит описывает одно законченное изменение (формат — в разделе [Коммиты](#коммиты)):

```bash
git add app/lib/screens/cable_detail.dart
git commit -m "feat(app): добавлен экран паспорта кабеля"
```

Публиковать ветку можно в любой момент — это ещё не сдача задачи:

```bash
git push -u origin task/YG-12
```

### Сдача задачи

1. Запушить последние коммиты.
2. В Gitea создать **Pull Request** `task/YG-12` → `dev`. Описание заполняется по шаблону: что сделано, как проверено, ссылки на задачу и ADR, чек-лист.
3. **Заголовок PR** — это будущее сообщение коммита в `dev`. Формат тот же, что у коммита, код задачи в конце:

   ```
   feat(app): добавлен экран паспорта кабеля [YG-12]
   ```

4. Ревьюер назначается автоматически по `.gitea/CODEOWNERS`. Ревью — в разделе [Code review](#code-review).
5. Если `dev` ушёл вперёд, нажать в PR кнопку **«Обновить ветку»** и выбрать обновление слиянием (не rebase — он переписывает уже запушенные коммиты). Если кнопка недоступна из-за конфликтов — см. [Разрешение конфликтов](#разрешение-конфликтов).
6. После одобрения PM сливает PR в `dev`.

### После слияния

Синхронизировать локальный `dev`:

```bash
git switch dev
git pull origin dev
```

Ветка `task/YG-12` остаётся в репозитории — по ней видно, кто и когда работал над задачей.

## Коммиты

Используется формат **Conventional Commits** с описанием на русском языке.

### Формат

```
<тип>(<scope>): <описание>
```

- **Тип** — категория изменения (см. таблицу ниже), на английском.
- **Scope** — папка верхнего уровня, которую затрагивает коммит.
- **Описание** — краткое, на русском, с маленькой буквы, без точки в конце.

Код задачи `[YG-N]` в коммитах ветки не обязателен — он ставится в заголовке PR и попадает в `dev` вместе с ним.

### Типы коммитов

| Тип        | Когда использовать                    | Пример                                                |
| ---------- | ------------------------------------- | ----------------------------------------------------- |
| `feat`     | Новая функциональность                | добавлен экран подключения по BLE                     |
| `fix`      | Исправление бага                      | исправлен расчёт порога CMRR                          |
| `refactor` | Рефакторинг без изменения поведения   | HealthScore вынесен в отдельный сервис                |
| `test`     | Добавление или правка тестов          | юнит-тесты расчёта Health Score                       |
| `docs`     | Документация и ADR                    | ФТТ обновлены до версии 0.6 (`spec`), ADR-013 (`adr`) |
| `chore`    | Зависимости, конфиги, служебные файлы | обновлён flutter_blue_plus до 1.31                    |
| `merge`    | Только слияние `dev` → `master`       | релиз hub/v0.1.0                                      |

Незавершённую работу не коммитят как отдельный тип: коммит фиксирует законченную часть задачи, даже небольшую.

### Допустимые значения scope

Scope строго соответствует папке верхнего уровня — за исключением `docs`, где scope уточняет подпапку, чтобы было понятно, что именно изменилось:

| Коммит         | Папка             | Когда использовать                                          |
| -------------- | ----------------- | ----------------------------------------------------------- |
| `…(app)`       | `app/`            | любые изменения в приложении                                |
| `…(contracts)` | `contracts/`      | контракт API (`openapi.yaml`)                               |
| `…(firmware)`  | `firmware/`       | любые изменения в прошивке                                  |
| `…(hardware)`  | `hardware/`       | схемы, BOM, даташиты                                        |
| `docs(spec)`   | `docs/spec/`      | ФТТ, архитектурные описания                                 |
| `docs(adr)`    | `docs/adr/`       | Architecture Decision Records                               |
| `docs(assets)` | `docs/assets/`    | картинки, диаграммы                                         |
| без scope      | корень, `.gitea/` | `README.md`, `CONTRIBUTING.md`, `.gitignore`, шаблоны Gitea |

Если изменение затрагивает сразу несколько папок — укажи их через `/`:

```
chore(app/firmware): обновлены интерфейсы BLE-пакетов
```

### Соавторство LLM

Если LLM (ChatGPT, Claude, GLM, Copilot в режиме чата и т. п.) написала или существенно переработала содержимое коммита — код, текст, конфигурацию, — она указывается соавтором. Вопросы к чату без переноса ответа в коммит и однострочное автодополнение не в счёт.

Соавтором указывается тот, кто внёс изменения, а не тот, кто оформил коммит. Если изменения внёс человек, а LLM только сформулировала сообщение коммита или выполнила сам коммит, трейлер не ставится.

Соавтор указывается трейлером в последнем абзаце сообщения коммита — название модели **с точной версией**:

```
docs(spec): архитектура дополнена компонентом Himo Hub

Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
```

Если у вендора нет служебного noreply-адреса, укажите только название модели. Если работали несколько моделей или разные версии одной модели — каждая отдельной строкой.

### Примеры

#### Хорошие коммиты ✅

```
feat(app): добавлен экран подключения по BLE
```

```
feat(firmware): GATT-сервер, отправка JSON-пакетов по BLE
```

```
fix(app): исправлен порог CMRR при сравнении с нормой
```

```
fix(firmware): корректный расчёт сопротивления на pin3 XLR
```

```
refactor(firmware): HAL-модули выделены в отдельную директорию
```

```
test(app): юнит-тесты расчёта Health Score для всех сценариев
```

```
docs(spec): ФТТ обновлены до версии 0.6
```

```
docs(adr): ADR-002 — выбор INA128P вместо INA217
```

```
chore(hardware): добавлен даташит MCP3208
```

```
chore(app): обновлён flutter_blue_plus до 1.31
```

#### Плохие коммиты ❌ и как их исправить

| Плохой коммит                                                      | Проблема                                         | Исправленный вариант                                    |
| ------------------------------------------------------------------ | ------------------------------------------------ | ------------------------------------------------------- |
| `fix`                                                              | Нет scope и описания — непонятно вообще ничего   | `fix(firmware): исправлен расчёт сопротивления на pin2` |
| `изменения`                                                        | Нет типа, нет scope, описание бессмысленно       | `refactor(app): упрощён парсинг BLE-пакетов`            |
| `feat(app): Added BLE screen`                                      | Описание на английском при русском соглашении    | `feat(app): добавлен экран подключения по BLE`          |
| `feat(app): Добавил экран BLE, поправил баги, обновил зависимости` | Один коммит на три несвязанных изменения         | Три отдельных коммита: `feat`, `fix`, `chore`           |
| `feat: всё`                                                        | Нет scope, описание бессмысленно                 | Разбить на конкретные коммиты по папкам                 |
| `WIP`                                                              | Незавершённое состояние вместо законченной части | `feat(app): добавлена секция истории тестов в паспорте` |

## Слияния

### `task/YG-N` → `dev`: squash

Все коммиты ветки задачи объединяются в один коммит в `dev`. История `dev` остаётся линейной: один коммит — одна задача. Подробная история работы сохраняется в ветке задачи и в PR.

Сообщение squash-коммита:

- **первая строка** — заголовок PR: `feat(app): добавлен экран паспорта кабеля [YG-12]`;
- **тело** — по желанию, краткий список изменений;
- **последний абзац** — все трейлеры `Co-Authored-By` из коммитов ветки, без повторов. Если LLM участвовала хотя бы в одном коммите и её изменения остались в итоговом diff, она соавтор итогового коммита.

Gitea при squash подставляет в тело тексты всех коммитов ветки — трейлеры оказываются в середине и перестают распознаваться. Перед слиянием сообщение нужно отредактировать.

### `dev` → `master`: merge commit

Релиз — Pull Request `dev` → `master`, слияние обычным merge commit. Сообщение называет выпускаемые компоненты с версиями и суть вошедших изменений:

```
merge(dev): релиз hub/v0.1.0 — каркас Himo Hub
```

### Итого

| Откуда      | Куда     | Когда сливаем          | Стратегия    | Пример сообщения                                    |
| ----------- | -------- | ---------------------- | ------------ | --------------------------------------------------- |
| `task/YG-N` | `dev`    | PR одобрен, PM сливает | squash       | `feat(app): добавлен экран паспорта кабеля [YG-12]` |
| `dev`       | `master` | Релиз                  | merge commit | `merge(dev): релиз hub/v0.1.0 — каркас Himo Hub`    |

### Релизы: теги компонентов

Компоненты выпускаются независимо, у каждого своя версия. Слияние в `master` само по себе ничего не выпускает: компонент выпускается **тегом** на коммите `master`.

```
<компонент>/vX.Y.Z
```

Например: `hub/v0.1.0`, `app/v0.4.0`. Версия — по [SemVer](https://semver.org/lang/ru/): X — несовместимые изменения, Y — новая функциональность, Z — исправления.

Тег ставит PM после слияния в `master`, тег аннотированный:

```bash
git tag -a hub/v0.1.0 -m "hub/v0.1.0 — каркас Himo Hub"
git push origin hub/v0.1.0
```

Тег — сигнал для выпуска: по нему собирается и разворачивается компонент. Сборка и развёртывание по тегам настраиваются вместе с CI/CD.

Если в одном слиянии выпускаются несколько компонентов, на коммит ставятся несколько тегов, а в сообщении слияния перечисляются все: `merge(dev): релиз hub/v0.2.0, app/v0.4.0`.

## Code review

Каждый PR в `dev` проходит ревью: без одобрения хотя бы одного участника слияние невозможно.

### Что проверяет ревьюер

- **Задача.** PR делает то, что написано в задаче YouGile, — и ничего постороннего.
- **Заголовок.** Формат Conventional Commits, код задачи `[YG-N]` в конце.
- **Проверка.** Раздел «Как проверено» заполнен; тесты проходят.
- **Чистота.** Нет секретов, сгенерированных файлов, отладочного вывода, закомментированного кода.
- **Документация.** Если изменилось поведение, интерфейс или требования — обновлены документы в `docs/`; если решение архитектурное — есть ADR.
- **Код.** Понятен без пояснений автора, написан в стиле окружающего кода.

### Как оставлять замечания

| Решение             | Когда                                             |
| ------------------- | ------------------------------------------------- |
| **Approve**         | Замечаний нет или остались только необязательные  |
| **Comment**         | Вопросы и пожелания, которые не блокируют слияние |
| **Request changes** | Есть то, что нужно исправить до слияния           |

Замечание формулируется так, чтобы автор мог исправить его без дополнительных вопросов: **что не так, почему это проблема и что предлагается**. Комментарий оставляется к конкретной строке. Необязательные пожелания помечаются словом «Необязательно:» — так автор видит, что блокирует слияние, а что нет.

```
❌  Не так.
✅  Порог 40 дБ захардкожен здесь и в health_score.dart — при изменении ФТТ
    поправят только одно место. Предлагаю вынести в общую константу.
```

### Как исправлять замечания

- Замечания исправляются **новыми коммитами в ту же ветку**. Не переписывайте уже запушенные коммиты (`--amend`, rebase, force push): ревьюер должен видеть, что изменилось с прошлого раза. При squash промежуточные коммиты всё равно не попадут в `dev`.
- На каждое замечание отвечайте в обсуждении: что исправлено или почему вы не согласны.
- Обсуждение отмечает решённым тот, кто его открыл.
- Новые коммиты сбрасывают одобрение — после исправлений запросите ревью повторно.

## Разрешение конфликтов

Конфликт возникает, если одни и те же строки менялись и в `dev`, и в ветке задачи. Тогда кнопка «Обновить ветку» в PR недоступна, и ветку нужно обновить локально:

```bash
git switch task/YG-12
git fetch origin
git merge origin/dev
```

Git сообщит о конфликте:

```
CONFLICT (content): Merge conflict in app/lib/main.dart
Automatic merge failed; fix conflicts and then commit the result.
```

**1. Посмотреть список конфликтных файлов**

```bash
git status
```

**2. Открыть файл и разрешить конфликт**

Git помечает конфликтную зону тремя маркерами, каждый на отдельной строке:

- `<<<<<<< HEAD` — начало версии из ветки задачи;
- `=======` — граница между версиями;
- `>>>>>>> origin/dev` — конец версии из `dev`.

Оставить нужный вариант (или объединить оба), убрать все три маркера.

В VS Code конфликты выделяются визуально — доступны кнопки:

- **Accept Current Change** — взять версию ветки задачи
- **Accept Incoming Change** — взять версию `dev`
- **Accept Both Changes** — вставить оба варианта подряд

**3. Отметить файл как разрешённый, завершить слияние и запушить**

```bash
git add app/lib/main.dart
git commit -m "merge: ветка синхронизирована с dev"
git push
```

**Отменить слияние** (если нужно разобраться, прежде чем разрешать конфликт):

```bash
git merge --abort           # возвращает всё к состоянию до git merge
```

## Architecture Decision Records (ADR)

Папка `docs/adr/` предназначена для фиксации **архитектурных решений** — не что было сделано, а почему именно так. ADR пишется, когда решение выбирает между реальными альтернативами, меняет интерфейс между частями системы или сужает объём работ.

Когда нужен ADR, как его оформить, нумерация, статусы и индекс — **[docs/adr/README.md](docs/adr/README.md)**. Шаблон — **[docs/adr/template.md](docs/adr/template.md)**.

## Вопросы и обсуждения

- **По задаче** — в чате задачи в YouGile: обсуждение остаётся рядом с задачей и видно всем, кто её открывает.
- **По конкретному коду в PR** — комментарием к строке в Pull Request.
- **Баг, найденный вне задачи** — новая задача в YouGile. В описании — как воспроизвести, что ожидалось и что произошло. Исправление идёт обычным порядком: ветка `task/YG-N`, PR с кодом задачи в заголовке.
