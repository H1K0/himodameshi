# ADR-024: Хотфиксы — ветка hotfix/YG-N от master с переносом в dev через merge commit

## Контекст

По [ADR-014](014-repository-and-branching.md) в `master` код попадает только слиянием из `dev`, а Git Flow с ветками `hotfix/*` был отвергнут как избыточный. Значит, исправить выпущенную версию можно только через `dev` и следующий выпуск `dev` → `master`.

Выпуск переносит в `master` всё, что накопилось в `dev`, — по всем компонентам сразу. Если в `dev` есть изменения, которые выпускать ещё рано (не проверены на dev-окружении, другой компонент не готов к выпуску), срочное исправление prod приходится либо отложить, либо выпустить вместе с лишним. Prod Hub обновляется по тегу на `master` ([ADR-017](017-deployment.md)), так что ошибка в выпущенной версии остаётся на prod до следующего выпуска.

Критерии курса (DoD): изменения в `master` — только через Pull Request, у каждого PR не меньше одного одобрения, слияние блокируется красным пайплайном, стратегия ветвления — одна из признанных (GitFlow, GitHub Flow, Trunk-Based).

## Решение

**Хотфикс** — срочное исправление выпущенной версии компонента, которое не может ждать следующего выпуска. Он делается в ветке `hotfix/YG-N` от `master`:

1. Ветка `hotfix/YG-N` создаётся от `master`.
2. PR `hotfix/YG-N` → `master` с теми же требованиями, что и PR в `dev`: одобрение, зелёный пайплайн. Слияние — squash, заголовок — `fix(<scope>): <описание> [YG-N]`.
3. Выпуск — тег компонента с увеличенной версией исправлений Z: `hub/v0.1.0` → `hub/v0.1.1`.
4. Перенос в `dev`: в ту же ветку вливаются `master`, затем `dev`, и она сливается в `dev` PR'ом через **merge commit**, не squash.

Merge commit на шаге 4 нужен, чтобы коммит хотфикса из `master` стал предком `dev`. После squash в `dev` было бы только такое же изменение в другом коммите. Тогда, если эти строки успеют поменяться в `dev`, следующий выпуск `dev` → `master` даст конфликт: для git это две разные правки одних и тех же строк.

Остальные исправления идут обычными задачами через `dev`. Пока `master` нет, хотфиксов тоже нет.

Остальное решение [ADR-014](014-repository-and-branching.md) остаётся в силе.

## Рассмотренные варианты

- **Ничего не менять: исправление через `dev` и внеочередной выпуск** — схема веток прежняя. Но в выпуск попадает всё из `dev`; если там есть то, что выпускать рано, хотфикс ждёт.
- **Исправление в `dev`, затем cherry-pick в ветку от `master`** — исправление сначала проверяется на dev-окружении. Но на prod оно попадает только после ревью и слияния в `dev`, а в двух ветках оказываются два разных коммита с одним изменением — с тем же конфликтом при следующем выпуске, что и при переносе squash'ем.
- **Ветка от `master`, перенос в `dev` squash'ем** — история `dev` остаётся линейной. Но коммит хотфикса не становится предком `dev`, и следующий выпуск может дать конфликт.
- **Ветка от `master`, перенос в `dev` через merge commit (выбран).**

## Обоснование

Критерии в порядке важности: требования курса > в prod попадает только то, что готово к выпуску > простота процесса для команды из четырёх человек.

- Все требования курса сохраняются: и хотфикс, и его перенос в `dev` проходят через PR с одобрением и пайплайном.
- Исправление prod не зависит от состояния `dev`: в выпуск попадает только оно.
- Процесс почти не отличается от обычной задачи: одна ветка на задачу, PR, squash. Новое — ветка стартует от `master` и сливается дважды, второй раз через merge commit.
- Схема совпадает с веткой hotfix в GitFlow (роль `develop` у `dev`, без веток `release/*`): стратегия остаётся узнаваемой.

## Последствия

**Плюсы:**

- Ошибку на prod можно исправить в любой момент, не выпуская незаконченное из `dev`.
- Следующий выпуск `dev` → `master` проходит без конфликтов из-за хотфикса.
- В `master` хотфикс — один коммит с кодом задачи, как задача в `dev`.

**Минусы и ограничения:**

- На хотфикс два PR и два ревью.
- История `dev` перестаёт быть строго линейной: после переноса хотфикса в ней появляются merge commit'ы, а через второго родителя — промежуточные коммиты ветки хотфикса (`git log --first-parent` их скрывает).
- Хотфикс проходит CI, но не живёт на dev-окружении до выпуска: dev-окружение разворачивается из `dev`, а исправление попадает туда только при переносе.
- Пока хотфикс не перенесён в `dev`, исправления нет ни в `dev`, ни на dev-окружении, а правка тех же строк в `dev` даст конфликт при выпуске. Перенос — обязательная часть задачи.

**Что нужно сделать:**

- CONTRIBUTING.md — ветка `hotfix/YG-N`, порядок хотфикса, тип `merge` для переноса в `dev`.
- При создании `master` — защита: только через PR, с одобрением и зелёным пайплайном.
- CI: проверки на PR в `master` — те же, что на PR в `dev` ([ADR-017](017-deployment.md) описывает только PR в `dev`).
