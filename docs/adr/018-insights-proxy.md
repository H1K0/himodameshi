## Контекст

К результатам тестов показываются ИИ-комментарии: языковая модель объясняет уже рассчитанные приложением вердикты и Health Score ([architecture.md, раздел 5](../spec/architecture.md#5-ии-комментарии)). Выбор модели и отказ от комментариев на правилах — предмет отдельного ADR об ИИ-комментариях (YG-46); здесь — только то, как комментарии проходят через Hub.

Сейчас приложение обращается к API модели напрямую, и ключ API находится в приложении — то есть фактически доступен любому, кто его извлечёт. Ключ нужно перенести на сервер. При этом действуют условия:

- комментарии должны быть доступны и тому, кто пользуется только приложением, без учётной записи Hub;
- комментарий нужен в двух местах: в приложении (сразу после теста) и на странице теста в вебе;
- запрос к модели стоит денег и занимает 1–3 секунды; ключ нужно защитить от расходования посторонними;
- модель отвечает недетерминированно: два запроса с одинаковыми данными дают разные тексты;
- тесты делаются и без связи и выгружаются в Hub позже ([hub/requirements.md](../spec/hub/requirements.md), HUB-7).

Первоначальный замысел: приложение получает анонимный токен устройства (`POST /api/v1/devices`), по нему запрашивает комментарий, сохраняет его вместе с тестом и отправляет в Hub при выгрузке; тесты без комментария Hub дополняет в фоне. Схема получилась запутанной: три пути появления комментария, возможные расхождения между ними, а токен, выдаваемый анонимно любому желающему, почти не защищает ключ.

## Решение

**Один эндпоинт `POST /api/v1/insights`:** на входе результаты теста, на выходе комментарий. Без учётной записи и без токена.

**Кэш по результатам.** Сервер приводит результаты к каноническому виду (фиксированный порядок полей, единый формат чисел) и считает ключ кэша — хеш от канонических результатов, версии промпта и модели. Если комментарий с таким ключом уже есть — возвращает его; если нет — запрашивает модель, сохраняет и возвращает. Кэш — таблица в PostgreSQL.

**Привязка к тесту.** Тест в Hub хранит ссылку на запись кэша:

- при выгрузке теста сервер считает ключ по его результатам и, если комментарий уже получен приложением, сразу привязывает его;
- если комментария ещё нет, он запрашивается при первом открытии теста в вебе и привязывается тогда;
- привязанный комментарий не меняется, в том числе при смене промпта или модели.

Одна запись кэша может быть привязана к нескольким тестам с одинаковыми результатами. Комментарий не входит в данные, которые приложение отправляет при выгрузке.

**Защита ключа:** ключ API — только в переменных окружения сервера; ограничение частоты запросов к `/insights` по IP; общий дневной лимит обращений к модели. При исчерпанном лимите комментарии временно недоступны, остальной сервис работает.

**Промпт** — в файле `hub/prompts/insight.ru.md`; его версия входит в ключ кэша.

## Рассмотренные варианты

- **Оставить вызов модели в приложении** — ничего не нужно делать на сервере. Но ключ остаётся внутри приложения.
- **Токен устройства, комментарий выгружается вместе с тестом, фоновое дополнение** (первоначальный замысел) — комментарий доступен офлайн сразу после получения. Но три пути появления комментария, расхождения между ними, лишний эндпоинт и хранение токенов; анонимный токен легко получить в любом количестве, так что защиту всё равно дают лимиты.
- **Комментарии только для пользователей Hub** — обычная аутентификация, никакой анонимности. Но пользователь без учётной записи остаётся без комментариев, что противоречит исходному решению.
- **Кэш в памяти процесса или в Redis** — проще таблицы или быстрее. Но кэш в памяти теряется при каждом перезапуске, а Redis — ещё один сервис ради одной таблицы.
- **Поле `test_id` в записи кэша вместо ссылки из теста** — связь в одном месте. Но одна запись кэша может принадлежать нескольким тестам, а поле вмещает только один.
- **Один эндпоинт, кэш по результатам, ссылка из теста (выбран).**

## Обоснование

Критерии в порядке важности: ключ API не покидает сервер > комментарии доступны без учётной записи > один и тот же текст в приложении и в вебе > простота.

Комментарий — функция от результатов теста, поэтому естественно адресовать его по результатам, а не по устройству или пользователю. Кэш по канонизированным результатам решает сразу две задачи: повторные запросы не тратят ключ, а приложение и веб, обратившись с одними и теми же результатами, получают один и тот же текст, несмотря на недетерминированность модели. Ссылка из теста фиксирует комментарий, который видел автор, и избавляет веб от повторной канонизации при каждом просмотре.

Отказ от токена устройства убирает целый механизм, почти не теряя в защите: токен выдаётся анонимно, а реальную защиту ключа и в первоначальной схеме давали бы лимиты. Если злоупотребления всё же начнутся, токен можно добавить позже, не меняя остальную схему.

## Последствия

**Плюсы:**

- Ключ API только на сервере.
- Один путь появления комментария вместо трёх; приложение и веб показывают одинаковый текст.
- Комментарий к тесту фиксируется и не меняется при смене промпта или модели.
- Повторные запросы не тратят ключ.
- Учётная запись для комментариев не нужна.

**Минусы и ограничения:**

- Ключ можно расходовать анонимно; дневной лимит ограничивает ущерб, но при исчерпании комментарии недоступны всем до конца дня.
- Многие абоненты мобильных операторов выходят в интернет через один IP — лимит по IP для них общий, поэтому он должен быть с запасом.
- Попаданий в кэш между разными тестами почти не будет: измерения у каждого теста свои. Кэш работает на повторных запросах одного и того же теста.
- Совпадение ключей у приложения и веба зависит от канонизации: если приложение пришлёт результаты не в том виде, в каком они хранятся в Hub, комментарий запросится заново.
- При первом открытии теста в вебе без привязанного комментария он появляется с задержкой в 1–3 секунды.
- Без связи приложение комментарий не получит; он появится, когда связь вернётся.
- Записи кэша, на которые больше не ссылается ни один тест (например, после удаления кабеля), остаются в таблице, пока их не удалит периодическая очистка.
