## Контекст

Весной проект жил в репозитории `tech/himodameshi-legacy` с трекером Vikunja: задачи сливались в `dev` merge commit'ами, в истории было много промежуточных коммитов. Осенью к приложению и прибору добавляется Himo Hub, и кодовых баз становится больше: мобильное приложение, сервер Hub, веб-интерфейс, контракты между ними (OpenAPI для Hub, приложения и веба; BLE-протокол для приложения и прибора), конфигурация развёртывания, документация.

Требования курса: публичный репозиторий, стратегия ветвления, изменения в основную ветку только через PR с одобрением, Conventional Commits, CI на каждый PR, окружения dev и prod. Задачи команда ведёт в YouGile, работает по Scrum. Сервер для CI и развёртывания — домашний (развёртывание описывается отдельным ADR).

Нужно решить, как разложить код по репозиториям, где их хостить, как ветвиться, сливать и выпускать компоненты.

## Решение

**Один репозиторий** — [git.hakoniwa.ru/tech/himodameshi](https://git.hakoniwa.ru/tech/himodameshi), публичный. Каталоги верхнего уровня по стекам: `app/`, `hub/`, `web/`, `contracts/`, `deploy/`, `docs/`, `firmware/`, `hardware/`. Каталог появляется вместе с первым кодом, а не заранее.

**Хостинг — Gitea** на своём сервере, CI — Gitea Actions. Резервное зеркало на GitHub (только для чтения) может быть добавлено позже отдельной задачей.

**Ветки:**

- `dev` — по умолчанию и интеграционная. Защищена: только через PR, одобрение хотя бы одного ревьюера и владельца кода (CODEOWNERS), сброс одобрений при новых коммитах, слияние только актуальной ветки.
- `task/YG-N` — по ветке на задачу, от `dev`.
- `master` — слитый и проверенный код, только слиянием из `dev`.

**Слияния:** задача → `dev` — squash, один коммит на задачу; `dev` → `master` — merge commit.

**Релизы — теги компонентов.** Компоненты выпускаются независимо, у каждого своя версия по SemVer. Выпуск — аннотированный тег `<компонент>/vX.Y.Z` на коммите `master` (`hub/v0.1.0`, `app/v0.4.0`). Слияние в `master` само по себе ничего не выпускает; сборка и развёртывание запускаются тегом. Контракты тегами не версионируются: у OpenAPI есть `info.version` и версия в пути `/api/v1`, у BLE-протокола — `pv`.

**Коды задач:** `YG-N` — YouGile, YouGile подключён к Gitea как внешний трекер (коды в коммитах и PR становятся ссылками). `VK-N` — архивные коды Vikunja в старых коммитах; ссылки `(tech/himodameshi-legacy#N)` ведут на PR архивного репозитория, он закрыт и доступен только участникам команды.

Правила для участников — в [CONTRIBUTING.md](../../CONTRIBUTING.md).

## Рассмотренные варианты

Структура:

- **Отдельный репозиторий на компонент** (приложение, Hub, веб, контракты) — независимые права и CI. Но изменение контракта растягивается на 3–4 PR в разных репозиториях, версии клиентов расходятся, документация и ADR живут неизвестно где.
- **Монорепозиторий (выбран).**

Хостинг:

- **GitHub основным** — привычный, огромная экосистема Actions. Но риск блокировок и ограничений из-за санкций, а облачному CI нужен доступ к домашнему серверу для развёртывания.
- **GitLab на своём сервере** — мощный встроенный CI. Но тяжёлый для домашнего железа: несколько гигабайт памяти только на сам GitLab.
- **Gitea на своём сервере (выбран)** — лёгкий, Actions совместимы с GitHub Actions, runner работает рядом с сервером развёртывания.

Ветвление:

- **GitHub Flow** (одна `main` и ветки задач) — проще всего, но нет отдельной ветки под dev-окружение.
- **Git Flow** (`develop`, `release/*`, `hotfix/*`) — избыточен для команды из четырёх человек и одного продукта на сервере.
- **Trunk-based** — требует feature flags и зрелого CI, которых пока нет.
- **`dev` / `master` / `task/YG-N` (выбран)** — две постоянные ветки под два окружения.

Слияние в `dev`:

- **Merge commit** — сохраняет структуру веток, но весной история `dev` превратилась в шум из промежуточных коммитов.
- **Rebase-merge** — линейная история, но в `dev` попадают все промежуточные коммиты.
- **Squash (выбран)** — один коммит на задачу; подробная история остаётся в ветке и PR.

Версии:

- **Одна версия на весь репозиторий** (`v0.1.0`) — проще, но приложение и Hub выпускаются в разном темпе: выпуск одного заставлял бы поднимать версию другого.
- **Теги компонентов (выбраны).**

## Обоснование

Критерии в порядке важности: требования курса > простота процесса для команды из четырёх человек > независимость инфраструктуры.

- **Монорепозиторий** главным образом ради контрактов: изменение `openapi.yaml`, сервера и обоих клиентов проходит одним PR и одним прогоном CI, рассинхронизация невозможна по построению. Для небольшой команды один набор правил, одно место для ADR и документации важнее изоляции.
- **Gitea** — единственный вариант, который одновременно работает на домашнем сервере без заметной нагрузки, не зависит от зарубежных сервисов и даёт CI, совместимый с GitHub Actions (готовые действия и документация в основном переносятся).
- **Две постоянные ветки** прямо соответствуют двум окружениям, которых требует курс: `dev` → dev, `master` → prod. Squash делает историю `dev` читаемой: один коммит — одна задача со ссылкой на YouGile.
- **Теги компонентов** разделяют «код готов» (слит в `master`) и «компонент выпущен» (поставлен тег). Формат со слэшем совпадает с соглашением Go для модулей в подкаталогах (`hub/vX.Y.Z`) и удобно фильтруется в CI (`hub/v*`).

## Последствия

**Плюсы:**

- Контракт и его потребители меняются атомарно.
- Одно место для кода, документации, ADR и CI.
- Линейная история `dev`, коды задач в ней — ссылки на YouGile.
- Компоненты выпускаются независимо, по готовности.

**Минусы и ограничения:**

- CI должен фильтровать запуски по путям, иначе каждый PR будет собирать Flutter, Go и Node.
- Репозиторий растёт за счёт всех стеков сразу; клонировать его приходится целиком.
- `master` общий: слияние переносит в него всё накопленное в `dev`. Поэтому в `dev` должно попадать только законченное — незавершённая работа по одному компоненту окажется в `master` вместе с выпуском другого.
- Gitea на домашнем сервере — единственная точка отказа для репозитория и CI, пока нет зеркала. Обслуживание (обновления, резервные копии) — на команде.
- После squash подробная история задачи доступна только в её ветке и PR, не в `dev`.
- Обсуждения весенних PR закрыты для внешних читателей: архивный репозиторий приватный.

**Что нужно сделать:**

- Настроить фильтры по путям в workflow Gitea Actions — вместе с CI/CD Hub.
- Настроить сборку и развёртывание по тегам `<компонент>/v*` — там же.
- Зеркало на GitHub — отдельная задача.
- `README.md` — структура репозитория и ссылка на CONTRIBUTING.
