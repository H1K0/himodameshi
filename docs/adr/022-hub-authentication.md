# ADR-022: Аутентификация в Hub — один непрозрачный токен сеанса, в вебе в cookie, в приложении в заголовке

## Контекст

У API Hub два клиента: веб-интерфейс (SvelteKit SPA на том же домене, что и API) и мобильное приложение ([ADR-015](015-hub-stack.md)). Вход — по нику и паролю, в вебе также через Telegram Login Widget ([ADR-016](016-telegram-login-widget.md)).

Что требуется ([hub/requirements.md](../spec/hub/requirements.md), HUB-1 и раздел 4):

- завершение всех сеансов по запросу пользователя (например, при утере телефона) и при смене пароля;
- пароли — адаптивный хеш с солью (Argon2id или bcrypt);
- ограничение частоты попыток входа, защита от XSS и CSRF;
- в версии 0.3 требований было записано: «сеансы приложения — токены доступа и обновления».

Модель данных уже содержит таблицу `auth_sessions` с хешем токена, клиентом (`web` / `app`), сроком действия и отметкой отзыва ([hub/data-model.md](../spec/hub/data-model.md), раздел 3.1). Формат токенов был оставлен этому решению.

Важное обстоятельство: требования обязывают проверять членство в команде при каждом обращении к её данным. То есть почти каждый запрос и так обращается к БД.

Сервер работает в одном экземпляре; объёмы — до 100 одновременных пользователей.

## Решение

**Один вид сеанса для обоих клиентов — непрозрачный токен.**

- Токен — 32 случайных байта из криптографического генератора, в виде base64url (43 символа). В `auth_sessions.token_hash` хранится его SHA-256; сам токен на сервере не хранится.
- На каждом запросе сервер считает SHA-256 от предъявленного токена и ищет действующий сеанс по уникальному индексу: `revoked_at IS NULL AND expires_at > now()`.
- Срок действия — 30 суток, **продлевается при использовании**. Чтобы чтение не превращалось в запись, `expires_at` обновляется, только если с прошлого продления прошло больше суток.
- Отзыв мгновенный: `revoked_at = now()`. Пользователь, завершивший сеансы, теряет доступ со следующего же запроса.

**Передача токена зависит от клиента, проверка — общая.**

- **Приложение** получает токен в теле ответа на вход и отправляет его в заголовке `Authorization: Bearer <токен>`. Хранит его в защищённом хранилище ОС (Android Keystore через `flutter_secure_storage`).
- **Веб** получает тот же токен в cookie и в теле ответа его не видит:
  `__Host-himo_session=<токен>; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=2592000`.
- Один middleware берёт токен из заголовка или из cookie и дальше работает одинаково. Клиент указывается при входе (`client: web | app`) и записывается в `auth_sessions.client`.

**CSRF.** Веб и API на одном домене, cookie `SameSite=Strict`. Но для браузера `dev.himo.hakoniwa.ru` и `git.hakoniwa.ru` — тот же сайт, что `himo.hakoniwa.ru`, поэтому `SameSite` сам по себе не защищает от страницы на соседнем поддомене. Дополнительно:

- для изменяющих запросов (`POST`, `PUT`, `PATCH`, `DELETE`) с аутентификацией по cookie сервер требует заголовок `Origin`, равный собственному адресу сервиса (переменная `PUBLIC_URL`); иначе — 403;
- префикс `__Host-` не даёт поддоменам установить или подменить cookie сеанса.

Запросы с `Authorization: Bearer` эта проверка не касается: браузер не подставляет такой заголовок сам.

**Пароли — Argon2id** (`golang.org/x/crypto/argon2`) с параметрами из рекомендаций OWASP: 19 МиБ памяти, 2 итерации, 1 поток, соль 16 байт. Параметры хранятся в строке хеша в формате PHC, поэтому их можно поднять позже, перехешируя пароль при следующем входе. Длина пароля — от 8 до 128 символов.

**Ник** — латинские буквы, цифры и `_`, от 3 до 32 символов; уникален без учёта регистра.

**Операции:**

| Операция                               | Что происходит с сеансами                                             |
| -------------------------------------- | --------------------------------------------------------------------- |
| Регистрация, вход, вход через Telegram | Создаётся новый сеанс                                                 |
| Выход                                  | Отзывается текущий сеанс, веб-cookie удаляется                        |
| Завершение всех сеансов                | Отзываются все сеансы пользователя, включая текущий                   |
| Смена пароля                           | Отзываются все сеансы, кроме текущего                                 |
| Удаление учётной записи                | Строки сеансов удаляются                                              |
| Исключение из команды                  | Сеансы не затрагиваются: доступ к команде закрывает проверка членства |

**Вход через Telegram** — только в вебе. SPA получает от виджета объект с данными пользователя и подписью и передаёт его в `POST /api/v1/auth/telegram`. Сервер проверяет подпись (HMAC-SHA256, ключ — SHA-256 от токена бота) и свежесть `auth_date` (не старше суток), ищет пользователя по `telegram_id` и создаёт веб-сеанс. Если Telegram не привязан ни к одной учётной записи — отказ `telegram_not_linked`, регистрации через Telegram нет. Привязка в профиле проверяет данные виджета так же.

**Ограничение частоты:** вход, регистрация и вход через Telegram — не больше 10 попыток в минуту с одного IP; превышение — 429. Неудачный вход отвечает одинаково для несуществующего ника и неверного пароля.

**Журнал событий безопасности** — в логах `slog`: вход, неудачный вход, выход, завершение всех сеансов, смена пароля, привязка и отвязка Telegram, удаление учётной записи. Без паролей и токенов.

## Рассмотренные варианты

- **Пара access + refresh: JWT доступа на 15 минут и долгоживущий refresh-токен с ротацией** — так было записано в требованиях. Проверка access-токена не требует БД. Но выигрыш исчезает, потому что БД всё равно нужна для проверки членства в команде. Взамен появляются секрет подписи, выпуск и проверка JWT, ротация refresh-токена и защита от его повторного использования, а в приложении — перехват 401, обновление токена и защита от двух одновременных обновлений, которые при ротации разлогинивают пользователя. Отзыв не мгновенный: украденный токен доступа живёт до 15 минут. Вебу эта пара всё равно не подходит — ему нужна cookie, и механизмов стало бы два.
- **Bearer-токен и в вебе** (токен в `localStorage`) — один способ передачи. Но токен доступен любому скрипту на странице, и одна XSS-уязвимость означает угон сеанса.
- **Cookie и в приложении** — тоже один способ передачи. Но HTTP-клиенту приложения пришлось бы хранить cookie самостоятельно, а защиту от CSRF, нужную только браузеру, пришлось бы применять и к приложению.
- **Сеансы в памяти процесса** — без обращений к БД. Но теряются при каждом перезапуске и выпуске новой версии.
- **bcrypt вместо Argon2id** — допускается требованиями и проще в настройке. Но обрезает пароль до 72 байт, а Argon2id — текущая рекомендация OWASP, и оба есть в `golang.org/x/crypto`.
- **Один непрозрачный токен, в вебе в cookie, в приложении в заголовке (выбран).**

## Обоснование

Критерии в порядке важности: безопасность сеансов (мгновенный отзыв, защита от XSS и CSRF) > простота реализации на сервере и в приложении > производительность сверх объёмов из требований.

- **Обращение к БД на каждом запросе — не цена, а данность.** Членство в команде проверяется при каждом обращении, сеанс ищется ещё одним запросом по уникальному индексу — доли миллисекунды. Так по умолчанию работают сессии в Django, Rails и Laravel. Пара access + refresh экономит этот запрос там, где сервисов много и общей базы сеансов нет; у нас один сервер и одна база.
- **Мгновенный отзыв** прямо отвечает требованию: «завершить все сеансы» при утере телефона срабатывает сразу, а не через 15 минут.
- **Меньше кода в приложении.** Валере не нужна логика обновления токенов — самый частый источник ошибок в мобильных клиентах. Токен истёк или отозван — 401, и приложение просит войти заново.
- **Cookie `HttpOnly` для веба** защищает токен от XSS почти бесплатно: в gin это одна строка установки cookie и одна строка чтения. Проверка `Origin` закрывает соседние поддомены, которые `SameSite` не отсекает.
- **Требование об access и refresh** было записано до этого анализа как типовое решение, а не как условие задачи, поэтому оно меняется вместе с этим ADR.

## Последствия

**Плюсы:**

- Один механизм сеансов и один middleware для обоих клиентов.
- Отзыв сеансов мгновенный.
- В приложении нет обновления токенов: только вход и хранение одного токена.
- Токен веб-сеанса недоступен скриптам на странице.
- Таблица `auth_sessions` из модели данных подходит без изменений.

**Минусы и ограничения:**

- Каждый запрос ищет сеанс в БД; при недоступности БД не работает ничего, включая чтение (но без БД API и так бесполезен).
- Украденный токен приложения действует до отзыва или до 30 суток без использования; защита — хранилище ОС и «завершить все сеансы».
- Проверка `Origin` требует правильной переменной `PUBLIC_URL` в каждом окружении; ошибка в ней блокирует изменения в вебе.
- Префикс `__Host-` требует `Secure`, поэтому локальная разработка веба — только через `localhost` (браузеры считают его безопасным) или dev-сервер Vite с проксированием.
- Ограничение частоты по IP общее для пользователей за одним NAT мобильного оператора.

**Что нужно сделать:**

- `hub/requirements.md` — раздел 4, «Безопасность»: сеансы — непрозрачные токены, хранятся хешами, отзываются при смене пароля и по запросу (версия 0.4).
- `hub/data-model.md`, раздел 3.1 — ссылка на этот ADR вместо «определит ADR об аутентификации».
- `contracts/openapi.yaml` — схемы безопасности `bearerAuth` и `cookieAuth`, эндпоинты `/auth/*` и `/me/*`.
- Приложение (APP-7) — хранение токена в `flutter_secure_storage`, повторный вход при 401.
