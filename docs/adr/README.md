# Architecture Decision Records

ADR фиксирует **почему** было принято архитектурное решение: какая была проблема, что рассматривали, что выбрали и чем за это платим. Что именно сделано, видно из кода и спецификаций; ADR хранит то, чего в них нет, — ход рассуждений.

Шаблон → **[template.md](template.md)**

---

## Когда нужен ADR

Пишите ADR, если решение:

- выбирает между несколькими реальными альтернативами (компонент, библиотека, сервис, подход);
- меняет интерфейс между частями системы — BLE-протокол, REST API, схему БД;
- сужает или расширяет объём работ (что входит в MVP / V1, что откладывается);
- через полгода будет непонятно без контекста: «а почему у нас так?».

Не нужен ADR для решений, которые очевидны, легко отменяются или касаются только внутренностей одного модуля.

> Сомневаетесь — спросите в задаче. Короткий ADR лучше потерянного обоснования.

---

## Как оформить

1. **Номер.** Возьмите следующий свободный номер из индекса ниже.
2. **Файл.** Скопируйте [template.md](template.md) в `NNN-короткое-название.md` — латиница, kebab-case: `013-device-postponed.md`.
3. **Ветка и PR.** ADR оформляется отдельным PR (или вместе с изменением, которое он обосновывает). Статус в PR — **Предложено**. В том же PR добавьте строку в индекс.
4. **Ревью.** Обсуждение идёт в комментариях к PR. Если по итогам решение меняется — правьте ADR в той же ветке.
5. **Принятие.** Перед слиянием поменяйте статус на **Принято** и поставьте дату. Отклонённый ADR тоже можно слить со статусом **Отклонено** — запись о том, почему отказались, сама по себе ценна.

**Автор** — тот, кто предложил решение и написал ADR. Указывается так же, как в контактах [CONTRIBUTING.md](../../CONTRIBUTING.md#контакты): имя и логин Gitea — «Влад (@H1K0)». Несколько авторов — через запятую. LLM в поле «Автор» не указывается: её участие отражается трейлером `Co-Authored-By` в коммите.

**Коллизия номеров.** Если два PR одновременно заняли один номер, тот, что сливается позже, перед слиянием переименовывает свой ADR на следующий свободный.

---

## Правила

- **Принятый ADR не переписывается.** Допустимы исправления опечаток и битых ссылок. Если решение изменилось — пишется новый ADR, который заменяет старый.
- **Замена оформляется с двух сторон.** В новом ADR поле «Заменяет» ссылается на старый. В старом меняются только поля «Статус» (→ Заменено) и «Заменён» — и это делается в том же PR, что и новый ADR.
- **Решение и спецификация синхронны.** Если ADR меняет требования или архитектуру, в разделе «Что нужно сделать» перечисляются документы для обновления; обновить их можно в том же PR или отдельными задачами.

### Статусы

| Статус     | Значение                                                        |
| ---------- | --------------------------------------------------------------- |
| Предложено | ADR в открытом PR, решение обсуждается                          |
| Принято    | Решение действует                                               |
| Отклонено  | Рассмотрено и не принято; ADR сохраняется как запись о причинах |
| Отложено   | Решение верное, реализация перенесена в указанную версию        |
| Заменено   | Отменено более новым ADR (ссылка в поле «Заменён»)              |
