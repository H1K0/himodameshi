## Контекст

Himo Hub — веб-сервис с REST API для мобильного приложения и веб-интерфейсом для браузера ([hub/requirements.md](../spec/hub/requirements.md)). API потребляют два клиента на разных языках: приложение на Dart и веб на TypeScript.

Критерии курса задают рамки: PostgreSQL; конфигурация из переменных окружения с типизированной загрузкой (в духе pydantic-settings) и `.env.example`; линтер, форматтер и статическая типизация в CI; тесты с PostgreSQL в CI и покрытием не ниже 60 %; Dockerfile с многоэтапной сборкой и запуском не от root; `docker compose up --build` поднимает всё с первого раза, миграции применяются при первом запуске; автоматическая документация OpenAPI с примерами; структурные логи с `request_id`; `GET /health` с проверкой БД. Конкретные инструменты из критериев (FastAPI, ruff, pytest) не обязательны — допустимы аналоги.

Бэкенд и базу ведёт Влад, у него есть опыт с Go, gin, pgx, goose и sqlc на других проектах (в том числе SvelteKit-фронтенд в одном образе с Go-сервером). Сервис разворачивается на домашнем сервере, где PostgreSQL обычно установлен на хосте, а не в контейнере.

## Решение

**Сервер:**

- **Go**, HTTP-фреймворк **gin**.
- **Contract-first:** источник правды об API — `contracts/openapi.yaml` (OpenAPI 3.0). Из него генерируются серверные интерфейсы и типы (oapi-codegen, strict-сервер под gin), TypeScript-типы для веба (`openapi-typescript`) и клиент для приложения (генератор выбирается вместе с разработчиком приложения).
- **PostgreSQL**, драйвер **pgx/v5**, запросы — **sqlc**: SQL в файлах с аннотациями, по ним генерируется типизированный Go-код. Именованные параметры (`@name`, `sqlc.narg`), необязательные фильтры через `NULL`, общее число строк — через `count(*) OVER ()`. Сгенерированный код проверяется в CI (`sqlc diff`).
- **Миграции — goose**, применяются при старте сервера. Схему sqlc читает из тех же миграций.
- **Конфигурация — переменные окружения**, разбор в типизированную структуру через **caarlos0/env** (обязательные поля, значения по умолчанию, проверка при старте). Локальные значения — в `.env` по образцу `.env.example`, их передаёт compose; сам сервер файл `.env` не читает. Строка подключения — одна переменная `DATABASE_URL`, поэтому PostgreSQL может быть как в контейнере, так и на хосте.
- **Логи — `log/slog`** в JSON: время, уровень, `request_id`, контекст запроса.
- **`GET /health`** проверяет соединение с БД.
- **Качество:** golangci-lint, gofumpt, `go vet` в составе линтера; `go test` с покрытием не ниже 60 %; интеграционные тесты на настоящем PostgreSQL — testcontainers-go локально, service container в CI.
- **Документация API — `/docs` на Scalar** по `openapi.yaml`. Это **эксперимент**: если не приживётся, заменяем на Swagger UI — замена сводится к одной HTML-странице.

**Веб:** **SvelteKit** в режиме SPA (`adapter-static`, fallback `index.html`). Собранная статика отдаётся тем же Go-сервером из каталога `STATIC_DIR`; на неизвестные пути вне `/api` сервер отвечает `index.html`. В разработке интерфейс отдаёт dev-сервер Vite с проксированием API.

**Контейнеры:**

- **Один образ** с многоэтапной сборкой: Node (сборка веба) → Go (сборка сервера) → distroless nonroot. Node и Go нужны только внутри сборки, на хосте ничего не собирается.
- **`compose.yaml`** — hub и PostgreSQL в контейнере, для разработки и проверки.
- **Продуктивный compose** — hub без PostgreSQL, `DATABASE_URL` указывает на PostgreSQL на хосте (подробнее — в ADR о развёртывании).

Аутентификация (токены, хеширование паролей, вход через Telegram) — отдельным решением.

## Рассмотренные варианты

Язык:

- **Python + FastAPI** — критерии курса фактически написаны под него: pydantic-settings, ruff, pytest, OpenAPI из коробки. Но в контейнере нужен интерпретатор с зависимостями, типизация необязательная, OpenAPI получается из кода, а не наоборот; опыта в команде меньше, чем с Go.
- **TypeScript (Node)** — один язык с вебом. Но рантайм тяжелее, а экосистема серверных фреймворков менее стабильна.
- **Dart** (dart_frog, shelf) — один язык с приложением. Но серверная экосистема маленькая: мало готового для PostgreSQL и OpenAPI.
- **Go (выбран).**

HTTP-фреймворк:

- **Стандартный `net/http`** — с Go 1.22 умеет паттерны маршрутов, без зависимостей. Но middleware, привязку параметров и ответы пришлось бы собирать самим.
- **chi, echo** — сопоставимы с gin, но опыта с ними нет.
- **gin (выбран)** — знаком, oapi-codegen генерирует под него сервер.

Описание API:

- **Code-first** (аннотации swaggo, фреймворк huma) — спецификация генерируется из кода. Но тогда клиенты приложения и веба зависят от того, как написан сервер, а изменение API обнаруживается постфактум.
- **Contract-first (выбран).**

Доступ к БД:

- **ORM** (GORM, ent) — меньше SQL. Но сложные запросы (фильтры, `ON CONFLICT` для идемпотентной выгрузки, курсоры) упираются в возможности ORM, а сгенерированный SQL непрозрачен.
- **Чистый pgx** — полная гибкость, динамические запросы пишутся просто. Но SQL лежит в строках и проверяется только при выполнении, разбор строк — вручную.
- **sqlc + pgx (выбран).**

Конфигурация:

- **godotenv и свой загрузчик** — знакомый подход. Но godotenv только читает файл, разбор и проверку пишем сами, а в контейнере файл `.env` и так передаёт compose.
- **caarlos0/env (выбран).**

Веб:

- **Отдельный контейнер** со статикой — независимые выпуски веба. Но два образа, две версии и согласование совместимости веба с API.
- **Svelte без SvelteKit** — легче, но маршрутизацию и структуру проекта пришлось бы собирать самим.
- **SvelteKit SPA в образе сервера (выбран).**

Документация API:

- **Swagger UI** — самый известный. Но устаревший интерфейс и неудобная навигация.
- **Redoc** — читаемый, но без отправки запросов со страницы.
- **Scalar (выбран как эксперимент).**

## Обоснование

Критерии в порядке важности: соответствие критериям курса > опыт команды > простота развёртывания > строгость контрактов.

- **Go** даёт один статический бинарник и маленький образ на distroless, типизацию на уровне компилятора и стандартную библиотеку, которая закрывает логи и большую часть HTTP. Это ускоряет и сборку, и развёртывание на домашнем сервере. Опыт Влада с Go, gin, pgx, goose и sqlc снижает риск: большая часть стека уже проверена на практике.
- **Contract-first** важен потому, что у API два клиента на разных языках. Спецификация, из которой генерируются сервер, TypeScript-типы и Dart-клиент, не даёт им разойтись; она же автоматически даёт документацию с примерами, как требует курс.
- **sqlc** проверяет SQL на этапе генерации и убирает ручной разбор строк, оставляя полноценный SQL — он нужен для идемпотентной выгрузки (`ON CONFLICT`), курсоров синхронизации и фильтров списков. Необязательные фильтры решаются через `NULL`-параметры — подход уже опробован на другом проекте.
- **caarlos0/env** — прямой аналог pydantic-settings: типизированная структура с проверкой при старте. Конфигурация целиком в переменных окружения, как требует 12-Factor.
- **Один образ с вебом** — один артефакт, одна версия (тег `hub/v*`), веб и API на одном домене без CORS. Пока веб — интерфейс к одному API той же команды, независимые выпуски почти ничего не дают.
- **`DATABASE_URL` вместо зашитого адреса** позволяет держать PostgreSQL в контейнере для разработки и на хосте на сервере без изменений кода.

## Последствия

**Плюсы:**

- Сервер, веб и приложение работают по одной спецификации; документация API всегда соответствует коду.
- Маленький образ без оболочки и пакетного менеджера, процесс не от root.
- `docker compose up --build` поднимает сервис и базу с первого раза, миграции применяются автоматически.
- PostgreSQL может жить и в контейнере, и на хосте.

**Минусы и ограничения:**

- Go многословен, особенно обработка ошибок. Инструменты из критериев курса закрываются аналогами (ruff → golangci-lint, black → gofumpt, mypy → компилятор Go), это придётся пояснять при сдаче.
- gin — лишняя зависимость по сравнению со стандартной библиотекой и свой тип контекста.
- Contract-first требует сначала описать API в `openapi.yaml`, потом писать код. oapi-codegen поддерживает OpenAPI 3.0, не всё из 3.1.
- Три генератора в цепочке (oapi-codegen, openapi-typescript, sqlc) — сгенерированный код нужно держать в актуальном состоянии и проверять в CI.
- Необязательные фильтры через `NULL`-параметры и сортировка через `CASE` хуже используют индексы, поиск через `ILIKE '%…%'` без триграммного индекса читает таблицу целиком. На объёмах из требований (10 000 кабелей) это несущественно, при росте — первое место для оптимизации.
- Миграции при старте требуют прав на DDL у пользователя приложения и рассчитаны на один экземпляр сервера.
- В distroless нет оболочки, curl и wget: отлаживать внутри контейнера неудобно, а healthcheck контейнера делается подкомандой самого сервера (`hub healthcheck`).
- Веб выпускается только вместе с сервером; сборка образа дольше из-за стадии Node.
- `caarlos0/env`, oapi-codegen и Scalar для команды новые.
