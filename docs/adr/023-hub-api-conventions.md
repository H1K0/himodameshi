# ADR-023: Соглашения API Hub — REST для ресурсов, синхронизация отдельными операциями `/sync/push` и `/sync/pull`

## Контекст

API Hub описывается контрактом `contracts/openapi.yaml`, из которого генерируются сервер на Go, типы для веба на TypeScript и клиент для приложения на Dart ([ADR-015](015-hub-stack.md)). Требования задают рамку: REST, JSON, `/api/v1`, ошибки по RFC 9457, время в RFC 3339, UUIDv7, имена полей как в BLE-протоколе ([hub/requirements.md](../spec/hub/requirements.md), раздел 4).

Внутри этой рамки остаётся много мелких решений, которые должны быть одинаковыми во всех эндпоинтах, иначе каждый клиент будет обрабатывать каждый эндпоинт по-своему: формат ошибок, пагинация, передача версии для оптимистичной блокировки, частичное или полное обновление, реакция на устаревшую версию приложения.

Отдельный вопрос — синхронизация с приложением (HUB-7). Она плохо ложится на ресурсы:

- выгрузка — это пачка разнородных объектов (новые кабели, правки, тесты), часто из нескольких команд, с результатом по каждому объекту;
- загрузка изменений принимает курсор и список отслеживаемых кабелей, который может быть длиной в сотни UUID;
- выгрузка и загрузка должны быть одной операцией каждая, а не серией запросов: так приложению проще не оказаться в наполовину синхронизированном состоянии.

Механизм синхронизации и модель данных под него уже определены ([hub/data-model.md](../spec/hub/data-model.md), [ADR-021](021-hub-data-model.md)).

## Решение

Полный протокол синхронизации — **[hub/sync.md](../spec/hub/sync.md)**, контракт — `contracts/openapi.yaml`. Ниже — общие соглашения.

**Адреса.**

- Все эндпоинты — под `/api/v1`, кроме `GET /health`.
- Коллекции вложены в команду: `/api/v1/teams/{teamId}/cables`, `/api/v1/teams/{teamId}/events`. Отдельные объекты адресуются плоско: `/api/v1/cables/{cableId}`, `/api/v1/tests/{testId}`. ID глобально уникальны, поэтому постоянные ссылки короче, а команда объекта известна серверу из БД.
- Действия, которые не сводятся к изменению полей, — подресурсы с `POST`: `/cables/{id}/archive`, `/teams/{id}/leave`.

**Формат.** JSON в UTF-8, имена полей и значения перечислений в `snake_case`, как в BLE-протоколе и в БД. Время — RFC 3339; сервер отдаёт UTC с `Z`. Отсутствующее значение — `null`, поле при этом присутствует.

**Ошибки — RFC 9457** (`application/problem+json`) с полем расширения `code` — машиночитаемой строкой вида `cable_archived`. Клиент выбирает текст сообщения по `code`, а не по `title` или `detail`. Ошибки проверки содержат список `errors` с путём к полю. Список кодов — в `openapi.yaml`.

**Доступ к чужим данным.**

- Команда, в которой пользователь не состоит (в том числе бывший участник), — `403` с `code: no_team_access`. Это явный признак, который требование HUB-7 обязывает отдавать бывшим участникам.
- Кабель, тест или приглашение, которые принадлежат чужой команде, неотличимы от несуществующих — `404`.
- Действие, доступное только владельцу, — `403` с `code: owner_only`.

**Пагинация** — `limit` (от 1 до 100, по умолчанию 50) и `offset`; ответ — `{items, total}`. Курсорная пагинация используется только в синхронизации.

**Изменение кабеля — полной заменой (`PUT`) с версией в теле.** Клиент присылает все изменяемые атрибуты (`name`, `cable_type`, `color`, `note`, `assignee_id`) и `version`, от которой сделана правка. Расхождение версии — `409` с `code: version_conflict` и актуальным кабелем в теле ответа.

**Повтор запроса.** `PUT` и `DELETE` повторяются без последствий. Пометка теста недействительным — `PUT /tests/{id}/invalidation`, снятие — `DELETE` того же адреса. Архивирование уже архивного кабеля отвечает текущим состоянием, а не ошибкой.

**Версия приложения.** Приложение отправляет заголовок `X-App-Version` с каждым запросом. Если версия ниже минимальной (переменная окружения сервера), сервер отвечает `426` с `code: app_outdated` и полем `min_app_version`. Запросы без заголовка (веб) не проверяются.

**Синхронизация — две операции под `/sync`, а не ресурсы:**

- **`POST /api/v1/sync/push`** — новые кабели, правки атрибутов и новые тесты одним пакетом, из любых команд пользователя, не больше 100 объектов. Весь пакет обрабатывается в одной транзакции, у каждого объекта — своя точка сохранения (`SAVEPOINT`): отклонённый объект откатывается до неё и не мешает остальным, принятые фиксируются вместе. Ответ — `200` с результатом по каждому объекту.
- **`POST /api/v1/sync/pull`** — изменения отслеживаемых кабелей одной команды после курсора. В теле — команда, курсор и список кабелей. Ответ строится по одному снимку БД (`REPEATABLE READ`), до 100 тестов на страницу.

**Что API не делает:** не создаёт кабели и тесты вне `push` (тест требует прибора), не сравнивает тесты и не строит PDF — это делает клиент по данным тестов. Чтобы клиенту не искать тесты для сравнения, `GET /tests/{id}` отдаёт `previous_test_id` и `reference_test_id`.

## Рассмотренные варианты

Синхронизация:

- **Обычные ресурсы:** `POST /cables`, `POST /tests`, `PUT /cables/{id}` по одному объекту, `GET /cables/{id}/changes?since=N` по каждому кабелю. Чистый REST, ничего не нужно обосновывать. Но выгрузка накопленных без связи данных превращается в десятки запросов без общей транзакции, а загрузка — в запрос на каждый отслеживаемый кабель. Push и pull перестают быть одной операцией каждая.
- **Пакетная выгрузка в команду** (`POST /teams/{id}/upload`) — команда в адресе. Но приложение копит данные нескольких команд сразу, и одна синхронизация стала бы несколькими выгрузками.
- **Правки атрибутов из приложения через `PUT /cables/{id}`, а не в пакете** — обработка конфликта в одном месте. Но выгрузка снова становится двухшаговой. На сервере правку выполняет одна функция при любом пути, так что выигрыш мал.
- **Пакет «всё или ничего»** — простая семантика. Но противоречит HUB-7: один тест в заархивированный тем временем кабель навсегда блокировал бы всю синхронизацию пользователя.
- **Загрузка через `GET` с курсором в адресе** — по правилам REST. Но без списка отслеживаемых кабелей сервер не может сообщить об удалённых (удаления не хранятся), а список из сотен UUID превышает разумную длину адреса (у nginx по умолчанию около 8 КБ на строку запроса).
- **`/sync/push` и `/sync/pull`, команда в теле (выбран).** Обе операции — в одном разделе адресов и документации, и сразу видно, где кончается обычный REST.

Обновление кабеля:

- **`PATCH` с частичным телом** — клиент присылает только изменённые поля. Но для `note` и `assignee_id` нужно различать «поле не передано» и «поле сброшено в `null`»; генераторы Go и Dart выражают это неудобными обёртками, и это частый источник ошибок.
- **`PATCH` по RFC 7396 (JSON Merge Patch)** — та же проблема с `null`.
- **`PUT` с полным набором изменяемых атрибутов (выбран).** У клиента всегда есть полное состояние кабеля — он его только что получил.

Версия для оптимистичной блокировки:

- **`ETag` и `If-Match`** — стандартный механизм HTTP. Но версию пришлось бы передавать в заголовке, а в пакетной выгрузке её всё равно нужно передавать в теле — получилось бы два способа.
- **Поле `version` в теле (выбран).**

Пагинация списков:

- **Курсорная везде** — устойчива к вставкам между страницами. Но в вебе нужны номера страниц и сортировка по разным полям, что с курсором сложнее.
- **`limit` и `offset` с `total` (выбран)** — уже заложено в ADR-015 через `count(*) OVER ()`.

Устаревшее приложение:

- **Отдельный эндпоинт `GET /meta` с минимальной версией** — приложение проверяет её само. Но проверку можно забыть, а несовместимый запрос всё равно нужно отклонять на сервере.
- **Заголовок `X-App-Version` и ответ `426` (выбран).**

## Обоснование

Критерии в порядке важности: одинаковое поведение всех эндпоинтов для двух генерируемых клиентов > соответствие требованиям HUB-7 > следование REST там, где оно ничего не стоит > краткость контракта.

- **REST для ресурсов, операции для синхронизации.** Кабели, тесты, команды и приглашения — обычные ресурсы, и REST описывает их без натяжек. Синхронизация — не ресурс, а протокол обмена состоянием: пакет разнородных объектов туда и выборка изменений по курсору обратно. Попытка выразить её ресурсами дала бы десятки запросов без общей транзакции. Курсор при этом не нарушает stateless: сервер ничего не помнит о клиенте, курсор хранит и присылает приложение, а `change_seq` — данные ресурсов, как `version`.
- **Транзакция с точками сохранения** даёт оба нужных свойства сразу: независимость объектов (требование HUB-7) и согласованность — ответ точно совпадает с тем, что записано, а при падении сервера посередине не записывается ничего, и повтор пакета проходит заново.
- **`code` в ошибках** позволяет приложению показывать понятные сообщения (требование APP-7) без разбора текста, а серверу — менять формулировки, не ломая клиентов.
- **`PUT` и `version` в теле** выбраны ради генерируемых клиентов: обычные структуры без обёрток для «не передано» и без отдельной работы с заголовками.
- **`403` для команды и `404` для объекта** совмещают два требования: бывший участник получает явный отказ, а знание ID кабеля или теста чужой команды ничего не раскрывает.

## Последствия

**Плюсы:**

- Синхронизация — два запроса: один push и по одному pull на команду (плюс страницы при большом объёме).
- Все эндпоинты одинаково сообщают об ошибках, одинаково листаются и одинаково проверяют версию.
- Сгенерированные клиенты работают с обычными структурами.
- Отступления от REST собраны в одном разделе `/sync` и обоснованы.

**Минусы и ограничения:**

- Ответ `push` — всегда `200`, даже если все объекты отклонены; клиент обязан смотреть результат каждого объекта.
- Пакетная транзакция держит блокировки строк всех затронутых команд до конца обработки пакета. Пакет ограничен 100 объектами, а строки команд блокируются в порядке их ID, чтобы избежать взаимоблокировок.
- `PUT` требует отправлять все изменяемые атрибуты, даже если меняется одно поле.
- `POST /sync/pull` не кэшируется HTTP-кэшами — для синхронизации это и не нужно.
- `offset` медленнее на дальних страницах и может пропустить или повторить строку, если список меняется между запросами; на объёмах команды (сотни кабелей) это несущественно.

**Что нужно сделать:**

- `contracts/openapi.yaml` — контракт по этим соглашениям.
- `hub/sync.md` — протокол синхронизации со стороны приложения.
- `hub/requirements.md` — ссылки на контракт и протокол синхронизации (версия 0.4).
- `hub/data-model.md`, раздел 5 — ссылка на `sync.md`, описание протокола переносится туда.
- `architecture.md`, раздел 6, и `app/requirements.md`, APP-7 — ссылки на `sync.md`.
- Сообщить Валере, что контракт готов: генератор Dart-клиента выбирается вместе с ним.
