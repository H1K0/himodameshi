# ADR-017: Развёртывание Himo Hub на домашнем сервере — Docker Compose, nginx, Gitea Actions

## Контекст

Критерии курса к развёртыванию: публичный URL, обратный прокси, HTTPS, переменные окружения на сервере, автоматический деплой, автоперезапуск, окружения dev и prod. К CI: на каждый PR — линтер, форматтер, тесты с PostgreSQL, покрытие не ниже 60 %, сборка образа с тегом версии или SHA и публикация в реестр; при красном пайплайне слияние блокируется. К наблюдаемости — логи в файл или систему сбора.

Бюджета на хостинг нет. У Влада есть домашний сервер: Ubuntu 22.04, Docker, nginx, сертификаты Let's Encrypt, Gitea ([ADR-014](014-repository-and-branching.md)), PostgreSQL на хосте. Перед роутером и сервером стоит ИБП. Домены: prod — `himo.hakoniwa.ru`, dev — `dev.himo.hakoniwa.ru`.

Стек Hub — один образ с сервером и вебом, PostgreSQL по `DATABASE_URL`, healthcheck подкомандой сервера ([ADR-015](015-hub-stack.md)). Компоненты выпускаются тегами `<компонент>/vX.Y.Z` ([ADR-014](014-repository-and-branching.md)).

## Решение

**Окружения** — оба на домашнем сервере, как два независимых compose-проекта:

|             | dev                               | prod                               |
| ----------- | --------------------------------- | ---------------------------------- |
| Домен       | `dev.himo.hakoniwa.ru`            | `himo.hakoniwa.ru`                 |
| Обновляется | при каждом слиянии в `dev`        | по тегу `hub/vX.Y.Z` на `master`   |
| Образ       | `sha-<коммит>`                    | `X.Y.Z`                            |
| База        | `himo_dev` со своим пользователем | `himo_prod` со своим пользователем |
| Секреты     | свой токен бота, свой ключ ИИ     | свои                               |

**Обратный прокси — nginx на хосте.** TLS завершается на nginx (Let's Encrypt через certbot), HTTP перенаправляется на HTTPS, заголовок HSTS. Контейнер Hub публикует порт только на `127.0.0.1`, nginx проксирует на него и передаёт `X-Forwarded-For` и `X-Forwarded-Proto`. Hub доверяет этим заголовкам только от адресов моста Docker — через них nginx на хосте достаёт до контейнера.

**PostgreSQL — на хосте.** Контейнер подключается через `host.docker.internal` (`extra_hosts: host-gateway`). PostgreSQL слушает адрес моста Docker, `pg_hba.conf` пускает из подсети Docker только пользователей `himo_dev` и `himo_prod` в их базы.

**Реестр образов — встроенный реестр контейнеров Gitea:** `git.hakoniwa.ru/tech/himo-hub`. Старые образы `sha-*` удаляются правилом очистки, версии `X.Y.Z` хранятся.

**Конвейер (Gitea Actions):**

| Событие          | Что происходит                                                                                                                                                                  |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PR в `dev`       | Линтер, проверка форматирования, тесты с PostgreSQL (service container), покрытие ≥ 60 %, сборка образа и публикация с тегом `sha-<коммит>`. Красный пайплайн блокирует слияние |
| Слияние в `dev`  | Образ `sha-<коммит>` разворачивается на dev                                                                                                                                     |
| Тег `hub/vX.Y.Z` | Сборка образа `X.Y.Z`, публикация, развёртывание на prod                                                                                                                        |

Остальные компоненты запускают свои задачи по фильтрам путей; здесь описан Hub.

**Деплой** — задача на runner'е: `docker compose pull`, `docker compose up -d`, ожидание статуса `healthy`. Если за отведённое время контейнер не стал здоровым — откат на предыдущий тег образа, задача падает.

**Runner — `act_runner` на том же сервере.** Он сам забирает задачи у Gitea, входящих подключений снаружи не нужно. Задачи CI и деплоя разделены метками runner'а. Деплойные задачи запускаются только на слияние в `dev` и на теги, никогда на открытие или обновление PR, и только у них есть доступ к секретам деплоя. Workflow из PR от форков запускаются только после одобрения участником команды.

**Секреты.** В репозитории только `.env.example`. На сервере у каждого окружения свой `.env` с правами `600`, его читает только пользователь деплоя. Токен для реестра — в секретах Gitea Actions.

**Автоперезапуск:** `restart: unless-stopped` поднимает контейнер после падения процесса и после перезагрузки сервера. Healthcheck контейнера — `hub healthcheck`.

**Логи** — драйвер `json-file` с ротацией (ограничение размера и числа файлов): логи хранятся в файлах на сервере, смотреть — `docker compose logs`.

**Резервные копии.** Сейчас: ежедневно вручную полная копия PostgreSQL через pgAdmin с ПК, копия синхронизируется с Яндекс Диском, история файла — 90 дней.

**Открытый dev.** dev-окружение доступно из интернета без ограничений, как и prod. Риски и меры:

| Риск                                                 | Мера                                                                                                                        |
| ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Посторонние регистрируются и пользуются dev          | Отдельная база, данные на dev считаются тестовыми и могут быть удалены в любой момент; в интерфейсе — заметная плашка «dev» |
| Расход ключа ИИ на dev через прокси `/insights`      | Отдельный ключ с минимальным лимитом; ограничение частоты запросов                                                          |
| dev попадает в поисковики, его путают с prod         | Заголовок `X-Robots-Tag: noindex`, плашка «dev»                                                                             |
| Уязвимость в ещё не выпущенном коде доступна снаружи | В dev попадает только код после ревью; секреты и база dev не пересекаются с prod                                            |
| Доступ к данным prod через dev                       | Разные пользователи и базы в PostgreSQL, разные секреты; у пользователя dev нет прав на базу prod                           |

## Рассмотренные варианты

Хостинг:

- **VPS в РФ** — стабильный аптайм и белый IP. Но платно, а бюджета нет.
- **PaaS** (облачные контейнерные платформы) — не нужно администрировать сервер. Но платно, а зарубежные платформы ещё и под риском ограничений.
- **Домашний сервер (выбран)** — бесплатно, полный контроль, всё необходимое уже установлено.

Запуск:

- **`docker run` из скриптов** — минимум зависимостей. Но конфигурация не декларативная, легко разойтись между окружениями.
- **Docker Swarm, k3s** — умеют перезапускать нездоровые контейнеры и обновлять без простоя. Но для одного сервера и одного сервиса это лишний уровень сложности.
- **Docker Compose (выбран).**

Доставка:

- **SSH с облачного CI** — нужен входящий SSH на домашний сервер из интернета.
- **Watchtower** — сам подтягивает новые образы. Но не знает о тестах и тегах, развёртывание становится неуправляемым.
- **Сборка из репозитория прямо на сервере** — без реестра. Но курс требует публикацию в реестр, на prod попадал бы не тот образ, что проверен в CI, а откат требовал бы пересборки.
- **Runner на сервере и образы из реестра (выбран).**

Момент деплоя на dev:

- **При открытии и обновлении PR** — изменения видны до слияния. Но выполнялся бы непроверенный код с доступом к Docker и секретам — при публичном репозитории это доступ к серверу для любого автора PR; к тому же открытые PR перезаписывали бы одно dev-окружение друг другу.
- **При слиянии в `dev` (выбран).**

TLS:

- **Caddy, Traefik** — сертификаты получаются автоматически. Но nginx уже стоит и обслуживает другие сервисы на сервере.
- **nginx + certbot (выбран).**

## Обоснование

Критерии в порядке важности: требования курса > нулевой бюджет > безопасность сервера > простота сопровождения одним человеком.

Домашний сервер — единственный вариант без затрат, и на нём уже есть всё нужное: Docker, nginx, сертификаты, Gitea. Compose даёт декларативное описание окружений, которое хранится в репозитории и одинаково для dev и prod, без накладных расходов оркестратора. Runner на том же сервере работает только с исходящими соединениями — не нужно открывать SSH в интернет. Реестр Gitea закрывает требование курса и даёт неизменяемые артефакты: на prod едет тот же образ, что проверен в CI, откат — это смена тега.

Деплой на dev при слиянии, а не при открытии PR, — главная мера безопасности: на сервере выполняется только код, прошедший ревью. Актуальность dev при этом сохраняется — он обновляется после каждой влитой задачи.

## Последствия

**Плюсы:**

- Хостинг бесплатный, всё под контролем команды.
- dev всегда соответствует ветке `dev`, prod — последнему выпущенному тегу.
- Неизменяемые образы и откат сменой тега.
- Конфигурация окружений хранится в репозитории.

**Минусы и ограничения:**

- Доступность зависит от электричества и провайдера. ИБП закрывает короткие отключения питания, но не перебои у провайдера и не долгие отключения — 99 % доступности из требований не гарантированы.
- Сервер — единственная точка отказа: на нём и prod, и dev, и Gitea, и CI. Пока Gitea недоступна, недоступны и репозиторий, и деплой.
- Runner с доступом к Docker фактически имеет права root на сервере. Защита держится на правилах запуска: деплой только после слияния, workflow из форков только после одобрения, секреты деплоя недоступны задачам PR. Ошибка в этих правилах — прямой риск для сервера.
- dev и prod делят ресурсы одной машины; сборка образов в CI нагружает тот же сервер.
- Docker не перезапускает контейнер, который завис, но не упал (`unhealthy`): `restart` срабатывает только при завершении процесса. Зависание ловится проверкой при деплое и мониторингом, но не исправляется автоматически.
- Резервное копирование ручное и зависит от ПК: пропущенный день увеличивает возможную потерю данных; восстановление из копии ещё не проверялось.
- Открытый dev — риски перечислены выше; меры снижают их, но не устраняют.

**Что нужно сделать:**

- Сертификаты для `himo.hakoniwa.ru` и `dev.himo.hakoniwa.ru`.
- Конфигурация nginx для обоих доменов — хранить в репозитории (`deploy/`) как образец.
- Compose-файлы окружений, `.env` на сервере, базы и пользователи в PostgreSQL, правила `pg_hba.conf`.
- `act_runner` с метками для CI и деплоя, одобрение workflow из форков, токен реестра в секретах, правило очистки образов.
- Workflow Gitea Actions для Hub: проверки PR, деплой на dev и prod, откат.
- Автоматизировать резервное копирование и провести учебное восстановление — отдельной задачей.
- `architecture.md` — схема развёртывания; README — раздел о развёртывании.
