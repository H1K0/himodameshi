## 1. Общая схема

ПАК «Химодамэси» состоит из трёх компонентов: прибора, мобильного приложения и веб-сервиса Himo Hub.

```
                                                          Браузер
                                                             │ HTTPS
                                                             ▼
┌────────────┐   BLE    ┌──────────────────┐  HTTPS   ┌──────────────────┐
│   Прибор   │ ───────► │    Мобильное     │ ───────► │     Himo Hub     │
│ (отложен)  │   JSON   │    приложение    │   REST   │  API + веб (SPA) │
└────────────┘          └────────┬─────────┘          └────────┬─────────┘
                                 │ HTTPS                       │
                                 ▼                             ▼
                        ┌──────────────────┐          ┌──────────────────┐
                        │  ИИ-комментарии  │          │    PostgreSQL    │
                        │   (API Z.ai)     │          └──────────────────┘
                        └──────────────────┘
```

| Компонент            | Что делает                                                                                         | Состояние                                                                |
| -------------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Прибор               | Измеряет целостность, CMRR и АЧХ кабеля, передаёт результаты в приложение по BLE                   | Реализация отложена ([ADR-013](../adr/013-device-postponed.md))          |
| Мобильное приложение | Тестирование, Health Score, паспорт кабеля, локальная история, ИИ-комментарии, синхронизация с Hub | Работает на mock-данных прибора                                          |
| Himo Hub             | Команды, общая история кабелей, синхронизация с приложением, веб-интерфейс                         | Требования, стек, модель данных и контракт API определены, кода пока нет |

Принципы:

- **Приложение автономно.** Тестирование и история не зависят от сети и от доступности Hub — приложение копит тесты и выгружает их позже.
- **Hub не общается с прибором.** Результаты измерений попадают в Hub только через приложение.
- **Оценки считает приложение.** Вердикты и Health Score рассчитываются в приложении; Hub хранит их как есть (HUB-5).
- **Компоненты связаны контрактами:** прибор и приложение — [BLE-протоколом](device/ble-protocol.md), приложение и веб с Hub — спецификацией OpenAPI (`contracts/openapi.yaml`).

```
┌─────────────────────────────────────────────────────────────────┐
│         Аппаратный модуль                                       │
│                                                                 │
│  Jack TS/TRS ──┐                                                │

│                │    мультиплексор        │        RGB LED       │
```

## 3. Протокол BLE

Прибор передаёт результаты через BLE GATT как JSON-пакеты. Одна служба, две характеристики: CMD (приложение → прибор) и DATA (прибор → приложение, Notify).

Полная спецификация — **[device/ble-protocol.md](device/ble-protocol.md)**. Протокол остаётся контрактом для будущей прошивки; изменения — по его правилам версионирования.

### 4.1 Схема локальной базы данных

Пять таблиц; результаты трёх тестов хранятся в отдельных таблицах, чтобы запросы по типу теста не требовали разбора JSON.

> Ниже — целевая схема с идентификаторами UUIDv7. В коде приложения пока целочисленные `id` (`INTEGER PRIMARY KEY AUTOINCREMENT`); переход — вместе с синхронизацией с Hub (APP-7).

```sql
CREATE TABLE cables (
    id          TEXT     PRIMARY KEY,  -- UUIDv7, генерируется приложением
    name        TEXT     NOT NULL,
    color       TEXT     NOT NULL,  -- hex без '#', напр. '639922'
    cable_type  TEXT     NOT NULL,  -- 'jack_ts' | 'jack_trs' | 'xlr'
    created_at  INTEGER  NOT NULL,  -- unix timestamp
    note        TEXT                -- заметка к кабелю, необязательная
);

CREATE TABLE test_sessions (
    id             TEXT    PRIMARY KEY,  -- UUIDv7, генерируется приложением
    cable_id       TEXT    NOT NULL REFERENCES cables(id) ON DELETE CASCADE,
    started_at     INTEGER NOT NULL,  -- unix timestamp
    health_score   INTEGER,           -- 0–100; NULL если тест не завершён
    ble_device_id  TEXT    NOT NULL   -- MAC или UUID BLE-устройства
);

CREATE TABLE continuity_results (
    session_id   TEXT PRIMARY KEY REFERENCES test_sessions(id) ON DELETE CASCADE,
    status       TEXT NOT NULL,  -- 'ok' | 'warning' | 'open' | 'short'
    conductors   TEXT NOT NULL   -- JSON: {"pin1":{"r":0.9,"s":"ok"}, ...}
);

CREATE TABLE cmrr_results (
    session_id  TEXT PRIMARY KEY REFERENCES test_sessions(id) ON DELETE CASCADE,
    value_db    REAL NOT NULL,
    status      TEXT NOT NULL   -- 'excellent' | 'ok' | 'fail'
);

CREATE TABLE freq_response_results (
    session_id  TEXT PRIMARY KEY REFERENCES test_sessions(id) ON DELETE CASCADE,
    status      TEXT NOT NULL,  -- 'excellent' | 'ok' | 'fail'
    points      TEXT NOT NULL   -- JSON: [[freq_hz, amplitude_db], ...]
);
```

**Ключевые решения:**

- **Идентификаторы — UUIDv7, их генерирует приложение.** Так кабели и тесты можно создавать без связи с Hub, а повторная выгрузка того же объекта не создаёт дубликат (HUB-4, HUB-5, HUB-7). UUID — первичный ключ, а не дополнительная колонка: один идентификатор в приложении, в API и в Hub, без постоянного сопоставления локальных и серверных ID. Хранится строкой в каноническом виде.
- **Миграция накопленных данных.** SQLite не меняет тип первичного ключа через `ALTER TABLE`, поэтому таблицы пересоздаются с копированием данных. Метка времени в UUIDv7 берётся из `created_at` кабеля и `started_at` теста, а не из момента миграции, — тогда порядок по UUID совпадает с реальным порядком создания.
- **Состояние синхронизации** — команда кабеля в Hub, что уже выгружено, курсор изменений — добавляется в схему вместе с APP-7.
- `conductors` хранится как JSON — структура зависит от типа кабеля (2 проводника у Jack TS, 3 у XLR), жёсткая схема усложнила бы миграции без выигрыша.
- `freq_response_results.points` — JSON-массив пар `[Гц, дБ]`; при необходимости индексации по частоте можно вынести в отдельную таблицу.
- `ON DELETE CASCADE` — удаление кабеля удаляет весь журнал тестов.
- `health_score` кэширует результат взвешенной формулы; пересчитывается при изменении результатов; NULL пока тесты не завершены.

## 5. ИИ-комментарии

К результатам тестов приложение и веб показывают комментарии на естественном языке. Их формирует языковая модель **GLM-4.7-Flash** через OpenAI-совместимый API Z.ai.

- **Модель объясняет, а не оценивает.** Вердикты и Health Score уже рассчитаны приложением по порогам; модель получает их вместе с измерениями и объясняет, что они значат для пользователя.
- **Сейчас** приложение обращается к API Z.ai напрямую.
- **Далее — прокси в Hub**, ключ API только на сервере:

```
Приложение ──результаты теста──► POST /api/v1/insights ──► кэш (PostgreSQL) ──нет──► модель (Z.ai)
                                         │                       │
Веб: страница теста ─────────────────────┘                       └──► тест в Hub ссылается
                                                                      на комментарий
```

  - Эндпоинт без учётной записи и токена: комментарии доступны и тем, кто пользуется только приложением.
  - Кэш по результатам: повторный запрос с теми же результатами возвращает тот же комментарий без обращения к модели, поэтому приложение и веб показывают одинаковый текст.
  - При выгрузке теста или первом его просмотре в вебе комментарий привязывается к тесту и дальше не меняется.
  - Защита ключа — ограничение частоты запросов по IP и общий дневной лимит обращений к модели. Промпт — в `hub/prompts/insight.ru.md`.

Выбор модели и отказ от комментариев на правилах — ADR об ИИ-комментариях (YG-46), он заменяет [ADR-004](../adr/004-insight-generator.md). Устройство прокси — [ADR-018](../adr/018-insights-proxy.md).

## 6. Himo Hub

Веб-сервис совместного ведения истории тестирования кабелей. Требования → [hub/requirements.md](hub/requirements.md)

| Часть            | Технологии                                                                       |
| ---------------- | -------------------------------------------------------------------------------- |
| API-сервер       | Go, gin; контракт `contracts/openapi.yaml`, серверный код по нему — oapi-codegen |
| Веб-интерфейс    | SvelteKit (SPA), отдаётся тем же сервером                                        |
| Хранилище        | PostgreSQL; доступ — pgx и sqlc; миграции — goose                                |
| Документация API | `/docs` по `openapi.yaml` (Scalar)                                               |
| Наблюдаемость    | Логи `log/slog` в JSON с `request_id`; `GET /health` с проверкой БД              |

Обоснование стека — [ADR-015](../adr/015-hub-stack.md).

Основные потоки:

- **Синхронизация.** Приложение выгружает новые кабели, правки и тесты одним пакетом (`POST /api/v1/sync/push`) — повтор с тем же UUIDv7 не создаёт дубликат; получает каталог кабелей команды; загружает кабель с полной историей, дальше — только изменения по курсору (`POST /api/v1/sync/pull`). Протокол — [hub/sync.md](hub/sync.md), соглашения API — [ADR-023](../adr/023-hub-api-conventions.md).
- **Веб-интерфейс.** Просмотр и сравнение тестов, управление кабелями и командой. Кабели и тесты создаются только в приложении.
- **Вход.** По нику и паролю; в вебе — также через Telegram Login Widget ([ADR-016](../adr/016-telegram-login-widget.md)). Сеанс — один непрозрачный токен: в вебе в cookie, в приложении в заголовке `Authorization` ([ADR-022](../adr/022-hub-authentication.md)).
- **Прокси ИИ** — [раздел 5](#5-ии-комментарии).

Модель данных → [hub/data-model.md](hub/data-model.md), обоснование ключевых решений — [ADR-021](../adr/021-hub-data-model.md). Контракт API → [contracts/openapi.yaml](../../contracts/openapi.yaml).

## 7. Развёртывание

```
                         Интернет
                            │ HTTPS
                            ▼
                ┌───────────────────────┐
                │ nginx на хосте        │  TLS (Let's Encrypt)
                └─────┬───────────┬─────┘
      himo.hakoniwa.ru│           │dev.himo.hakoniwa.ru
                      ▼           ▼
                ┌──────────┐ ┌──────────┐
                │ hub-prod │ │ hub-dev  │  контейнеры, Docker Compose
                └────┬─────┘ └────┬─────┘
                     ▼            ▼
                ┌───────────────────────┐
                │ PostgreSQL на хосте   │  базы himo_prod и himo_dev
                └───────────────────────┘
```

Всё работает на одном домашнем сервере вместе с Gitea, runner'ом Gitea Actions и реестром образов Gitea:

- **PR** — проверки (линтер, форматирование, тесты с PostgreSQL, покрытие) и сборка образа `sha-<коммит>`;
- **слияние в `dev`** — образ разворачивается на dev;
- **тег `hub/vX.Y.Z`** — образ `X.Y.Z` разворачивается на prod.

Подробности, риски открытого dev-окружения и ограничения — [ADR-017](../adr/017-deployment.md).
