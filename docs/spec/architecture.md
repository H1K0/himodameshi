## 1. Общая схема

```
┌─────────────────────────────────────────────────────────────────┐
│         Аппаратный модуль                                       │
│                                                                 │
│  Jack TS/TRS ──┐                                                │
│  XLR M/F    ───┼──► CD74HC4067  ──► ESP32-S3 ──► OLED 128×64    │
│                │    мультиплексор        │        RGB LED       │
│  AD9833 DDS ◄──┘                         │                      │
│  (генератор)                             │ BLE                  │
│  MCP3208 АЦП                             │                      │
│  INA128P усилитель                       ▼                      │
│  TP4056 + 18650                  Мобильное приложение           │
│  USB-C (зарядка + отладка)         Flutter (iOS/Android)        │
└─────────────────────────────────────────────────────────────────┘
```

Устройство проводит измерения автономно, результаты передаются на смартфон по BLE в виде JSON-пакетов. Приложение хранит историю локально и не требует интернета для основных функций.

## 3. Протокол передачи данных

Прошивка передаёт результаты через BLE GATT как JSON-пакет. Одна служба, две характеристики: CMD (app → устройство) и DATA (устройство → app, Notify).

Полная спецификация протокола — в **[docs/spec/ble-protocol.md](ble-protocol.md)**. Изменения в протоколе — через отдельный ADR и смену поля `pv`.

## 4. Программный стек

### 4.1 Мобильное приложение

Архитектура — Clean Architecture с разделением на три слоя: data, domain, presentation.

| Слой / назначение         | Технологии                               |
| ------------------------- | ---------------------------------------- |
| UI-фреймворк              | Flutter (Dart)                           |

| Облако (V2)               | Firebase или Supabase                    |

### 4.2 InsightGenerator

Компонент, формирующий комментарии к результатам тестов на естественном языке. Реализован как интерфейс: результат теста на входе, текстовый комментарий на выходе.

В MVP — реализация на правилах и шаблонах с подстановкой значений и вариативными формулировками. Работает офлайн, без задержки. В версии 2 реализацию можно подменить на облачный LLM-слой (Premium-фича) без изменений в UI.

Подробнее — [ADR-004](../adr/004-insight-generator.md).

### 4.3 Схема локальной базы данных

Реализована через drift ORM (SQLite). Четыре таблицы; результаты трёх тестов хранятся в отдельных таблицах, чтобы запросы по типу теста не требовали разбора JSON.

```sql
CREATE TABLE cables (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    name        TEXT     NOT NULL,
    color       TEXT     NOT NULL,  -- hex без '#', напр. '639922'
    photo_path  TEXT,               -- NULL если фото не добавлено
    cable_type  TEXT     NOT NULL,  -- 'jack_ts' | 'jack_trs' | 'xlr'
    created_at  INTEGER  NOT NULL   -- unix timestamp
);

CREATE TABLE test_sessions (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    cable_id       INTEGER NOT NULL REFERENCES cables(id) ON DELETE CASCADE,
    started_at     INTEGER NOT NULL,  -- unix timestamp
    health_score   INTEGER,           -- 0–100; NULL если тест не завершён
    ble_device_id  TEXT    NOT NULL   -- MAC или UUID BLE-устройства
);

CREATE TABLE continuity_results (
    session_id   INTEGER PRIMARY KEY REFERENCES test_sessions(id) ON DELETE CASCADE,
    status       TEXT NOT NULL,  -- 'ok' | 'warning' | 'open' | 'short'
    conductors   TEXT NOT NULL   -- JSON: {"pin1":{"r":0.9,"s":"ok"}, ...}
);

CREATE TABLE cmrr_results (
    session_id  INTEGER PRIMARY KEY REFERENCES test_sessions(id) ON DELETE CASCADE,
    value_db    REAL NOT NULL,
    status      TEXT NOT NULL   -- 'excellent' | 'ok' | 'fail'
);

CREATE TABLE freq_response_results (
    session_id  INTEGER PRIMARY KEY REFERENCES test_sessions(id) ON DELETE CASCADE,
    status      TEXT NOT NULL,  -- 'excellent' | 'ok' | 'fail'
    points      TEXT NOT NULL   -- JSON: [[freq_hz, amplitude_db], ...]
);
```

**Ключевые решения:**

- `conductors` хранится как JSON — структура зависит от типа кабеля (2 проводника у Jack TS, 3 у XLR), жёсткая схема усложнила бы миграции без выигрыша.
- `freq_response_results.points` — JSON-массив пар `[Гц, дБ]`; в MVP достаточно, в версии 2 можно вынести в отдельную таблицу при необходимости индексации по частоте.
- `ON DELETE CASCADE` — удаление кабеля удаляет весь журнал тестов.
- `health_score` кэширует результат взвешенной формулы (см. раздел 4.4); пересчитывается при изменении результатов; NULL пока тесты не завершены.

### 4.4 Алгоритм Health Score

Health Score (0–100) — взвешенная сумма трёх суб-скоров, каждый из которых опирается на **численные значения**, а не только на статусы. Статусы (`ok`, `excellent` и т. д.) остаются в таблицах результатов — для отображения в UI; Health Score — синтетический показатель для быстрой общей оценки.

#### Катастрофические условия

Если у **любого** проводника статус `open` или `short` → $\text{health\_score} = 0$ без дальнейших вычислений.

#### Суб-скор целостности $S_c$ (0–100)

Для каждого проводника $i$ с измеренным сопротивлением $r_i$ (Ω):

$$s_i = \begin{cases} 100 - 4\,r_i & r_i < 5\,\Omega \quad\text{(зона ok)} \\ \max\!\left(0,\; 80 - \dfrac{8}{9}(r_i - 5)\right) & r_i \geq 5\,\Omega \quad\text{(зона warning и выше)} \end{cases}$$

$$S_c = \frac{1}{n}\sum_{i=1}^{n} s_i$$

Граничные точки: $r = 0\,\Omega \Rightarrow s = 100$; $r = 5\,\Omega \Rightarrow s = 80$; $r = 50\,\Omega \Rightarrow s = 40$; $r \geq 95\,\Omega \Rightarrow s = 0$.  
Пороги из [continuity-requirements.md](continuity-requirements.md): ok $< 5\,\Omega$, warning $5\text{–}50\,\Omega$.

#### Суб-скор CMRR $S_m$ (0–100) — для XLR и Jack TRS

Применяется к балансным кабелям (`xlr`, `jack_trs`). Jack TS — небалансный, CMRR не измеряется.

$$S_m = \begin{cases} 0 & d < 20 \\ 2\,(d - 20) & 20 \leq d < 60 \\ \min\!\left(100,\; 80 + (d - 60)\right) & d \geq 60 \end{cases}$$

где $d$ — измеренное значение CMRR в дБ.

| $d$ (дБ)  | $S_m$ | Статус по ФТТ          |
| --------- | ----- | ---------------------- |
| $< 20$    | 0     | fail                   |
| $40$      | 40    | граница fail / ok      |
| $60$      | 80    | граница ok / excellent |
| $\geq 80$ | 100   | excellent              |

Пороги из [cmrr-requirements.md](cmrr-requirements.md): fail $< 40\,\text{дБ}$, ok $40\text{–}60\,\text{дБ}$, excellent $> 60\,\text{дБ}$.

#### Суб-скор АЧХ $S_f$ (0–100)

Если хотя бы одна точка содержит сентинел $-99.0$ (пропадание сигнала) → $S_f = 0$.

Значения $v_i$ — отклонение в дБ от опорного уровня 1 кГц; $v_{16} \equiv 0.0$ по определению ([BLE-протокол §4](ble-protocol.md)).

**Зоны частот.** Из 30 точек (10 Гц – 40 кГц) формула использует две зоны с разной логикой:

- **20 Гц – 20 кГц** — основной аудиодиапазон; пороги ФТТ (±1 / ±3 дБ) заданы именно здесь.
- **20 кГц – 40 кГц** — сверхзвуковая зона; небольшой завал (≤ 3 дБ) естествен для кабелей длиной > 5 м, но значительный (> 3 дБ) указывает на раннюю ёмкостную деградацию.
- **10 Гц – 20 Гц** — точки измеряются и передаются в приложение для отображения полного графика и комментариев InsightGenerator, но **не** участвуют в расчёте score: пороги ФТТ на этот диапазон не распространяются.

**Основной скор (аудиодиапазон):**

$$\text{peak} = \max_i |v_i|, \qquad \sigma = \sqrt{\frac{1}{n}\sum_{i=1}^{n} v_i^2} \qquad \text{для точек } 20\,\text{Гц} \leq f \leq 20\,\text{кГц}$$

$$S_{f,\text{audio}} = \max\!\left(0,\; 100 - 14 \cdot \text{peak} - 6 \cdot \sigma\right)$$

$\text{peak}$ наказывает за локальный выброс, $\sigma$ — за систематический завал. При равномерном отклонении ($\sigma = \text{peak}$) формула даёт точные граничные значения.

**ВЧ-штраф (сверхзвуковая зона):**

$$\text{peak}_{hf} = \max_i |v_i| \qquad \text{для точек } 20\,\text{кГц} < f \leq 40\,\text{кГц}$$

$$\text{penalty}_{hf} = \max\!\left(0,\; (\text{peak}_{hf} - 3) \times 4\right)$$

**Итоговый суб-скор:**

$$S_f = \max\!\left(0,\; S_{f,\text{audio}} - \text{penalty}_{hf}\right)$$

| Профиль АЧХ                                | peak  | $\sigma$ | $\text{peak}_{hf}$ | $S_f$ | Статус по ФТТ |
| ------------------------------------------ | ----- | -------- | ------------------ | ----- | ------------- |
| Идеальная                                  | 0 дБ  | 0 дБ     | 0 дБ               | 100   | —             |
| Excellent-граница (равномерн.)             | ±1 дБ | 1 дБ     | 0 дБ               | 80    | excellent     |
| Ok-граница (равномерн.)                    | ±3 дБ | 3 дБ     | 0 дБ               | 40    | ok            |
| Один ВЧ-выброс ±6 дБ (норм. аудио)         | 0 дБ  | 0 дБ     | 6 дБ               | 88    | excellent     |
| Сильная ВЧ-деградация ±10 дБ (норм. аудио) | 0 дБ  | 0 дБ     | 10 дБ              | 72    | ok            |
| Fail (равномерн.)                          | ±5 дБ | 5 дБ     | 0 дБ               | 0     | fail          |

Пороги из [freq-response-requirements.md](freq-response-requirements.md): excellent $\leq \pm1\,\text{дБ}$, ok $\leq \pm3\,\text{дБ}$ в диапазоне 20 Гц – 20 кГц.

#### Итоговая формула и веса по типу кабеля

$$\text{health\_score} = \operatorname{round}(w_c \cdot S_c + w_m \cdot S_m + w_f \cdot S_f)$$

| Тип кабеля | $w_c$ | $w_m$ | $w_f$ | Тип тракта  |
| ---------- | ----- | ----- | ----- | ----------- |
| `xlr`      | 0.35  | 0.35  | 0.30  | балансный   |
| `jack_trs` | 0.35  | 0.35  | 0.30  | балансный   |
| `jack_ts`  | 0.60  | —     | 0.40  | небалансный |

Для `jack_ts` CMRR не измеряется; $w_c + w_f = 1.0$. Целостность получает больший вес, так как для небалансного кабеля именно она определяет пригодность к работе.

## 5. Стратегия разработки

Порядок разработки — software-first:

1. **Flutter-приложение с mock-данными** — полноценный UX без реального устройства. Mock-слой изолирует UI от транспорта и подменяется реальным BLE-соединением без изменений в бизнес-логике.
2. **Освоение hardware по модулям** — LED → AD9833 (генератор) → MCP3208 (АЦП, SPI совместно с AD9833) → INA128P (усилитель) → интеграция на макетной плате.
3. **Интеграция** — после валидации UX приложения, под уже зафиксированный JSON-протокол.

Дорожная карта и поэтапный план → **[roadmap.md](roadmap.md)** · Триггеры сокращения и расширения объёма → **[scope-triggers.md](scope-triggers.md)**
