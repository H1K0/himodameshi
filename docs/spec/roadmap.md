- [ ] **Экран тестирования: прогресс в реальном времени** — поток пакетов `status` управляет прогресс-баром; переходы состояний: idle → testing → done/error
- [ ] **Экран тестирования: отображение результатов** — рендер `result:continuity` (Ω по проводникам + статус), `result:cmrr` (дБ + бейдж), `result:freq_response` (30-точечный столбчатый или линейный график + статус)

**Неделя 3 (29 апр – 5 мая)**

- [ ] **Доменная функция Health Score** — чистая Dart-функция: принимает 1–3 объекта `TestResult`, возвращает enum `HealthScore` (`excellent`/`ok`/`fail`). Без зависимостей от BLE, пригодна для unit-тестирования
- [ ] **Экран «Паспорт кабеля»** — полная история тестов одного кабеля из mock-данных. Раскрываемые карточки по каждой тестовой сессии. Временная шкала Health Score
- [ ] **Экран «Коллекция»** — список кабелей с фильтром по статусу здоровья, текстовый поиск по имени
- [ ] **Экран «Настройки»** — метка имени устройства, «Забыть устройство» (заглушка), версия приложения. Статичный пока
- [ ] **Схема БД drift** — таблицы: `cables(id, name, color_label, photo_path, created_at)`, `test_sessions(id, cable_id, ts, cable_type)`, `test_results(id, session_id, test_type, json_payload)`. Миграция 001 применяется при запуске

_На этом этапе нет зависимостей от прошивки — mock-провайдер обеспечивает все данные._

#### Направление «Железо + Прошивка» — Влад + Ваня

**Неделя 2 (22–28 апр)** — железо прибывает ~22 апр

- [ ] **Проверить доставку BOM** — сверить все 8 компонентов с заказом, проверить шины питания мультиметром
- [ ] **AD9833 SPI** — подключить к ESP32-S3, сгенерировать синус 1 кГц, проверить мультиметром в режиме AC (или через обратную связь с ADS1115)
- [ ] **ADS1115 I2C** — подключить к шине I2C, считать напряжение с делителя. Подтвердить точность ±1%
- [ ] **Мультиплексор CD74HC4067** — подключить S0–S3 к GPIO, переключаться между 4 каналами под управлением прошивки, проверить маршрутизацию сигнала мультиметром

**Неделя 3 (29 апр – 5 мая)**

- [ ] **Сигнальный тракт INA128P** — дифференциальный вход от выхода мультиплексора, несимметричный выход на ADS1115. Проверить усиление и смещение
- [ ] **Ядро измерения целостности** — скетч для ESP32-S3 (без BLE): подать известное напряжение через канал мультиплексора → считать через ADS1115 → вычислить R (Ом) → вывести в Serial. Тестировать с резисторами 1 Ом, 10 Ом, обрыв
- [ ] **Заглушка BLE GATT-сервера** — NimBLE: сервис + характеристики CMD + DATA рекламируются. Телефон обнаруживает и подключается
- [ ] **Парсер CMD** — ArduinoJson десериализует `start_test` и `cancel`. Логирование в Serial
- [ ] **Автомат состояний + эмиттер заглушки** — состояния: idle → testing → done. Захардкоженные JSON-пакеты результатов отправляются через Notify. _Приложение может подключаться и отображать результаты без реальных измерений_ — это позволяет тестировать интеграцию приложения с прошивкой на Этапе 2

**Критерий готовности Этапа 1:** Приложение показывает все 5 экранов с mock-данными, логика Health Score работает, схема БД существует. Заглушка BLE прошивки подключается к телефону и отправляет фиктивные пакеты. Ядро измерения целостности выдаёт реальные значения Ом в Serial.

#### Направление «Прошивка + Железо» — Влад + Ваня

**Неделя 4 (6–10 мая) — Целостность + CMRR**

- [ ] **Полная реализация теста целостности** — все 3 типа кабелей: `jack_ts` (tip + sleeve), `jack_trs` (tip + ring + sleeve), `xlr` (pin1 + pin2 + pin3). Правильные граничные значения: обрыв = 99999.0, КЗ = 0.01
- [ ] **Отправка JSON `result:continuity`** — реальные значения через BLE Notify
- [ ] **Инжекция сигнала для CMRR** — AD9833 выдаёт синус 1 кГц одновременно на оба дифференциальных входа INA128P. ADS1115 считывает амплитуду выходного сигнала
- [ ] **Расчёт CMRR** — `20 × log10(V_вх / V_вых)`. Сначала откалибровать V_вх
- [ ] **Отправка JSON `result:cmrr`** — реальное значение в дБ через BLE Notify

**Неделя 5 (13–19 мая) — АЧХ**

- [ ] **Цикл свипа частот** — перебрать все 30 значений из нормативной таблицы частот. Для каждой: установить частоту AD9833 → подождать стабилизации сигнала → считать амплитуду через ADS1115
- [ ] **Нормировка** — разделить все амплитуды на амплитуду при индексе 16 (1 кГц), перевести в дБ. `v[16]` всегда должен быть ровно `0.0`
- [ ] **Обновления прогресса** — отправлять `status: testing, test: "freq_response", progress: i/30.0` после каждого шага по частоте
- [ ] **Отправка JSON `result:freq_response`** — реальный массив `v[]` из 30 значений float

**Точка синхронизации 1 — 6 мая:** BLE-клиент приложения ↔ заглушка BLE прошивки. Отправить `start_test{xlr}` из приложения, получить фиктивные пакеты результатов, приложение их отображает на экране тестирования. Требование: это должно работать до того, как прошивка реализует реальные алгоритмы.

**Точка синхронизации 2 — 14 мая:** Первые реальные данные через BLE. Тест целостности на реальном XLR-кабеле → реальные значения Ом видны в приложении. Присутствуют все три участника.

**Критерий готовности Этапа 2:** Все 3 алгоритма измерений реализованы в прошивке. Приложение использует реальный BLE (переключатель включён), сохраняет результаты в БД, показывает комментарии InsightGenerator.

## Вариант А — Быстрый прототип

**Сокращения области относительно Б:**

- Архитектура приложения: плоская — без слоёв Clean Architecture. Класс `BleService` + Riverpod `StateNotifier`. Достаточно для демо, достаточно для дальнейшего расширения
- Отказ от InsightGenerator — хардкод 3 меток исхода («Отлично / Норм / Плохо»)
- Отказ от экспорта PDF и QR-кода
- Экран «Коллекция»: заглушка («Скоро будет»)
- Прошивка: реализовать только Целостность + CMRR. АЧХ отправляет захардкоженный пакет-заглушку «excellent»
- Железо: только путь XLR для демо (пропустить каналы мультиплексора для Jack — вдвое снижает сложность схемы)

**Влияние на расписание:** Этап 2 заканчивается ~10 мая. Этап 3 начинается 11 мая с запасом 17 дней.

| Плюсы                                                      | Минусы                                                                           |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Готово к демо ~20 мая, запас 8 дней                        | Нет экспорта PDF, нет АЧХ — спецификация не выполнена                            |
| Простой код — легче для начинающих с Flutter               | Health Score на основе только Целостности + CMRR: вводящая в заблуждение метрика |
| Меньше каналов мультиплексора — ниже риск аналоговой схемы | Кодовая база требует значительного рефакторинга перед выходом v1.0               |
| Меньше давления на Влада по освоению аналогового CMRR      | Нельзя тестировать кабели Jack вообще                                            |

**Подходит для:** демо инвестору/партнёру, где важнее история «устройство → телефон по BLE», чем полнота тестов.

## Вариант Б — Сбалансированный (рекомендуется)

Поэтапный план выше. Полное соответствие спецификации, прагматичная реализация. Скелет Clean Architecture без избыточной инженерии.

**Ключевые решения, делающие его реалистичным:**

- Заглушка BLE прошивки (Этап 1, Неделя 3) разделяет разработку приложения и прошивки. Приложение может быть завершено на 100% до появления реальных алгоритмов прошивки
- Ваня гибко переключается: поддержка железа на Неделях 2–3, переход на поддержку приложения на Неделях 4–5 если прошивка опережает
- InsightGenerator — чисто доменная логика, без зависимости от железа, можно разрабатывать и тестировать изолированно в любое время

| Плюсы                                                                          | Минусы                                                                                     |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| Все MVP-фичи по спецификации                                                   | Напряжённо — 43 дня с двумя начинающими на своих стеках                                    |
| Clean Architecture упрощает онбординг при разработке v2 и добавление новых фич | Алгоритмы прошивки CMRR + АЧХ требуют точной аналоговой калибровки                         |
| InsightGenerator + экспорт PDF добавляют реальную ценность продукта в демо     | Влад должен освоить PlatformIO, NimBLE, ArduinoJson, I2C/SPI параллельно со сборкой железа |
| Паттерн заглушки прошивки: приложение никогда не заблокировано железом         |                                                                                            |

**Запасной план при рисках:** Если алгоритмы прошивки запаздывают после 19 мая — сдать заглушку прошивки (захардкоженные реалистичные значения) + полностью готовое приложение для демо. Приложение само по себе на 100% соответствует спецификации и демонстрирует полный UX.

## Вариант В — Упор на качество архитектуры

**Дополнительная работа сверх Б:**

- Строгое соблюдение Clean Architecture: интерфейсы репозиториев, классы use-case, внедрение зависимостей через Riverpod override
- Unit-тесты для всех доменных классов (InsightGenerator, HealthScore, парсер BLE-пакетов): `flutter test`
- Widget-тесты для экранов «Тестирование» и «Паспорт кабеля»
- GitHub Actions CI: `flutter test` + `flutter analyze` + `pio run --environment esp32s3` на каждый PR в `dev`
- Политика код-ревью: без approval не мержить
- 5–8 новых ADR по решениям реализации слоя приложения

| Плюсы                                                        | Минусы                                                                                      |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| Кодовая база уровня портфолио/инвестора                      | +1–2 недели накладных расходов на 43-дневный таймлайн                                       |
| Тесты ловят регрессии при BLE-интеграции, ломающей mock-путь | Начинающие Flutter-разработчики тратят пропорционально больше времени на тесты, чем на фичи |
| CI автоматически обеспечивает соблюдение соглашений          | Высокий риск не успеть с MVP к 28 мая                                                       |
| Сильная позиция для open-source выпуска или роста команды    |                                                                                             |

**Подходит для:** мягкого дедлайна, или после успешного демо Варианта А/Б, когда команда решает довести до production-качества перед более широким выходом.
