## Контекст

| Участник | Роль                          | Сильные стороны           | Основной риск                                |

| Влад     | PM, лид по прошивке           | Python/Go/C               | Нет опыта в embedded                         |

**Жёсткий дедлайн:** 28 мая — 43 дня от сегодня (15 апр).

**Критический путь:** заказ железа → доставка → макетная плата → ядро измерений → BLE прошивки → интеграция BLE в приложение → сквозной демо. Всё остальное выполняется параллельно.

**Архитектурное ограничение:** Mock BLE-провайдер и реальный BLE-провайдер реализуют один и тот же интерфейс `BleDataSource`. Это позволяет приложению собираться и тестироваться независимо от прошивки на всём протяжении разработки.

**Объём MVP по ФТТ:**

- Три теста: Целостность, CMRR, АЧХ передачи сигнала (10 Гц – 40 кГц)
- Три типа кабелей: Jack TS, Jack TRS, XLR симметричный
- Идентификация кабеля: имя + цветная метка + фото
- База кабелей с историей, паспорт кабеля, экспорт PDF через системный share sheet
- InsightGenerator — комментарии к результатам тестов на естественном языке
- Health Score — итоговая цветовая оценка

#### Направление «Приложение» — Валера

**Неделя 2 (22–28 апр)**

- [ ] **Экран тестирования: прогресс в реальном времени** — поток пакетов `status` управляет прогресс-баром; переходы состояний: idle → testing → done/error
- [ ] **Экран тестирования: отображение результатов** — рендер `result:continuity` (Ω по проводникам + статус), `result:cmrr` (дБ + бейдж), `result:freq_response` (массив амплитуд по 30 точкам — линейный или столбчатый график + статус)

**Неделя 3 (29 апр – 5 мая)**

- [ ] **Доменная функция Health Score** — чистая Dart-функция: принимает 1–3 объекта `TestResult`, возвращает enum `HealthScore` (`excellent` / `ok` / `fail`). Без зависимостей от BLE, пригодна для unit-тестирования
- [ ] **Идентификация кабеля (ФТ-2.4)** — модель `Cable` с полями `id`, `name` (свободный текст), `color_label` (выбор из палитры), `photo_path` (снимок камерой). Экран создания нового кабеля при первом тесте
- [ ] **Экран «Паспорт кабеля»** — полная история тестов одного кабеля из mock-данных. Раскрываемые карточки по каждой тестовой сессии. Временная шкала Health Score
- [ ] **Экран «Коллекция»** — список кабелей с фильтром по статусу здоровья, текстовый поиск по имени и цвету (ФТ-2.5)
- [ ] **Экран «Настройки»** — метка имени устройства, «Забыть устройство» (заглушка), версия приложения. Статичный пока
- [ ] **Подключить drift, схема БД** — таблицы: `cables(id, name, color_label, photo_path, created_at)`, `test_sessions(id, cable_id, ts, cable_type)`, `test_results(id, session_id, test_type, json_payload)`. Миграция 001 применяется при запуске

_На этом этапе у Валеры нет зависимостей от прошивки — mock-провайдер обеспечивает все данные._

- [ ] **Заглушка BLE GATT-сервера** — NimBLE: сервис + характеристики CMD + DATA рекламируются. Телефон обнаруживает и подключается

**Неделя 3 (29 апр – 5 мая)**

### Этап 2 — Реальные измерения + BLE-клиент (6–19 мая)

#### Направление «Приложение» — Валера

**Неделя 4 (6–12 мая)**

- [ ] **Подключить flutter_blue_plus** — сканирование по UUID сервиса, подключение, запрос MTU 247 (минимум 100 — отключение с ошибкой если меньше)
- [ ] **Реальный BLE-провайдер** — тот же интерфейс `BleDataSource`, что использовался mock-ом; теперь реализован через flutter_blue_plus. Подмена через Riverpod override (без изменений в слое представления)
- [ ] **Запись в характеристику CMD** — отправить `start_test` и `cancel`. Тестировать против заглушки BLE прошивки
- [ ] **Подписка на DATA** — получать Notify из характеристики DATA, десериализовать JSON, маршрутизировать в состояние Riverpod
- [ ] **Переключатель mock/real в Настройках** — секция отладки для переключения между mock и реальным BLE. Поддерживает mock работоспособным на протяжении разработки прошивки

**Неделя 5 (13–19 мая)**

- [ ] **Сохранение результатов тестов в БД** — записывать `TestSession` + `TestResult` в drift при получении `status: done`. Загружать историю на экране «Паспорт кабеля»
- [ ] **InsightGenerator (ADR-004)** — реализация на правилах: ≥5 шаблонов комментариев на тип теста × 3 исхода = ≥45 строк. Вход: объект `TestResult` → выход: `String`. Без сети, без зависимости от BLE. Оформлен как интерфейс, чтобы в V2 подключить облачный LLM-слой без изменения UI
- [ ] **Подключение InsightGenerator** — показывать сгенерированный текст комментария в карточках результатов на экране «Паспорт кабеля»

#### Направление «Прошивка + Железо» — Влад + Ваня

**Неделя 4 (6–12 мая) — Целостность + CMRR**

- [ ] **Полная реализация теста целостности** — все 3 типа кабелей: `jack_ts` (tip + sleeve), `jack_trs` (tip + ring + sleeve), `xlr` (pin1 + pin2 + pin3). Корректные граничные значения по ФТ-2.2: ОК (<5 Ом), Предупреждение (5–50 Ом), Обрыв = 99999.0, КЗ = 0.01
- [ ] **Отправка JSON `result:continuity`** — реальные значения через BLE Notify
- [ ] **Инжекция сигнала для CMRR** — AD9833 выдаёт синус 1 кГц одновременно на оба дифференциальных входа INA128P. ADS1115 считывает амплитуду выходного сигнала. **Риск:** см. отдельный документ `cmrr-requirements.md`
- [ ] **Расчёт CMRR** — `20 × log10(V_вх / V_вых)`. Сначала откалибровать V_вх и убедиться, что рассогласование импедансов источника минимально
- [ ] **Отправка JSON `result:cmrr`** — реальное значение в дБ через BLE Notify. Пороги по ФТ-2.2: Отлично (>60 дБ) / Удовл. (40–60) / Плохо (<40)

**Неделя 5 (13–19 мая) — АЧХ передачи сигнала**

- [ ] **Цикл свипа частот** — перебрать 30 значений в диапазоне 10 Гц – 40 кГц по логарифмической шкале. Для каждой частоты: установить AD9833 → подождать стабилизации сигнала → считать амплитуду через ADS1115
- [ ] **Нормировка** — разделить все амплитуды на амплитуду в опорной точке (1 кГц), перевести в дБ. Опорное значение всегда `0.0` дБ
- [ ] **Обновления прогресса** — отправлять `status: testing, test: "freq_response", progress: i/30.0` после каждого шага по частоте
- [ ] **Отправка JSON `result:freq_response`** — реальный массив `v[]` из 30 значений float + вердикт (отлично / удовл. / плохо) по отклонению характеристики от плоской

**Точка синхронизации 1 — 6 мая:** BLE-клиент приложения ↔ заглушка BLE прошивки. Отправить `start_test{xlr}` из приложения, получить фиктивные пакеты результатов, приложение их отображает на экране тестирования. Требование: это должно работать до того, как прошивка реализует реальные алгоритмы.

**Точка синхронизации 2 — 10 мая (КЛЮЧЕВАЯ):** Ревью состояния CMRR. Если аналоговый тракт нестабилен и цифры шумят — активируется триггер из плана Б-минус (см. отдельный документ).

**Точка синхронизации 3 — 14 мая:** Первые реальные данные через BLE. Тест целостности на реальном XLR-кабеле → реальные значения Ом видны в приложении. Присутствуют все три участника.

**Критерий готовности Этапа 2:** Все 3 алгоритма измерений реализованы в прошивке (или принят триггер на заглушку третьего). Приложение использует реальный BLE, сохраняет результаты в БД, показывает комментарии InsightGenerator.

## Риск-карта

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Задержка/брак доставки железа | Средняя | Высокое | Дубли критичных компонентов в Этапе 0 |
| CMRR не даёт стабильных цифр | **Высокая** | Высокое | Триггер 10 мая на упрощение объёма |
| Свип АЧХ нестабилен (шум, нелинейность тракта) | Средняя | Среднее | Нормировка к опорной точке, ограничение МVP-набора частот при необходимости |
| Потери BLE-пакетов, MTU-проблемы на конкретных Android | Средняя | Среднее | Буфер в Этапе 3, переключатель mock/real для сравнения |
| Валера буксует на связке Riverpod+drift | Средняя | Среднее | Поэтапное введение зависимостей, drift не раньше Недели 3 |
| Влад перегружен координацией | Средняя | Высокое | Ваня — лид по железу, снимает с Влада часть контекста |
| Отсутствие осциллографа для отладки SPI/I2C | Низкая (если проверить в Этапе 0) | Критическое | Проверка наличия оборудования в чек-листе Этапа 0 |
