## Уровни амбиций к 28 мая

Команда работает по основному плану и продвигается так далеко, как позволяет прогресс. Минимум — это пол, не потолок. Чем больше успеем — тем лучше.

| Уровень      | Что показываем 28 мая                                                                                        |
| ------------ | ------------------------------------------------------------------------------------------------------------ |
| **Минимум**  | Mock-приложение на телефоне + симуляция в Proteus (хотя бы один тест). Показываются независимо, BLE не нужен |
| **Цель**     | Реальное устройство собрано + хотя бы один тест на настоящем кабеле + приложение подключено по BLE           |
| **Идеально** | Полный MVP по ФТТ: все три теста × все три типа кабелей, BLE, PDF-экспорт, InsightGenerator, Health Score    |

Переход между уровнями происходит органично по мере выполнения работ — никакого отдельного решения «идём на уровень выше» не требуется.

**Ключевой триггер для «Цель» и выше:** если к 3 мая Proteus показывает работающий тест целостности, железо заказывается немедленно. Доставка ~7 дней → компоненты на руках к 10–11 мая. Это открывает возможность собрать устройство и при хорошем ходе работ дойти до «Идеально» к 28 мая.

**После 28 мая:** проект продолжается без временны́х ограничений. Приоритет — качество. Всё, что не успело к 28 мая, доделывается спокойно.

**Архитектурное ограничение:** Mock BLE-провайдер и реальный BLE-провайдер реализуют один и тот же интерфейс `BleDataSource`. Приложение собирается и демонстрируется полностью независимо от прошивки на всём протяжении разработки.

**Полный объём по ФТТ (финальная цель):**

- Три теста: Целостность, CMRR, АЧХ (10 Гц – 40 кГц)
- Три типа кабелей: Jack TS, Jack TRS, XLR симметричный
- Идентификация кабеля: имя + цветная метка + фото
- База кабелей с историей, паспорт кабеля, экспорт PDF через share sheet
- InsightGenerator, Health Score

## Этап 1 — Параллельная разработка (20 апр – 3 мая)

Два направления идут полностью независимо и не блокируют друг друга.

### Направление «Приложение» — Валера

**Неделя 1 (20–26 апр)**

- [ ] Скелет Clean Architecture — `lib/data/`, `lib/domain/`, `lib/presentation/`
- [ ] Mock BLE-провайдер — Riverpod-провайдер, читающий `app/mock/ble_mock_packets.json`, отдающий `Stream<BlePacket>`. Обеспечивает весь UI до интеграции с реальным BLE
- [ ] Навигационная оболочка — нижняя панель с 5 экранами-заглушками: Dashboard, Тестирование, Паспорт, Коллекция, Настройки
- [ ] **Экран Dashboard** — индикатор BLE-соединения, список кабелей из mock, цветовой индикатор Health Score
- [ ] **Экран тестирования** — выбор Jack TS / TRS / XLR; кнопка «Старт»; прогресс-бар; отображение результатов `continuity`, `cmrr`, `freq_response`

**Неделя 2 (27 апр – 3 мая)**

- [ ] **Health Score** — чистая Dart-функция без BLE-зависимостей: `TestResult → HealthScore(excellent/ok/fail)`
- [ ] **Идентификация кабеля** — модель `Cable(id, name, color_label, photo_path)`. Экран создания нового кабеля
- [ ] **Экран «Паспорт кабеля»** — история тестов, раскрываемые карточки, временная шкала Health Score
- [ ] **Экран «Коллекция»** — фильтр по статусу здоровья, текстовый поиск
- [ ] **Экран «Настройки»** — имя устройства, «Забыть устройство» (заглушка), версия
- [ ] **Drift, схема БД** — `cables`, `test_sessions`, `test_results`. Миграция 001 при запуске

### Направление «Прошивка + Proteus» — Влад + Ваня

Ресурс: научный руководитель знаком с Proteus и готов помочь. При первых трудностях — обращаться к нему, не тратить дни на самостоятельную отладку.

**Неделя 1 (20–26 апр)**

- [ ] **Ваня: Датащиты и схема** — AD9833, MCP3208, INA128P, CD74HC4067, SSD1306. Схема подключения GPIO ESP32-S3 → каждый компонент в `hardware/`
- [ ] **Ваня: Базовая схема в Proteus** — ESP32-S3 (или совместимый), делитель напряжения на входе АЦП. Схема открывается и компилируется без ошибок
- [ ] **Влад: PlatformIO + proof-of-life** — проект компилируется и загружается в симулятор. Мигание светодиода

**Неделя 2 (27 апр – 3 мая)**

- [ ] **Ваня: Схема теста целостности в Proteus** — R_ref + переменный резистор (или набор фиксированных) для эмуляции OK / обрыв / КЗ. MCP3208 можно упростить до прямой подачи напряжения на ADC ESP32 на этом этапе
- [ ] **Влад: Ядро целостности** — `R_cable = R_ref × V_mid / (V_supply − V_mid)`. Вывод в Virtual Terminal Proteus. Три разных резистора → три разных результата
- [ ] **Влад: `ble_config.h`** — UUID из [ble-protocol.md](ble-protocol.md) как именованные константы

**Критерий готовности Этапа 1:** приложение — 5 экранов с mock, Health Score, идентификация кабелей, схема БД. Proteus — три разных резистора на входе → три разных значения в Virtual Terminal.

**Ключевое решение на 3 мая:** если Proteus показывает работающий тест целостности → железо заказывается немедленно. Это открывает путь к уровням «Цель» и «Идеально» к 28 мая. Триггеры и критерии — в [scope-triggers.md](scope-triggers.md).

## Этап 2 — Развитие (4–17 мая)

С этого этапа план разветвляется в зависимости от того, заказано ли железо.

### Направление «Приложение» — Валера

**Неделя 3 (4–10 мая)**

- [ ] **flutter_blue_plus** — сканирование по UUID сервиса, подключение, запрос MTU 247 (минимум 100 — отключение с ошибкой если меньше)
- [ ] **Реальный BLE-провайдер** — тот же интерфейс `BleDataSource`; подмена через Riverpod override
- [ ] **CMD + DATA** — запись `start_test` / `cancel`; подписка на Notify; маршрутизация в Riverpod
- [ ] **Переключатель mock/real в Настройках** — mock остаётся работоспособным

**Неделя 4 (11–17 мая)**

- [ ] **Сохранение в БД** — `TestSession` + `TestResult` при `status: done`
- [ ] **InsightGenerator** — ≥5 шаблонов × 3 типа теста × 3 исхода. Интерфейс для LLM в V2
- [ ] **Подключение InsightGenerator** к карточкам результатов

### Направление «Прошивка + Proteus» — Влад + Ваня

**Неделя 3 (4–10 мая)**

- [ ] **BLE GATT-заглушка** — NimBLE: сервис + характеристики CMD + DATA. Захардкоженные JSON-пакеты через Notify — для тестирования BLE-интеграции с приложением
- [ ] **Парсер CMD + автомат состояний** — ArduinoJson: `start_test` / `cancel`; idle → testing → done
- [ ] **Полный тест целостности в Proteus** — все 3 типа кабелей: `jack_ts`, `jack_trs`, `xlr`. Граничные значения ФТ-2.2

**Неделя 4 (11–17 мая)**

- [ ] **CMRR в Proteus** — INA128P или упрощённая модель; `20 × log10(V_вх / V_вых)`. Если компонент отсутствует — инжектировать значение переменной и показать расчёт
- [ ] **АЧХ в Proteus** — свип 30 частот (или 5–7 по триггеру). [freq-response-requirements.md](freq-response-requirements.md)

**Параллельно — если железо на руках (≈ 11 мая):**

- [ ] **Ваня: Приёмка + базовая макетка** — проверить BOM, шины питания; ESP32-S3 на breadboard
- [ ] **Ваня: AD9833 + MCP3208** — SPI, первый сигнал, проверить осциллографом / мультиметром
- [ ] **Ваня: CD74HC4067 + INA128P + разъёмы Jack/XLR** — мультиплексор, дифференциальный тракт, прозвонка

**Параллельно — если железо собрано:**

- [ ] **Влад: Первое реальное измерение** — известный резистор → MCP3208 → значение Ω в Serial
- [ ] **Влад: Тест целостности на реальном кабеле** — результат через BLE Notify в приложение
- [ ] **Влад: CMRR на реальном железе** — INA128P, инжекция 1 кГц, расчёт. [cmrr-requirements.md](cmrr-requirements.md)

**Точка синхронизации — 10 мая:** первое BLE-соединение приложения с заглушкой прошивки. `start_test{xlr}` → фиктивные пакеты → отображение в приложении.

**Критерий готовности Этапа 2 (базовый):** приложение с реальным BLE, БД, InsightGenerator. Proteus — все три теста. **Критерий «Цель»:** плюс реальное устройство с одним работающим тестом по BLE.
