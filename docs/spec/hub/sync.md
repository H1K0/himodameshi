# Синхронизация приложения с Himo Hub

Версия 0.1 · Октябрь 2026

Требования → [HUB-7](requirements.md#hub-7-синхронизация-с-приложением), [APP-7](../app/requirements.md#app-7-синхронизация-с-himo-hub) · Контракт → [openapi.yaml](../../../contracts/openapi.yaml) · Соглашения API → [ADR-023](../../adr/023-hub-api-conventions.md) · Серверная сторона → [data-model.md, раздел 5](data-model.md#5-синхронизация-с-приложением)

Как приложение обменивается с Hub кабелями и тестами: что оно хранит у себя, в каком порядке выгружает и загружает данные, как обрабатывает отказы и конфликты. Документ — общая договорённость сервера и приложения; SQL и устройство счётчика изменений на сервере описаны в модели данных.

---

## 1. Общая картина

Синхронизация необязательна: без учётной записи Hub приложение работает полностью. Когда пользователь вошёл в Hub, синхронизация состоит из двух операций:

| Операция | Запрос                   | Что делает                                                           |
| -------- | ------------------------ | -------------------------------------------------------------------- |
| **Push** | `POST /api/v1/sync/push` | Отправляет в Hub новые кабели, правки их атрибутов и новые тесты     |
| **Pull** | `POST /api/v1/sync/pull` | Получает изменения отслеживаемых кабелей одной команды после курсора |

Отдельно от синхронизации:

- **каталог** кабелей команды — `GET /api/v1/teams/{teamId}/cables`, обычный постраничный список; из него пользователь выбирает, какой кабель загрузить;
- **ИИ-комментарии** — `POST /api/v1/insights`, без учётной записи ([ADR-018](../../adr/018-insights-proxy.md)).

**Отслеживаемый кабель** — кабель, который есть в Hub и копия которого лежит в приложении: приложение выгрузило его само или загрузило из каталога. Только по отслеживаемым кабелям приложение получает изменения.

Сервер ничего не помнит о клиенте между запросами: что выгружено и до какого места загружено, хранит приложение и само сообщает серверу.

## 2. Что хранит приложение

| Где     | Поле      | Значение                                                                                      |
| ------- | --------- | --------------------------------------------------------------------------------------------- |
| Команда | `cursor`  | Курсор изменений команды (раздел 5). Нет значения — по этой команде ещё ничего не загружалось |
| Кабель  | `team_id` | Команда в Hub. `NULL` — кабель только локальный                                               |
| Кабель  | `synced`  | Hub хотя бы раз подтвердил кабель (выгрузка принята или кабель загружен)                      |
| Кабель  | `version` | Последняя известная версия кабеля на сервере                                                  |
| Кабель  | `dirty`   | Есть локальные правки атрибутов, ещё не принятые сервером                                     |
| Тест    | `synced`  | Hub принял тест                                                                               |

Отслеживаемые кабели команды — кабели с этим `team_id` и `synced = true`.

Тест, однажды отправленный в Hub, локально не меняется: сервер узнаёт повтор по совпадению содержимого (раздел 3.4).

## 3. Push

### 3.1 Что отправляется

| Раздел запроса  | Что попадает                                                                              |
| --------------- | ----------------------------------------------------------------------------------------- |
| `cables`        | Кабели с `team_id` и `synced = false` — пользователь выбрал команду при первой выгрузке   |
| `cable_updates` | Кабели с `synced = true` и `dirty = true` — вместе с `version`, от которой сделана правка |
| `tests`         | Тесты с `synced = false` у кабелей, у которых есть `team_id`                              |

Кабели, которые пользователь не выгружал ни в одну команду, и их тесты не отправляются.

Один запрос — не больше **100 объектов** в сумме. Если накопилось больше, приложение отправляет несколько запросов: сначала все новые кабели, потом правки, потом тесты, чтобы тест не ушёл раньше своего кабеля.

### 3.2 Как сервер обрабатывает пакет

- Порядок внутри пакета: новые кабели → правки → тесты. Новый кабель и его тесты можно отправить в одном пакете.
- Весь пакет — одна транзакция, у каждого объекта своя точка сохранения. Отклонённый объект откатывается и **не мешает остальным**. Принятые объекты фиксируются вместе: если связь оборвалась или сервер упал до ответа, не записано ничего, и повтор пакета пройдёт как первая отправка.
- Ответ — всегда `200` с результатом по каждому объекту, даже если отклонены все. Ошибка всего запроса (`400`, `401`, `426`) означает, что пакет не обрабатывался.

### 3.3 Пример

```json
POST /api/v1/sync/push
{
  "cables": [
    { "id": "0192f1a0-…-01", "team_id": "0192e000-…-aa", "name": "XLR 5 м", "cable_type": "xlr",
      "color": "639922", "note": null, "created_at": "2026-10-18T14:02:11Z" }
  ],
  "cable_updates": [
    { "id": "0192d7c3-…-07", "version": 3, "name": "Jack 3 м (сцена)", "cable_type": "jack_trs",
      "color": "e24b4a", "note": "Заменён штекер", "assignee_id": null }
  ],
  "tests": [
    { "id": "0192f1a2-…-0b", "cable_id": "0192f1a0-…-01", "measured_at": "2026-10-18T14:05:40Z", "…": "…" }
  ]
}
```

```json
200 OK
{
  "cables": [
    { "id": "0192f1a0-…-01", "status": "accepted", "cable": { "id": "0192f1a0-…-01", "version": 1, "…": "…" } }
  ],
  "cable_updates": [
    { "id": "0192d7c3-…-07", "status": "rejected",
      "error": { "code": "version_conflict", "detail": "Кабель изменён другим участником" },
      "cable": { "id": "0192d7c3-…-07", "version": 4, "name": "Jack 3 м", "…": "…" } }
  ],
  "tests": [
    { "id": "0192f1a2-…-0b", "status": "accepted" }
  ]
}
```

### 3.4 Что делает приложение с результатом

| Результат           | Объект       | Что делает приложение                                                                                                                                |
| ------------------- | ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `accepted`          | новый кабель | `synced = true`, `version` из ответа. Если состояние в ответе отличается от локального (повтор после правки в вебе) — показать расхождение, раздел 4 |
| `accepted`          | правка       | `dirty = false`, `version` из ответа                                                                                                                 |
| `accepted`          | тест         | `synced = true`                                                                                                                                      |
| `version_conflict`  | правка       | Показать расхождение и предложить выбрать версию, раздел 4                                                                                           |
| `cable_archived`    | правка, тест | Сообщить, что кабель в архиве и не принимает изменений. Объект остаётся невыгруженным; вернуть кабель из архива можно в вебе                         |
| `cable_not_found`   | правка, тест | Кабеля в Hub нет. Если `synced = true` — кабель удалён в Hub (раздел 5.5); если `false` — ошибка приложения                                          |
| `no_team_access`    | любой        | Пользователь больше не участник команды (раздел 5.6)                                                                                                 |
| `id_conflict`       | кабель, тест | Объект с таким ID уже есть с другим содержимым (тест) или в другой команде (кабель). Ошибка приложения: показать и записать в лог                    |
| `cable_type_locked` | правка       | Тип нельзя менять: у кабеля уже есть тесты. Вернуть прежний тип                                                                                      |
| `not_a_member`      | правка       | Ответственный не состоит в команде. Сбросить ответственного и показать сообщение                                                                     |
| `validation_error`  | любой        | Объект не прошёл проверку структуры. Ошибка приложения: показать `detail` и записать в лог                                                           |

**Повтор.** Если ответ потерялся, приложение отправляет те же объекты ещё раз. Тест с тем же ID и тем же содержимым принимается повторно с тем же результатом; новый кабель с тем же ID в той же команде — тоже, в ответе его актуальное состояние. Правка при повторе может получить `version_conflict` от собственной первой отправки: тогда в ответе — кабель с уже применёнными своими значениями, расхождения нет, и приложение просто принимает серверную версию.

## 4. Конфликт атрибутов кабеля

Конфликт возникает, когда кабель изменили в Hub (в вебе или с другого телефона) после того, как приложение получило свою `version`, а в приложении в это время сделали свою правку.

1. Сервер отклоняет правку с `version_conflict` и возвращает актуальный кабель.
2. Приложение показывает расхождение по полям: «у вас — …, в Hub — …».
3. Пользователь выбирает:
   - **версию Hub** — приложение записывает кабель из ответа, `dirty = false`;
   - **свою** — приложение берёт `version` из ответа, оставляет свои значения и `dirty = true`; правка уйдёт со следующим push как обычная. В журнале команды она появится как изменение с «было / стало», так что чужая правка не откатывается незаметно.

Слияния по отдельным полям нет: выбирается версия кабеля целиком.

## 5. Pull

### 5.1 Номер изменения и курсор

У каждой команды в Hub есть счётчик изменений. Любое изменение внутри команды получает следующий номер: создание кабеля, правка атрибутов (включая ответственного), архивирование и возврат, новый тест, пометка теста недействительным и её снятие. Номер записывается в изменённую строку кабеля или теста, поэтому **каждая строка хранит номер своего последнего изменения**.

Пример жизни одного кабеля:

| Событие                         | Номер | Номера строк после события   |
| ------------------------------- | ----: | ---------------------------- |
| Кабель создан                   |     1 | кабель = 1                   |
| Тест A выгружен                 |     2 | кабель = 1, A = 2            |
| Тест B выгружен                 |     3 | кабель = 1, A = 2, B = 3     |
| Кабель переименован             |     4 | **кабель = 4**, A = 2, B = 3 |
| Тест A помечен недействительным |     5 | кабель = 4, **A = 5**, B = 3 |

Строки с номером больше N — ровно то, что изменилось после отметки N.

**Курсор** — отметка, до которой приложение уже получило все изменения отслеживаемых кабелей команды. Приложение хранит один курсор на команду и присылает его в каждом pull; сервер отвечает изменениями с номерами больше курсора и новым курсором.

Почему номер, а не время изменения: транзакции фиксируются не в том порядке, в каком начались, и изменение с более ранним временем может стать видимым позже. По условию «изменено после T» приложение его бы пропустило. Номера внутри команды выдаются под блокировкой и идут строго в порядке фиксации ([data-model.md, раздел 5.1](data-model.md#51-счётчик-изменений-команды)).

### 5.2 Запрос и ответ

```json
POST /api/v1/sync/pull
{ "team_id": "0192e000-…-aa", "cursor": 3, "cables": ["0192f1a0-…-01", "0192d7c3-…-07"] }
```

```json
200 OK
{
  "cables": [ { "id": "0192f1a0-…-01", "name": "XLR 5 м (сцена)", "version": 2, "…": "…" } ],
  "tests": [ { "id": "0192f1a2-…-0b", "invalidation": { "reason": "Не тот кабель", "…": "…" }, "…": "…" } ],
  "deleted_cables": [],
  "cursor": 5,
  "has_more": false
}
```

- `cables` — отслеживаемые кабели, изменённые после курсора, целиком.
- `tests` — новые и изменённые тесты отслеживаемых кабелей, по возрастанию номера изменения, не больше 100.
- `deleted_cables` — отслеживаемые кабели, которых в команде больше нет (раздел 5.5).
- `cursor` — новый курсор; `has_more` — есть ли ещё изменения.

Ответ строится по одному снимку БД: кабели, тесты, удалённые кабели и курсор согласованы между собой.

### 5.3 Страницы

Если изменений больше 100, сервер отдаёт первые 100 по порядку номеров, `cursor` указывает на последний отданный номер, `has_more = true`. Приложение повторяет pull с новым курсором, пока `has_more` не станет `false`.

### 5.4 Как приложение применяет ответ

- Каждую страницу — **в одной транзакции SQLite вместе с новым курсором.** Если приложение закрылось или связь оборвалась между страницами, ничего не теряется: следующий pull продолжит с сохранённого курсора.
- Кабели и тесты записываются **поверх по ID**: запись того же объекта второй раз ничего не ломает. На этом держится правило первой загрузки (раздел 6).
- Если у кабеля `dirty = true`, его атрибуты и `version` из pull **не записываются**: локальная правка ещё не выгружена, и при следующем push сервер вернёт конфликт с актуальным состоянием (раздел 4). Тесты такого кабеля записываются как обычно.
- Пока у загружаемого кабеля `has_more = true`, приложение может показывать его как «загружается», чтобы пользователь не видел неполную историю.

### 5.5 Удалённые кабели

Кабель в Hub удаляется окончательно, вместе с тестами, и отдельной отметки об удалении сервер не хранит. Поэтому приложение присылает список отслеживаемых кабелей, а сервер возвращает в `deleted_cables` те, которых в команде больше нет.

Получив кабель в `deleted_cables`, приложение перестаёт его отслеживать (`team_id = NULL`, `synced = false`) и сообщает, что кабель удалён в Hub. Локальная копия с историей остаётся на телефоне; пользователь может удалить её сам.

Тот же признак — `cable_not_found` в ответе push для кабеля с `synced = true`.

Если на телефоне кабель просто перестали отслеживать, сервер об этом не узнаёт: приложение перестаёт передавать его ID.

### 5.6 Потеря доступа к команде

Если пользователь вышел из команды или его исключили, pull по этой команде отвечает `403` с `code: no_team_access`, push — тем же кодом для её объектов. Приложение прекращает синхронизацию этой команды, сообщает пользователю и оставляет локальные копии: копии на телефоне не отзываются (HUB-2).

## 6. Первая загрузка кабеля

Пользователь выбрал в каталоге кабель Z, которого на телефоне нет.

1. Pull только по этому кабелю с курсором 0: `{"team_id": "…", "cursor": 0, "cables": ["Z"]}`. Сервер отдаёт кабель и всю его историю — страницами, как в разделе 5.3.
2. Кабель Z становится отслеживаемым: `synced = true`, `version` из ответа.
3. Курсор команды обновляется по правилу ниже.

### 6.1 Правило курсора при первой загрузке

> **Первая загрузка кабеля не сдвигает курсор команды, если он уже есть.** Если курсора у команды ещё нет, записывается курсор из ответа первой загрузки.

Почему так. Курсор команды обещает: «все изменения *всех* отслеживаемых кабелей команды с номером не больше курсора у приложения уже есть». Первая загрузка Z даёт это только для Z.

Пример. Приложение отслеживает кабели X и Y, курсор команды — 100. Тем временем в Hub появились изменения X и Y с номерами 101–120.

| Шаг                    | Запрос                           | Что получено                                                        |  Курсор команды |
| ---------------------- | -------------------------------- | ------------------------------------------------------------------- | --------------: |
| До загрузки            | —                                | —                                                                   |             100 |
| Первая загрузка Z      | `cursor: 0, cables: [Z]`         | Вся история Z; курсор в ответе — 120                                | **100**, не 120 |
| Следующий обычный pull | `cursor: 100, cables: [X, Y, Z]` | Изменения X и Y после 100 и повторно изменения Z с номерами 101–120 |             120 |

Если бы на втором шаге приложение записало 120, изменения X и Y с номерами 101–120 были бы потеряны: их никто не запрашивал, а следующий pull начался бы после 120. Повторно полученные изменения Z безвредны: они записываются поверх по ID (раздел 5.4).

Если курсора у команды нет — Z первый отслеживаемый кабель этой команды на телефоне, — других кабелей, которые можно пропустить, нет, и приложение записывает курсор из ответа.

То же правило действует, когда приложение само выгрузило новый кабель: если у команды ещё нет курсора, приложение считает его равным 0, и следующий pull вернёт историю кабеля, которая у приложения уже есть. Это лишний, но безвредный трафик.

### 6.2 Назначить себя ответственным

При загрузке кабеля можно сразу назначить себя ответственным (HUB-7): это обычная правка атрибутов с `assignee_id` текущего пользователя — в следующем push или сразу через `PUT /api/v1/cables/{cableId}`.

## 7. Сеанс синхронизации

Когда синхронизироваться, решает приложение — например, после каждого теста, при открытии раздела Hub и по кнопке. Порядок внутри сеанса:

1. **Push** — пачками по 100 объектов, пока есть что отправлять.
2. **Pull** — по каждой команде, у которой есть отслеживаемые кабели, пока `has_more = true`.

Push идёт первым, чтобы локальные правки дошли до сервера раньше, чем pull принесёт чужие. Свои только что выгруженные тесты вернутся в pull ещё раз — запись поверх по ID ничего не ломает.

Без связи приложение ничего не отправляет и копит объекты; сеанс синхронизации начнётся, когда связь появится.

## 8. Ошибки уровня запроса

| Ответ | `code`             | Когда                                              | Что делает приложение                                         |
| ----- | ------------------ | -------------------------------------------------- | ------------------------------------------------------------- |
| `401` | `unauthorized`     | Сеанс истёк или завершён                           | Предложить войти заново; несинхронизированные данные остаются |
| `403` | `no_team_access`   | Pull по команде, в которой пользователь не состоит | Раздел 5.6                                                    |
| `426` | `app_outdated`     | Версия из `X-App-Version` ниже минимальной         | Предложить обновить приложение; синхронизация остановлена     |
| `400` | `validation_error` | Запрос не соответствует контракту                  | Ошибка приложения: записать в лог                             |
| `5xx` | —                  | Ошибка сервера                                     | Повторить позже; данные остаются невыгруженными               |
